## 1. 데이터베이스 보안의 핵심 원칙

데이터베이스 보안은 단순히 특정 기술을 적용하는 것을 넘어, 데이터를 안전하게 보호하기 위한 체계적인 접근 방식과 원칙을 수립하는 것에서 시작합니다. 모든 보안 전략의 기반이 되는 세 가지 핵심 원칙은 다음과 같으며, 이 원칙들은 서로를 보완하며 데이터베이스의 기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability)을 보장하는 데 목적이 있습니다.

### 1.0.1. 데이터베이스 보안의 3요소: 기밀성, 무결성, 가용성 (CIA Triad)

데이터베이스 보안의 궁극적인 목표는 정보 보안의 핵심 3요소인 기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability)을 보장하는 것입니다. 이 세 가지 요소는 서로 밀접하게 연관되어 있으며, 어느 하나라도 손상되면 데이터베이스 시스템의 신뢰성이 저하됩니다.

*   **기밀성 (Confidentiality):**
    인가된 사용자만이 데이터에 접근할 수 있도록 보장하는 원칙입니다. 민감한 정보가 비인가된 개인이나 시스템에 노출되는 것을 방지하는 데 중점을 둡니다.
    *   **위협:** 데이터 유출, 스니핑(Sniffing), 비인가된 접근.
    *   **방어 기법:**
        *   **접근 제어:** 최소 권한의 원칙(PoLP)을 적용하여 사용자별, 역할별로 접근 가능한 데이터와 수행 가능한 작업을 엄격하게 제한합니다. 예를 들어, 인사팀 직원에게는 모든 직원 정보에 대한 `SELECT` 권한을 부여하지만, 일반 부서 직원에게는 자신의 부서 직원 정보만 조회할 수 있는 뷰(`VIEW`)에 대한 `SELECT` 권한만 부여합니다.
        *   **데이터 암호화:**
            *   **전송 중 암호화 (Encryption in Transit):** SSL/TLS 등을 사용하여 클라이언트와 서버 간 통신 구간의 데이터를 암호화합니다.
            *   **저장 시 암호화 (Encryption at Rest):** TDE(Transparent Data Encryption)나 파일 시스템 암호화 등을 통해 디스크에 저장된 데이터를 암호화합니다. 실무적으로는 주민등록번호나 신용카드 정보와 같은 민감 데이터는 데이터베이스에 저장하기 전에 AES-256과 같은 강력한 알고리즘으로 암호화하여 저장합니다.
        *   **데이터 마스킹/비식별화:** 실제 민감 데이터를 노출하지 않고, 테스트나 분석 목적으로 가공된 데이터를 제공합니다. 개발/테스트 환경에서는 실제 고객의 이메일 주소를 `user***@example.com`과 같이 일부만 보이게 마스킹하거나, 이름, 주소 등을 가상의 값으로 대체하여 사용합니다.

*   **무결성 (Integrity):**
    데이터가 정확하고 완전하며, 인가된 방식으로만 변경될 수 있도록 보장하는 원칙입니다. 데이터의 신뢰성과 일관성을 유지하는 데 중점을 둡니다.
    *   **위협:** 데이터 변조, 삭제, 삽입, SQL 인젝션, 데이터 손상.
    *   **방어 기법:**
        *   **접근 제어:** `INSERT`, `UPDATE`, `DELETE`와 같은 DML 권한을 엄격하게 관리하고, 인가된 사용자만이 데이터를 변경할 수 있도록 합니다. 웹 애플리케이션 계정에는 `SELECT` 및 `INSERT` 권한만 부여하고, `UPDATE`나 `DELETE` 권한은 특정 관리자 계정에만 부여하여 데이터의 무단 변경을 방지합니다.
        *   **데이터 유효성 검증:** 애플리케이션 및 데이터베이스 레벨에서 입력값 유효성 검증(Input Validation)을 수행하여 비정상적인 데이터 입력을 차단합니다. 회원가입 시 이메일 주소 형식(`@`, `.` 포함 여부)을 검증하고, 숫자만 입력되어야 하는 필드에 문자열이 들어오지 않도록 데이터베이스의 `CHECK` 제약조건이나 애플리케이션 로직으로 확인합니다.
        *   **트랜잭션 관리:** ACID 속성을 준수하는 트랜잭션을 통해 데이터 변경 작업의 원자성, 일관성, 고립성, 지속성을 보장합니다. 은행 계좌 이체 시, 출금과 입금 두 작업이 모두 성공하거나 모두 실패하도록 하나의 트랜잭션으로 묶어 처리하여 데이터 불일치를 방지합니다.
        *   **감사 및 로깅:** 모든 데이터 변경 이력을 상세하게 기록하고, 비인가된 변경 시도를 탐지합니다. 관리자 계정으로 중요 테이블의 데이터가 변경될 때마다, 변경 전후 값, 변경 시각, 변경자 IP 등의 정보를 감사 로그 테이블에 기록하여 추후 문제 발생 시 원인을 파악할 수 있도록 합니다.
        *   **백업 및 복구:** 데이터 손상 시 원본 데이터를 복원할 수 있도록 정기적인 백업 및 복구 전략을 수립합니다. 매일 새벽 2시에 전체 데이터베이스 백업을 수행하고, 주 1회는 백업 데이터의 복원 테스트를 진행하여 실제 재해 발생 시 데이터 손실을 최소화할 수 있도록 대비합니다.

*   **가용성 (Availability):**
    인가된 사용자가 필요할 때 언제든지 데이터에 접근하고 사용할 수 있도록 보장하는 원칙입니다. 시스템이 정상적으로 작동하여 서비스 중단 없이 데이터를 제공하는 데 중점을 둡니다.
    *   **위협:** 서비스 거부 공격(DoS/DDoS), 하드웨어 장애, 소프트웨어 오류, 네트워크 문제, 자연재해.
    *   **방어 기법:**
        *   **고가용성(High Availability) 아키텍처:** 데이터베이스 클러스터링, 복제(Replication), 미러링(Mirroring) 등을 통해 단일 장애점(Single Point of Failure)을 제거하고 시스템 중단 시간을 최소화합니다. 주(Primary) 데이터베이스 서버에 장애가 발생하더라도, 실시간으로 데이터를 동기화하고 있던 보조(Secondary) 서버로 자동으로 전환(Failover)되어 서비스 중단 없이 데이터베이스를 계속 사용할 수 있도록 구성합니다.
        *   **재해 복구(Disaster Recovery) 계획:** 재해 발생 시 데이터를 복구하고 서비스를 재개하기 위한 상세한 계획을 수립하고 주기적으로 훈련합니다. 지진이나 화재와 같은 대규모 재해에 대비하여, 주 데이터센터와 수백 킬로미터 떨어진 원격지에 재해 복구 센터를 구축하고, 주기적으로 DR 훈련을 실시하여 실제 재해 상황에 대응할 수 있는 역량을 확보합니다.
        *   **성능 튜닝:** 쿼리 최적화, 인덱스 관리, 시스템 리소스 튜닝 등을 통해 데이터베이스의 응답 속도를 유지하고 과부하를 방지합니다. 특정 시간대에 발생하는 느린 쿼리를 `EXPLAIN`으로 분석하여 인덱스를 추가하거나 쿼리를 재작성함으로써, 사용자가 서비스 지연 없이 데이터를 조회할 수 있도록 합니다.
        *   **모니터링 및 알림:** 시스템 리소스(CPU, 메모리, 디스크 I/O) 및 데이터베이스 성능 지표를 지속적으로 모니터링하고, 임계치 초과 시 즉시 알림을 발생시켜 선제적으로 대응합니다. 데이터베이스 서버의 CPU 사용률이 80%를 5분 이상 초과하거나, 디스크 사용량이 90%에 도달하면 담당자에게 SMS나 이메일로 자동 알림을 보내어 장애 발생 전에 미리 조치할 수 있도록 합니다.
        *   **정기적인 유지보수:** 소프트웨어 패치, 하드웨어 점검 등을 통해 시스템의 안정성을 유지합니다. 매월 정기적으로 데이터베이스 소프트웨어의 보안 패치를 적용하고, 서버 하드웨어의 디스크 상태를 점검하여 잠재적인 장애 요소를 사전에 제거합니다.

### 1.1. 최소 권한의 원칙 (Principle of Least Privilege)

**개념:** '알아야 할 필요'와 '해야 할 필요'에 기반하여, 사용자나 애플리케이션에 업무 수행에 필요한 최소한의 권한만 부여하는 원칙입니다. 이는 데이터베이스 보안에서 가장 기본적이면서도 가장 중요한 원칙입니다.

**중요성:**
*   **실수 방지:** 데이터 분석가가 실수로 `UPDATE`나 `DELETE` 문을 실행하여 운영 데이터를 변경하는 사고를 원천적으로 방지할 수 있습니다.
*   **피해 최소화:** 애플리케이션의 계정이 탈취되더라도, 공격자는 해당 계정이 가진 최소한의 권한 내에서만 활동할 수 있으므로 피해 범위를 크게 줄일 수 있습니다.
*   **책임 추적 용이성:** 각 사용자가 자신에게 부여된 명확한 권한 내에서만 활동하므로, 문제 발생 시 원인을 파악하고 책임 소재를 명확히 하는 데 용이합니다.

**실무 적용:**
*   **`root` 계정 사용 금지:** `root`나 `sa` 같은 최고 관리자 계정은 서버 관리 및 초기 설정 용도로만 사용하고, 일상적인 애플리케이션 연결이나 데이터 분석 작업에는 절대 사용하지 않습니다.
*   **역할별 사용자 생성:** 각 사용자 및 서비스(애플리케이션)별로 별도의 데이터베이스 계정을 생성합니다.
    *   **데이터 분석가:** 일반적으로 운영 데이터베이스의 테이블에 대해 `SELECT` 권한만 부여받습니다.
    *   **웹 애플리케이션:** 회원 정보 테이블에는 `SELECT`, `INSERT`, `UPDATE` 권한을, 주문 관련 테이블에는 추가적으로 `DELETE` 권한을 부여하는 등 역할에 따라 필요한 권한만 세분화하여 부여합니다.
*   **구체적인 권한 부여:** `GRANT ALL PRIVILEGES`와 같이 포괄적인 권한 대신, `GRANT SELECT, INSERT ON specific_table TO 'user'@'host';`와 같이 특정 객체에 대한 특정 권한을 명시적으로 부여합니다.

### 1.2. 심층 방어 (Defense in Depth)

**개념:** 단 하나의 보안 계층에 의존하지 않고, 여러 개의 독립적인 보안 계층을 겹겹이 쌓아 하나의 방어선이 뚫리더라도 다음 방어선이 공격을 막을 수 있도록 하는 전략입니다. 이는 마치 성을 지키기 위해 해자, 성벽, 감시탑, 내부 경비병 등 다중 방어 체계를 구축하는 것과 같습니다.

**실무 적용:**
1.  **네트워크 계층:**
    *   **방화벽:** 데이터베이스 서버의 포트(예: MySQL 3306)는 특정 애플리케이션 서버나 관리자 IP 대역에서만 접근할 수 있도록 방화벽 규칙을 설정합니다.
    *   **VPC/사설망:** 데이터베이스를 인터넷에 직접 노출시키지 않고, 외부 접근이 통제된 가상 사설 클라우드(VPC)나 사설 네트워크 안에 배치합니다.
2.  **서버(OS) 계층:**
    *   **OS 강화(Hardening):** 데이터베이스가 실행되는 운영체제에 불필요한 서비스나 포트를 비활성화하고, 보안 패치를 최신 상태로 유지합니다.
3.  **데이터베이스(DBMS) 계층:**
    *   **인증 강화:** 강력한 비밀번호 정책(복잡도, 길이, 주기적 변경)을 강제하고, 가능하면 다중 인증(MFA)을 도입합니다.
    *   **권한 제어:** 최소 권한의 원칙에 따라 사용자 권한을 정밀하게 제어합니다.
    *   **데이터 암호화:** SSL/TLS를 사용해 클라이언트와 서버 간 통신을 암호화(전송 중 암호화)하고, TDE(Transparent Data Encryption) 등의 기능을 사용해 디스크에 저장된 데이터를 암호화(저장 시 암호화)합니다.
4.  **애플리케이션 계층:**
    *   **SQL 인젝션 방지:** 모든 SQL 쿼리는 반드시 매개변수화된 쿼리(Parameterized Query) 또는 준비된 구문(Prepared Statement)을 사용하여 작성합니다.
5.  **데이터 및 감사 계층:**
    *   **감사 로그:** 중요한 데이터에 대한 접근 및 변경 이력을 기록하고 주기적으로 검토하여 비정상적인 활동을 탐지합니다.

### 1.3. 공격 표면 최소화 (Attack Surface Minimization)

**개념:** 공격자가 악용할 수 있는 시스템의 잠재적인 진입점(공격 표면)의 수를 줄이는 원칙입니다. 시스템이 외부에 노출하는 기능이 적을수록, 공격자가 발견하고 악용할 수 있는 취약점도 줄어듭니다.

**실무 적용:**
*   **불필요한 기능 비활성화:** 데이터베이스가 제공하는 기능 중 현재 사용하지 않는 기능(예: 특정 저장 프로시저, 원격 접속 기능, 파일 입출력 명령어)은 비활성화합니다.
*   **네트워크 노출 제한:** 데이터베이스가 꼭 필요한 네트워크 인터페이스와 포트에서만 리스닝하도록 설정합니다. 예를 들어, 로컬 애플리케이션만 사용한다면 `localhost`에서만 접속을 허용합니다.
*   **계정 관리:** 사용하지 않는 오래된 사용자 계정이나 기본적으로 생성된 테스트용 계정은 즉시 삭제하거나 비활성화합니다.
*   **소프트웨어 최소화:** 데이터베이스 서버에는 데이터베이스 운영과 직접적으로 관련 없는 소프트웨어(예: 웹 서버, 컴파일러)를 설치하지 않습니다.
*   **샘플 데이터베이스 제거:** 설치 시 함께 제공되는 `test`와 같은 샘플 데이터베이스는 알려진 취약점이나 기본 계정을 포함할 수 있으므로, 프로덕션 환경에서는 반드시 제거합니다.

## 2. 사용자 및 권한 관리 (DCL)

데이터 제어어(DCL, Data Control Language)는 데이터베이스에 대한 접근 권한을 부여(`GRANT`)하거나 회수(`REVOKE`)하는 데 사용되는 명령어 그룹입니다. DCL은 1장에서 다룬 '최소 권한의 원칙'을 실제로 구현하는 핵심적인 도구이며, 이를 통해 관리자는 어떤 사용자가 어떤 데이터에 접근하여 어떤 작업을 수행할 수 있는지를 정밀하게 통제할 수 있습니다.

### 2.1. 사용자 계정 관리 (`CREATE`, `ALTER`, `DROP USER`)

권한을 관리하기 위한 첫 단계는 사용자를 식별할 수 있는 계정을 생성하고 관리하는 것입니다.

*   **`CREATE USER`**: 새로운 사용자 계정을 생성합니다.

    **기본 문법:**
    ```sql
    CREATE USER 'username'@'hostname' IDENTIFIED BY 'password';
    ```

    *   `'username'`: 생성할 사용자의 이름입니다.
    *   `'hostname'`: 해당 사용자가 접속을 허용할 IP 주소나 호스트명을 지정합니다. 이는 매우 중요한 보안 설정입니다.
        *   `'localhost'` 또는 `'127.0.0.1'`: 데이터베이스 서버 내부에서만 접속을 허용합니다.
        *   `'192.168.1.100'`: 특정 IP 주소에서만 접속을 허용합니다. (예: 애플리케이션 서버)
        *   `'192.168.1.%'`: 특정 IP 대역(`192.168.1.x`)에서의 접속을 허용합니다.
        *   `'%'`: **모든 외부 IP**에서의 접속을 허용합니다. 보안상 매우 취약하므로, 특별한 경우가 아니라면 절대 사용하지 않는 것이 좋습니다.
    *   `IDENTIFIED BY 'password'`: 사용자의 비밀번호를 설정합니다. 항상 복잡하고 예측 불가능한 비밀번호를 사용해야 합니다.

    **실무 예제:**
    ```sql
    -- 데이터 분석가 'sally'를 특정 데스크톱 IP에서만 접속 가능하도록 생성
    CREATE USER 'sally'@'192.168.10.55' IDENTIFIED BY 'P@ssw0rd_for_sally_!@#';

    -- 웹 애플리케이션을 위한 서비스 계정 생성
    CREATE USER 'webapp_user'@'192.168.1.10' IDENTIFIED BY 'a_very_long_and_complex_password_for_app';
    ```

*   **`ALTER USER`**: 기존 사용자 계정의 속성을 변경합니다.

    주로 비밀번호 변경, 비밀번호 만료 정책 설정, 계정 잠금 등의 용도로 사용됩니다.

    **실무 예제:**
    ```sql
    -- 사용자 비밀번호 변경
    ALTER USER 'sally'@'192.168.10.55' IDENTIFIED BY 'a_new_and_stronger_password';

    -- 90일마다 비밀번호를 변경하도록 설정 (MySQL 기준)
    ALTER USER 'webapp_user'@'192.168.1.10' PASSWORD EXPIRE INTERVAL 90 DAY;

    -- 퇴사 등의 이유로 계정을 일시적으로 잠금
    ALTER USER 'sally'@'192.168.10.55' ACCOUNT LOCK;
    ```

*   **`DROP USER`**: 사용자 계정을 영구적으로 삭제합니다.

    **실무 예제:**
    ```sql
    -- 더 이상 사용하지 않는 계정 삭제
    DROP USER 'sally'@'192.168.10.55';
    ```
    **주의:** 사용자를 삭제하기 전에 해당 사용자가 소유한 데이터베이스 객체는 없는지, 실행 중인 프로세스는 없는지 확인하는 것이 안전합니다.

### 2.2. 권한 부여 및 회수 (`GRANT`, `REVOKE`)

사용자 계정을 생성한 후에는 해당 사용자에게 필요한 권한을 부여하고, 불필요한 권한은 회수해야 합니다.

*   **`GRANT`**: 사용자에게 특정 권한을 부여합니다.

    **기본 문법:**
    ```sql
    GRANT [권한 종류] ON [객체 종류] [객체 이름] TO 'username'@'hostname';
    ```

    *   **권한 종류:** `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `EXECUTE`(프로시저 실행), `ALL PRIVILEGES`(모든 권한) 등
    *   **객체 이름:** `database_name.*`(데이터베이스 내 모든 객체), `database_name.table_name`(특정 테이블) 등

    **실무 예제 (최소 권한의 원칙 적용):**
    ```sql
    -- 데이터 분석가 'sally'에게 'sales' 데이터베이스의 모든 테이블에 대한 읽기(SELECT) 권한만 부여
    GRANT SELECT ON sales.* TO 'sally'@'192.168.10.55';

    -- 웹 애플리케이션 'webapp_user'에게 'users' 테이블에 대한 조회, 삽입, 수정 권한 부여
    GRANT SELECT, INSERT, UPDATE ON my_app.users TO 'webapp_user'@'192.168.1.10';

    -- 다른 사용자에게 권한을 부여할 수 있는 권한까지 함께 부여 (매우 신중하게 사용해야 함)
    -- GRANT ALL PRIVILEGES ON my_app.* TO 'dev_lead'@'%' WITH GRANT OPTION;
    ```

*   **`REVOKE`**: 사용자에게 부여된 권한을 회수합니다.

    **기본 문법:**
    ```sql
    REVOKE [권한 종류] ON [객체 이름] FROM 'username'@'hostname';
    ```

    **실무 예제:**
    ```sql
    -- 'webapp_user'의 'users' 테이블에 대한 UPDATE 권한 회수
    REVOKE UPDATE ON my_app.users FROM 'webapp_user'@'192.168.1.10';
    ```

### 2.3. 역할 기반 접근 제어 (RBAC: `CREATE ROLE`)

사용자가 많아지면 각 개인에게 일일이 권한을 부여하고 관리하는 것은 비효율적이고 실수를 유발하기 쉽습니다. **역할 기반 접근 제어(RBAC, Role-Based Access Control)**는 여러 권한을 '역할(Role)'이라는 하나의 그룹으로 묶고, 사용자에게는 이 역할 자체를 부여하는 효율적인 권한 관리 방식입니다.

**RBAC 워크플로우:**
1.  **역할 생성:** 직무에 따라 필요한 역할을 생성합니다.
    ```sql
    CREATE ROLE 'data_analyst_role', 'web_developer_role';
    ```
2.  **역할에 권한 부여:** 각 역할에 필요한 권한들을 부여합니다.
    ```sql
    -- 데이터 분석가 역할에 sales DB 읽기 권한 부여
    GRANT SELECT ON sales.* TO 'data_analyst_role';

    -- 웹 개발자 역할에 app DB 모든 권한 부여
    GRANT SELECT, INSERT, UPDATE, DELETE ON my_app.* TO 'web_developer_role';
    ```
3.  **사용자에게 역할 부여:** 생성한 역할을 실제 사용자에게 부여합니다.
    ```sql
    -- 신입 분석가 'bob'에게 데이터 분석가 역할 부여
    GRANT 'data_analyst_role' TO 'bob'@'192.168.10.56';

    -- 개발자 'alice'에게 웹 개발자 역할 부여
    GRANT 'web_developer_role' TO 'alice'@'192.168.1.11';
    ```
4.  **기본 역할 활성화:** 사용자가 로그인할 때마다 부여된 역할이 자동으로 활성화되도록 설정합니다.
    ```sql
    SET DEFAULT ROLE ALL TO 'bob'@'192.168.10.56', 'alice'@'192.168.1.11';
    ```

**RBAC의 장점:**
*   **관리 간소화:** 신입 사원이 입사하면 해당 직무의 역할만 부여하면 되므로 관리가 매우 편리해집니다. 권한 변경이 필요할 때도 역할의 권한만 수정하면 해당 역할을 가진 모든 사용자에게 일괄 적용됩니다.
*   **일관성 및 표준화:** 동일 직무를 가진 모든 사용자가 동일한 권한을 갖게 되어 권한 부여의 일관성을 유지할 수 있습니다.
*   **보안 강화:** 사람 중심이 아닌 역할 중심으로 권한을 관리하므로, 불필요한 권한이 잘못 부여될 가능성이 줄어듭니다.

### 2.4. 부여된 권한 확인 (`SHOW GRANTS`)

사용자나 역할에 어떤 권한이 부여되어 있는지 확인하는 것은 보안 관리의 필수적인 부분입니다.

**기본 문법:**
```sql
SHOW GRANTS FOR 'username'@'hostname';
```

**실무 예제:**
```sql
-- 'bob' 사용자에게 부여된 권한 확인
SHOW GRANTS FOR 'bob'@'192.168.10.56';

-- 'data_analyst_role' 역할에 부여된 권한 확인
SHOW GRANTS FOR 'data_analyst_role';

-- 현재 접속한 사용자의 권한 확인
SHOW GRANTS FOR CURRENT_USER;
-- 또는 간단히
SHOW GRANTS;
```
`SHOW GRANTS`의 결과에는 사용자에게 직접 부여된 권한과, 역할을 통해 부여된 권한이 모두 표시되므로, 현재 사용자가 어떤 작업을 수행할 수 있는지 정확하게 파악할 수 있습니다.


## 3. 주요 보안 위협과 방어 기법

데이터베이스 보안 원칙을 수립하고 사용자 권한을 정밀하게 관리하더라도, 공격자들은 시스템의 취약점을 파고드는 다양한 공격을 시도합니다. 이 섹션에서는 데이터베이스가 직면하는 가장 대표적인 보안 위협과 그에 대한 효과적인 방어 기법을 다룹니다.

### 3.1. SQL 인젝션 (SQL Injection)

**개념:** 공격자가 애플리케이션의 입력값(예: 로그인 폼, 검색창, URL 파라미터)을 조작하여 의도치 않은 악의적인 SQL 코드를 데이터베이스에서 실행하게 만드는 공격 기법입니다. 가장 오래되었지만 여전히 가장 치명적인 웹 애플리케이션 보안 취약점 중 하나입니다.

**공격 원리 및 예시:**

공격은 주로 사용자의 입력을 검증 없이 그대로 받아 동적 SQL 쿼리를 만드는 코드에서 발생합니다.

*   **상황:** 사용자의 아이디와 비밀번호를 받아 로그인시키는 PHP 코드

*   **취약한 코드 (절대 이렇게 작성하면 안 됩니다):**
    ```php
    <?php
        $userId = $_POST['user_id']; // 사용자로부터 아이디 입력 받음
        $userPw = $_POST['user_pw']; // 사용자로부터 비밀번호 입력 받음

        // 사용자의 입력을 그대로 문자열로 합쳐서 쿼리를 생성
        $query = "SELECT * FROM users WHERE user_id = '" . $userId . "' AND password = '" . $userPw . "';";
        
        // ... 이 쿼리를 데이터베이스에 실행 ...
    ?>
    ```

*   **공격자의 악의적인 입력:**
    사용자가 비밀번호를 모르는 상태에서, `user_id` 입력창에 다음과 같이 입력합니다.
    `admin' OR '1'='1`

*   **데이터베이스에서 실제 실행되는 쿼리:**
    위 입력값으로 인해 서버에서 조립된 최종 SQL 쿼리는 다음과 같이 변질됩니다.
    ```sql
    SELECT * FROM users WHERE user_id = 'admin' OR '1'='1' AND password = '...';
    ```
    `WHERE` 절의 `user_id = 'admin'` 부분은 거짓이지만, `OR '1'='1'` 조건이 항상 참(TRUE)이므로 `WHERE` 절 전체가 참이 되어버립니다. 결과적으로 인증을 우회하고 `users` 테이블의 첫 번째 사용자인 `admin`으로 로그인하게 될 수 있습니다.

*   **추가적인 위협:** 공격자는 `UNION`을 사용하여 다른 테이블의 정보를 빼내거나, `DROP TABLE` 같은 명령어를 주입하여 데이터를 파괴할 수도 있습니다.

**방어 기법:**

1.  **매개변수화된 쿼리 (Parameterized Query) 사용 (가장 중요하고 근본적인 해결책):**
    **준비된 구문(Prepared Statement)**이라고도 불리며, 사용자의 입력값이 SQL 쿼리의 구조를 변경할 수 없도록 원천적으로 차단하는 가장 효과적인 방법입니다. SQL문의 '틀'과 사용자의 '입력값'을 분리하여 데이터베이스에 전달하므로, 데이터베이스는 입력값을 절대 실행 코드로 해석하지 않고 순수한 데이터로만 취급합니다.

    *   **안전한 코드 (PHP PDO 예시):**
        ```php
        <?php
            $userId = $_POST['user_id'];
            $userPw = $_POST['user_pw'];

            // 1. SQL 쿼리의 '틀'을 준비 (입력값은 ? 플레이스홀더로 처리)
            $query = "SELECT * FROM users WHERE user_id = ? AND password = ?;";
            $stmt = $pdo->prepare($query);

            // 2. 입력값을 파라미터로 전달하여 쿼리 실행
            $stmt->execute([$userId, $userPw]);
            
            // ... 결과 처리 ...
        ?>
        ```

2.  **입력값 검증 (Input Validation):**
    애플리케이션단에서 사용자 입력값이 예상된 형식, 타입, 길이, 문자셋인지 항상 검증합니다. 예를 들어, 전화번호 필드에 SQL 특수문자가 포함되어 있다면 입력을 거부하는 방식입니다. 이는 SQL 인젝션 방어의 보조적인 수단입니다.

3.  **최소 권한의 원칙 적용:**
    웹 애플리케이션이 사용하는 데이터베이스 계정의 권한을 최소화합니다. 예를 들어, `SELECT`, `INSERT`, `UPDATE` 권한만 있고 `DROP` 권한이 없다면, 설령 SQL 인젝션 공격이 성공하더라도 테이블이 삭제되는 최악의 상황은 막을 수 있습니다.

### 3.2. 데이터 무단 접근

**개념:** SQL 인젝션 외에도 다양한 경로를 통해 인가되지 않은 사용자가 데이터베이스에 접근하여 데이터를 유출, 변조, 파괴하는 모든 행위를 포함합니다.

**주요 위협 경로:**
*   **취약한 인증 정보:** 사용자들이 `1234`, `password`, `admin` 등 추측하기 쉬운 비밀번호를 사용하거나, 여러 시스템에서 동일한 비밀번호를 재사용하는 경우입니다.
*   **인증 정보 탈취:** 피싱(Phishing) 공격, 사용자 PC의 악성코드, 또는 소스코드에 하드코딩된 데이터베이스 접속 정보가 외부에 노출되어 관리자 계정이 탈취될 수 있습니다.
*   **권한 상승 공격:** 공격자가 낮은 권한의 계정을 탈취한 후, 시스템의 다른 취약점을 이용해 관리자(root) 권한을 획득하는 공격입니다.
*   **보안이 취약한 백업:** 암호화되지 않은 데이터베이스 백업 파일이 외부 클라우드 스토리지나 파일 서버에 방치되어 유출되는 경우입니다.
*   **내부자 위협:** 허가된 권한을 가진 내부 직원이 악의적인 의도를 가지고 데이터를 유출하거나, 실수로 데이터를 외부에 노출하는 경우입니다.

**방어 기법 (심층 방어 전략):**

1.  **강력한 인증 체계 구축:**
    *   **비밀번호 정책 강화:** 데이터베이스와 애플리케이션 모두에 비밀번호 최소 길이, 복잡도(대/소문자, 숫자, 특수문자 조합), 주기적 변경 등의 정책을 강제합니다.
    *   **다중 인증 (MFA):** 특히 관리자 계정과 같이 중요한 계정에는 비밀번호 외에 OTP나 생체 인증 등 추가적인 인증 수단을 적용합니다.

2.  **엄격한 권한 관리 (최소 권한의 원칙):**
    2장에서 다룬 DCL과 RBAC를 철저히 적용하여, 모든 사용자와 서비스는 자신의 역할에 필요한 최소한의 데이터에만 접근할 수 있도록 통제합니다.

3.  **모든 구간에서의 데이터 암호화:**
    *   **전송 중 암호화 (Encryption in Transit):** 클라이언트와 데이터베이스 서버 간의 모든 통신은 SSL/TLS를 적용하여 암호화합니다. 이를 통해 네트워크상의 데이터 탈취(Eavesdropping)를 방지합니다.
    *   **저장 시 암호화 (Encryption at Rest):** TDE(Transparent Data Encryption)나 파일 시스템 레벨 암호화를 통해 데이터베이스 파일 자체가 디스크에 암호화된 상태로 저장되도록 합니다. 이는 서버나 백업 파일이 물리적으로 도난당하더라도 데이터를 보호할 수 있습니다.

4.  **지속적인 감사 및 모니터링:**
    *   **감사 로그 활성화:** 누가, 언제, 어디서, 어떤 데이터에 접근했는지 상세한 로그를 기록하고, 이를 정기적으로 분석하여 비정상적인 접근 패턴을 탐지합니다.
    *   **이상 행위 탐지:** 특정 시간대에 과도한 데이터를 조회하거나, 실패한 로그인 시도가 급증하는 등 이상 징후를 자동으로 탐지하고 경고하는 시스템을 구축합니다.

5.  **정기적인 보안 진단:**
    주기적으로 시스템의 취약점을 스캔하고, 모의 해킹(Penetration Testing)을 수행하여 잠재적인 보안 허점을 사전에 발견하고 조치합니다.


## 4. 객체를 활용한 보안 강화

`GRANT`와 `REVOKE`를 이용한 직접적인 권한 관리는 보안의 기본이지만, 때로는 더 정교하고 동적인 접근 제어가 필요합니다. 데이터베이스 객체인 **뷰(View)**와 **저장 프로시저(Stored Procedure)**는 기본 테이블에 대한 직접적인 접근을 차단하고, 잘 정의된 인터페이스(API) 역할의 추상화 계층을 제공함으로써 보안을 한층 더 강화할 수 있습니다.

### 4.1. 뷰(View)를 이용한 접근 제어

뷰는 하나 이상의 테이블을 기반으로 생성된 가상의 테이블입니다. 사용자에게 실제 테이블 대신 뷰에 대한 접근 권한을 부여함으로써, 보여주고자 하는 데이터만 선택적으로 노출할 수 있습니다.

**보안상 이점:**

*   **컬럼 수준 보안 (수직적 보안):** 테이블의 여러 컬럼 중, 민감한 정보(예: 연봉, 주민등록번호)를 제외한 특정 컬럼들만 선택하여 뷰를 생성하고, 해당 뷰에 대한 접근 권한만 사용자에게 부여할 수 있습니다.
*   **로우 수준 보안 (수평적 보안):** 뷰의 `WHERE` 절을 이용하여 특정 조건을 만족하는 로우들만 노출시킬 수 있습니다. 예를 들어, 각 부서의 매니저는 자기 부서 소속의 직원 정보만 볼 수 있도록 제한할 수 있습니다.
*   **복잡성 은닉:** 여러 테이블을 조인한 복잡한 쿼리를 뷰로 만들어두면, 사용자에게는 복잡한 스키마 구조를 숨기고 단순화된 데이터 집합만 제공할 수 있습니다.

**구현 단계 및 실무 예제:**

1.  **기본 테이블 정의:** `employees` 테이블에 민감한 정보인 `salary` 컬럼이 포함되어 있다고 가정합니다.

2.  **뷰 생성:**
    *   **예제 1: 컬럼 수준 보안**
        인사팀 외의 일반 사용자에게는 연봉 정보를 제외한 기본 직원 정보만 보여주는 뷰를 생성합니다.
        ```sql
        CREATE VIEW v_public_employees AS
        SELECT employee_id, first_name, last_name, email, department_name
        FROM employees e
        JOIN departments d ON e.department_id = d.department_id;
        ```

    *   **예제 2: 로우 수준 보안**
        영업부 매니저(`sales_manager`)에게는 영업부(department_id = 80) 소속 직원들의 정보만 보여주는 뷰를 생성합니다.
        ```sql
        CREATE VIEW v_sales_team AS
        SELECT employee_id, first_name, last_name, email
        FROM employees
        WHERE department_id = 80;
        ```

3.  **권한 재설정:**
    사용자에게 기본 테이블에 대한 직접 접근 권한을 회수하고, 생성된 뷰에 대한 권한을 부여합니다.
    ```sql
    -- 일반 사용자 'guest'에게는 기본 테이블 접근 권한을 회수
    REVOKE ALL PRIVILEGES ON employees FROM 'guest'@'localhost';

    -- 대신 v_public_employees 뷰에 대한 SELECT 권한만 부여
    GRANT SELECT ON v_public_documents TO 'guest'@'localhost';

    -- 영업부 매니저에게는 v_sales_team 뷰에 대한 SELECT 권한 부여
    GRANT SELECT ON v_sales_team TO 'sales_manager'@'localhost';
    ```
    이제 `guest` 사용자는 연봉 정보를 볼 수 없으며, `sales_manager`는 다른 부서의 직원 정보를 조회할 수 없게 됩니다.

### 4.2. 저장 프로시저(Stored Procedure)를 이용한 접근 제어

저장 프로시저는 특정 작업을 수행하기 위한 SQL 문의 집합을 데이터베이스에 저장해 둔 객체입니다. 사용자에게 테이블에 대한 직접적인 DML(`INSERT`, `UPDATE`, `DELETE`) 권한을 주는 대신, 프로시저를 실행(`EXECUTE`)할 권한만 부여하여 정해진 로직으로만 데이터를 조작하도록 강제할 수 있습니다.

**보안상 이점:**

*   **정해진 동작만 허용:** 사용자는 프로시저 내에 정의된 SQL 로직만 실행할 수 있으며, 임의의 `UPDATE`나 `DELETE` 문을 실행할 수 없습니다. 예를 들어, '직원 퇴사 처리' 프로시저는 퇴사일 기록, 관련 테이블 상태 업데이트 등 정해진 작업만 수행하도록 강제할 수 있습니다.
*   **입력값 검증:** 프로시저 내에서 매개변수에 대한 유효성 검증 로직을 추가하여, 비정상적인 데이터가 입력되는 것을 방지할 수 있습니다.
*   **공격 표면 축소:** 애플리케이션이나 사용자는 테이블에 대한 직접적인 DML 권한이 필요 없고, 오직 `EXECUTE` 권한만 있으면 되므로 공격 표면이 크게 줄어듭니다.
*   **감사 용이성:** 프로시저 내에 특정 작업이 실행될 때마다 로그 테이블에 기록을 남기는 로직을 쉽게 추가할 수 있습니다.

**구현 단계 및 실무 예제:**

1.  **상황 정의:** 일반 사용자가 자신의 비밀번호를 직접 변경할 수 있어야 하지만, 다른 사용자의 비밀번호나 `users` 테이블의 다른 컬럼을 수정해서는 안 됩니다.

2.  **저장 프로시저 생성:**
    사용자 ID와 새 비밀번호를 입력받아 비밀번호를 변경하는 프로시저를 생성합니다.
    ```sql
    DELIMITER //

    CREATE PROCEDURE sp_change_password(IN current_user_id INT, IN new_password VARCHAR(255))
    BEGIN
        -- 입력값 유효성 검증 (예: 비밀번호 길이, 복잡도 등)
        IF LENGTH(new_password) < 8 THEN
            SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Password must be at least 8 characters long.';
        END IF;

        -- 실제 데이터 변경 작업
        UPDATE users
        SET password_hash = SHA2(new_password, 256) -- 비밀번호는 항상 해시하여 저장
        WHERE user_id = current_user_id;

        -- 감사 로그 기록
        INSERT INTO audit_log (user_id, action, timestamp) 
        VALUES (current_user_id, 'Password Changed', NOW());

    END //

    DELIMITER ;
    ```

3.  **권한 부여:**
    웹 애플리케이션 사용자(`webapp_user`)에게 `users` 테이블에 대한 `UPDATE` 권한을 주는 대신, 이 프로시저를 실행할 권한만 부여합니다.
    ```sql
    -- 테이블에 대한 직접적인 UPDATE 권한은 없어야 함
    -- REVOKE UPDATE ON my_app.users FROM 'webapp_user'@'localhost';

    -- 프로시저 실행 권한만 부여
    GRANT EXECUTE ON PROCEDURE my_app.sp_change_password TO 'webapp_user'@'localhost';
    ```

4.  **애플리케이션에서의 호출:**
    이제 애플리케이션은 `UPDATE` 쿼리를 직접 실행하는 대신, 안전하게 프로시저를 호출합니다.
    ```sql
    CALL sp_change_password(123, 'new_secure_password_!@#');
    ```
    이러한 접근 방식은 애플리케이션 개발자가 실수로 잘못된 `UPDATE` 쿼리를 작성하는 것을 방지하고, 모든 비밀번호 변경 작업이 정해진 규칙과 감사 절차를 따르도록 보장합니다.


## 5. 데이터베이스 감사 (Auditing)

데이터베이스 감사는 사용자나 애플리케이션이 데이터베이스에 수행한 동작을 추적하고 기록하는 체계적인 절차입니다. 앞서 다룬 접근 제어(Access Control)가 허가되지 않은 접근을 막는 **예방(Preventive) 통제**라면, 감사는 사후에 어떤 일이 일어났는지 추적하고 분석하는 **탐지(Detective) 통제**에 해당합니다. "누가, 언제, 어떤 데이터에, 무슨 작업을 했는가?"를 기록하여 보안 사고 발생 시 원인을 규명하고, 비정상적인 행위를 탐지하며, 규제 준수 요구사항을 충족하는 데 핵심적인 역할을 합니다.

### 5.1. 감사의 개념과 필요성

**개념:** 데이터베이스 감사는 특정 이벤트가 발생했을 때, 그에 대한 상세 정보(예: 접속 IP, 사용자 계정, 실행된 쿼리, 접근한 테이블, 시간 등)를 시간 순서에 따라 **감사 추적(Audit Trail)** 또는 **감사 로그(Audit Log)**라는 형태로 기록하는 것을 의미합니다. 일반적으로 다음과 같은 활동들이 감사 대상이 됩니다.

*   서버 시작 및 종료
*   사용자 로그인 및 로그아웃 (성공 및 실패 이력 포함)
*   권한 변경 (`GRANT`, `REVOKE` 등 DCL 실행)
*   데이터베이스 스키마 변경 (`CREATE`, `ALTER`, `DROP` 등 DDL 실행)
*   중요 데이터에 대한 접근 (`SELECT`)
*   데이터 변경 (`INSERT`, `UPDATE`, `DELETE`)

**필요성:**

1.  **보안 사고 조사:** 데이터 유출이나 비인가된 데이터 변경과 같은 보안 사고가 발생했을 때, 감사 로그는 공격의 경로와 피해 범위를 파악하는 데 결정적인 증거 자료를 제공합니다.
2.  **이상 행위 탐지:** 평소와 다른 패턴의 활동을 분석하여 잠재적인 위협을 사전에 탐지할 수 있습니다. 예를 들어, 특정 사용자가 갑자기 대량의 데이터를 조회하거나, 특정 IP에서 반복적으로 로그인 실패가 발생하는 등의 이상 징후를 파악할 수 있습니다.
3.  **규제 준수 (Compliance):** 개인정보보호법(PII), GDPR, HIPAA, PCI-DSS 등 많은 산업 규제 및 법규는 민감한 데이터에 대한 접근 기록을 의무적으로 수집하고 보관하도록 요구합니다. 감사는 이러한 규제 준수의 필수 요건입니다.
4.  **내부자 위협 억제:** 모든 활동이 기록되고 있다는 사실만으로도 악의적인 의도를 가진 내부 사용자의 비정상적인 활동을 억제하는 효과가 있습니다.

### 5.2. 감사 로그 활성화 및 분석

감사를 활성화하는 방법은 사용하는 데이터베이스 관리 시스템(DBMS)에 따라 다릅니다.

*   **DBMS 제공 감사 기능 활용:**
    대부분의 상용 DBMS와 일부 오픈소스 DBMS는 강력한 내장 감사 기능을 제공합니다. 예를 들어, MySQL은 Enterprise 버전에서 Audit Plugin을 제공하며, MariaDB나 Percona Server 같은 오픈소스 배포판에서도 자체 감사 플러그인을 사용할 수 있습니다. 이러한 플러그인을 활성화하면 어떤 사용자의 어떤 활동을 기록할지 세밀하게 정책을 설정할 수 있습니다.

    *   **설정 예시 (개념):**
        DBMS 설정 파일에서 감사 플러그인을 활성화하고, 감사할 이벤트의 종류(예: `CONNECT`(접속), `QUERY`(쿼리), `TABLE`(테이블 접근)), 로그 형식(JSON, XML 등), 로그 파일 경로 등을 지정합니다.

*   **트리거(Trigger)를 이용한 수동 감사:**
    DBMS가 제공하는 감사 기능이 부족하거나, 특정 테이블의 특정 컬럼 변경과 같이 매우 세밀한 감사가 필요할 때 DML 트리거를 활용할 수 있습니다.

    *   **상황:** `employees` 테이블의 `salary` 컬럼이 변경될 때마다, 누가, 언제, 얼마에서 얼마로 변경했는지 기록해야 합니다.

    *   **구현 예제:**
        1.  **감사 기록을 저장할 테이블 생성:**
            ```sql
            CREATE TABLE salary_audit (
                audit_id INT AUTO_INCREMENT PRIMARY KEY,
                employee_id INT,
                old_salary DECIMAL(10, 2),
                new_salary DECIMAL(10, 2),
                changed_by VARCHAR(255),
                changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
            );
            ```
        2.  **`employees` 테이블에 `AFTER UPDATE` 트리거 생성:**
            ```sql
            DELIMITER //
            CREATE TRIGGER trg_salary_audit
            AFTER UPDATE ON employees
            FOR EACH ROW
            BEGIN
                -- salary 컬럼이 실제로 변경되었을 경우에만 기록
                IF OLD.salary <> NEW.salary THEN
                    INSERT INTO salary_audit (employee_id, old_salary, new_salary, changed_by)
                    VALUES (OLD.employee_id, OLD.salary, NEW.salary, USER());
                END IF;
            END //
            DELIMITER ;
            ```
    *   **장단점:** 이 방식은 매우 유연하고 원하는 정보만 정확히 기록할 수 있다는 장점이 있지만, 모든 테이블에 개별적으로 구현해야 하고, 트리거 자체가 데이터베이스 성능에 부하를 줄 수 있다는 단점이 있습니다.

*   **로그 분석 및 관리:**
    감사 로그는 생성하는 것만큼이나 분석하고 관리하는 것이 중요합니다.

    1.  **중앙 집중식 로깅:** 여러 데이터베이스 서버의 감사 로그를 ELK 스택(Elasticsearch, Logstash, Kibana)이나 Splunk 같은 중앙 로그 관리 시스템으로 전송하여 통합 관리하고 분석하는 것이 효율적입니다.
    2.  **정기적인 검토 및 알림:** 감사 로그를 정기적으로 검토하는 프로세스를 수립해야 합니다. 또한, '관리자 권한 부여', '반복적인 로그인 실패' 등 심각한 보안 이벤트에 대해서는 실시간으로 보안 담당자에게 알림이 가도록 시스템을 구성해야 합니다.
    3.  **로그 보관 및 보호:** 감사 로그 자체도 매우 민감한 정보이므로, 비인가된 접근이나 변조로부터 안전하게 보호해야 합니다. 또한, 법적 또는 규제 요구사항에 따라 정해진 기간 동안 안전하게 보관해야 합니다.
