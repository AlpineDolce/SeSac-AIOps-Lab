## 1. 대량 데이터 처리 최적화 (심화)

데이터 파이프라인, 특히 ETL(Extract, Transform, Load) 과정에서 'L(Load)' 단계의 성능은 전체 파이프라인의 효율성을 좌우하는 핵심 요소입니다. 수십만, 수백만 건의 데이터를 데이터베이스에 적재할 때, 순진한(naive) 방식으로 로우(row)마다 `INSERT` 쿼리를 실행하는 것은 네트워크 왕복 비용과 데이터베이스의 트랜잭션 오버헤드로 인해 실용적이지 않습니다.

이 섹션에서는 대량 데이터를 효율적으로 처리하기 위한 다양한 기법을 내부 동작 원리와 함께 심도 있게 비교 분석합니다.

### 1.1. 대량 삽입(Bulk Insert) 전략 비교

대량 삽입의 핵심 목표는 **네트워크 왕복 횟수를 최소화**하고, **데이터베이스가 한 번에 많은 양의 작업을 처리**하도록 하는 것입니다.

| 전략 | 추상화 수준 | 내부 동작 원리 | 장점 | 단점 | 추천 시나리오 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`cursor.executemany()`** | 낮음 (DB-API) | 드라이버가 여러 파라미터 셋을 DB로 보내 반복 실행. `REWRITE` 옵션에 따라 단일 쿼리로 묶일 수 있음. | 간단하고 표준적. 대부분의 DB-API 드라이버에서 지원. | 드라이버 구현에 따라 성능 편차가 큼. ORM의 편의 기능 없음. | 간단한 스크립트에서 빠르게 대량의 데이터를 삽입할 때. |
| **`INSERT ... VALUES (), (), ...`** | 낮음 (SQL) | 단일 `INSERT` 문에 여러 `VALUES` 절을 포함하여 하나의 큰 쿼리로 전송. | DB에 최적화된 구문으로 매우 빠름. 네트워크 왕복 1회. | SQL 문자열을 직접 조립해야 하므로 번거롭고 SQL Injection 위험. | 성능이 극도로 중요하고, SQL을 안전하게 생성할 수 있을 때. |
| **`session.bulk_insert_mappings()`** | 중간 (ORM) | ORM 객체 생성 없이, 딕셔너리 리스트를 `INSERT` 문으로 직접 변환. `executemany`와 유사하게 동작. | ORM의 편의성(연결 관리 등)을 일부 활용하면서도 성능이 좋음. | ORM 객체 생명주기(Lifecycle) 이벤트를 건너뜀. 관계 자동 동기화 안됨. | ETL 작업처럼 대량의 정제된 데이터를 ORM 환경 내에서 적재할 때. |
| **`LOAD DATA INFILE`** | 낮음 (DB 특화) | DB 서버가 직접 파일을 읽어 테이블에 적재. 네트워크를 거의 타지 않음. | **가장 빠름.** 대용량 파일(CSV, TSV) 적재에 압도적인 성능. | MySQL/MariaDB 등 특정 DB에서만 지원. 보안 설정(권한)이 필요함. | 수백만 건 이상의 파일 데이터를 DB로 마이그레이션하는 배치 작업. |

#### 1.1.1. `cursor.executemany()` 심층 분석

`pymysql`과 같은 드라이버에서 `executemany`는 여러 개의 `INSERT` 문을 서버로 보내는 것처럼 동작할 수 있지만, 실제로는 파라미터만 여러 번 보내고 쿼리는 한 번만 전송하여 효율을 높입니다.

```python
# executemany 예시
import pymysql
# ... connection 설정 ...
try:
    with conn.cursor() as cursor:
        data_to_insert = [
            ('David', 'Kim', '2024-06-01', 'DEV', 70000.00, 1),
            ('Eve', 'Park', '2024-06-05', 'HR', 58000.00, 2),
        ]
        # 쿼리 템플릿은 한 번만 전송되고, 데이터 묶음이 서버로 전달됨
        insert_sql = "INSERT INTO employees (first_name, last_name, hire_date, job_id, salary, department_id) VALUES (%s, %s, %s, %s, %s, %s)"
        cursor.executemany(insert_sql, data_to_insert)
        conn.commit()
        print(f"Inserted {cursor.rowcount} rows using executemany.")
finally:
    conn.close()
```

#### 1.1.2. SQLAlchemy `bulk_insert_mappings`의 역할

이 메서드는 ORM의 편리함과 벌크 작업의 성능 사이에서 훌륭한 균형을 제공합니다. ORM 객체를 하나하나 만들고 `session.add()`하는 것과 달리, 객체 상태 추적에 드는 CPU와 메모리 오버헤드가 없습니다.

```python
# bulk_insert_mappings 예시
from sqlalchemy.orm import sessionmaker
# ... engine, Employee 모델 설정 ...
SessionLocal = sessionmaker(bind=engine)
session = SessionLocal()
try:
    data_dicts = [
        {'first_name': 'Ivan', 'last_name': 'Petrov', ...},
        {'first_name': 'Julia', 'last_name': 'Sidorova', ...},
    ]
    # 이 시점에는 ORM 객체가 생성되지 않음
    session.bulk_insert_mappings(Employee, data_dicts)
    session.commit() # commit 시점에 최적화된 INSERT 실행
    print("Inserted rows using bulk_insert_mappings.")
finally:
    session.close()
```

### 1.2. 대량 업데이트 및 삭제 전략

대량 업데이트/삭제 역시 **`WHERE` 절을 활용하여 단일 쿼리로 여러 로우를 처리**하는 것이 핵심입니다.

#### 1.2.1. `UPDATE ... WHERE IN (...)`

가장 표준적인 방법입니다. 업데이트할 로우의 ID 목록을 `WHERE IN` 절에 넘겨 한 번에 처리합니다.

```python
# id_list = [1, 5, 10, 25]
# update_sql = "UPDATE employees SET salary = salary * 1.1 WHERE employee_id IN %s"
# cursor.execute(update_sql, (id_list,))
```

#### 1.2.2. SQLAlchemy `bulk_update_mappings`

`bulk_insert_mappings`와 유사하게, 딕셔너리 리스트를 받아 대량 업데이트를 수행합니다. 각 딕셔너리는 **반드시 업데이트할 로우를 식별할 기본 키(PK) 값을 포함**해야 합니다.

```python
# bulk_update_mappings 예시
session = SessionLocal()
try:
    updates = [
        # 각 딕셔너리는 반드시 PK(employee_id)를 포함해야 함
        {'employee_id': 1, 'salary': 95000.00},
        {'employee_id': 2, 'salary': 62000.00},
    ]
    session.bulk_update_mappings(Employee, updates)
    session.commit()
    print("Updated rows using bulk_update_mappings.")
finally:
    session.close()
```

#### 1.2.3. 실무적 고려사항: 교착 상태(Deadlock)와 잠금(Locking)

대량 업데이트/삭제 작업은 테이블의 많은 로우에 대한 잠금을 유발할 수 있습니다. 만약 동시에 다른 트랜잭션이 이 로우들에 접근하려고 하면, **교착 상태(Deadlock)** 가 발생하여 양쪽 트랜잭션이 모두 실패할 수 있습니다.

-   **해결 전략**:
    1.  **작업 순서 정하기**: 모든 트랜잭션이 테이블에 접근하는 순서를 동일하게 맞추면 교착 상태를 줄일 수 있습니다. (예: 항상 `departments` 테이블을 먼저 수정하고 `employees` 테이블을 수정)
    2.  **배치(Batch) 처리**: 전체 작업을 더 작은 배치 단위로 나누어 커밋을 자주 실행합니다. 이는 한 번에 잠그는 로우의 수를 줄여 다른 트랜잭션이 끼어들 여지를 줍니다.
    3.  **서비스 이용량이 적은 시간대 실행**: 다른 사용자와의 경합을 최소화할 수 있는 시간에 배치 작업을 실행합니다.
    4.  **적절한 격리 수준(Isolation Level) 사용**: 필요에 따라 데이터베이스의 트랜잭션 격리 수준을 조정하여 동시성을 제어할 수 있지만, 이는 매우 신중하게 접근해야 합니다.

## 2. 파이썬-SQL 연동 도구 선택 가이드 (심화)

파이썬으로 데이터베이스와 상호작용할 때, 어떤 도구를 선택하느냐는 프로젝트의 생산성, 유지보수성, 그리고 성능에 지대한 영향을 미칩니다. 선택지는 크게 **저수준 DB-API 드라이버**와 **고수준 SQLAlchemy 라이브러리**로 나뉩니다. 특히 SQLAlchemy는 그 자체로 **Core(SQL 표현 언어)**와 **ORM(객체 관계 매핑)**이라는 두 가지 접근 방식을 제공하여, 상황에 맞는 최적의 도구를 선택할 수 있는 유연성을 제공합니다.

### 2.1. 접근 방식에 따른 철학 비교

-   **DB-API (`pymysql`, `psycopg2`)**: **"SQL이 왕이다."**
    -   **철학**: 개발자가 SQL을 완벽하게 제어해야 한다는 철학입니다. 라이브러리는 데이터베이스와의 통신 채널을 열어주고 SQL 실행 결과를 파이썬 데이터 타입으로 변환해주는 최소한의 역할만 수행합니다.
    -   **장점**: 군더더기 없는(zero-overhead) 성능, 데이터베이스 고유의 비표준 SQL 기능까지 모두 활용 가능.
    -   **단점**: 모든 SQL을 문자열로 직접 작성해야 하므로 오타에 취약하고, SQL Injection에 대한 방어를 수동으로 관리해야 하며, 코드 재사용성이 떨어집니다.

-   **SQLAlchemy Core**: **"SQL을 파이썬으로 조립한다."**
    -   **철학**: SQL의 강력함과 구조를 유지하면서, 파이썬의 프로그래밍 능력(조건문, 반복문, 함수)을 활용하여 SQL을 동적으로, 그리고 안전하게 생성하자는 철학입니다.
    -   **장점**: SQL Injection으로부터 안전하며, 쿼리를 프로그래밍 방식으로 조립할 수 있어 재사용성과 가독성이 높습니다. 복잡한 분석 쿼리 작성에 매우 강력합니다.
    -   **단점**: ORM만큼의 완전한 추상화는 제공하지 않으므로, 여전히 테이블과 컬럼 구조에 대해 명확히 알고 있어야 합니다.

-   **SQLAlchemy ORM**: **"데이터베이스를 객체처럼 다룬다."**
    -   **철학**: 데이터베이스의 테이블 구조를 파이썬 클래스로 추상화하여, 개발자가 SQL을 전혀 몰라도 객체 조작만으로 데이터 작업을 할 수 있게 하자는 철학입니다.
    -   **장점**: 최고의 생산성과 유지보수성. 비즈니스 로직에만 집중할 수 있게 해줍니다.
    -   **단점**: 추상화로 인한 약간의 성능 오버헤드가 있으며, ORM의 내부 동작(특히 로딩 전략)을 이해하지 못하면 N+1 문제와 같은 성능 병목을 유발하기 쉽습니다.

### 2.2. 시나리오별 코드 비교: "부서별 평균 연봉 계산"

**요구사항**: Engineering 부서 직원들의 평균 연봉을 계산하는 쿼리를 작성합니다.

<details>
<summary><b>1. DB-API (`pymysql`) 방식</b></summary>

```python
# SQL 문자열을 직접 작성하고 파라미터를 전달
sql = """
    SELECT AVG(e.salary)
    FROM employees e
    JOIN departments d ON e.department_id = d.department_id
    WHERE d.name = %s
"""
cursor.execute(sql, ('Engineering',))
avg_salary = cursor.fetchone()[0]
print(f"Engineering 부서 평균 연봉 (pymysql): {avg_salary}")
```
- **특징**: 직관적이지만, SQL이 문자열이라 오타 검증이 어렵고 다른 부분에서 재사용하기 힘듭니다.
</details>

<details>
<summary><b>2. SQLAlchemy Core 방식</b></summary>

```python
from sqlalchemy import select, func, table, column

# 테이블 객체를 정의하거나, 기존 MetaData에서 가져옴
employees = table('employees', column('salary'), column('department_id'))
departments = table('departments', column('department_id'), column('name'))

# 파이썬 코드로 SQL 쿼리를 조립
query = select(func.avg(employees.c.salary)).select_from(
    employees.join(departments, employees.c.department_id == departments.c.department_id)
).where(departments.c.name == 'Engineering')

# `engine.connect()`를 통해 실행
with engine.connect() as connection:
    avg_salary = connection.execute(query).scalar_one()
    print(f"Engineering 부서 평균 연봉 (Core): {avg_salary}")
```
- **특징**: SQL의 구조(SELECT, JOIN, WHERE)가 파이썬 함수로 명확하게 표현됩니다. `query` 객체를 다른 함수에 전달하거나 일부를 수정하여 재사용하기 용이합니다.
</details>

<details>
<summary><b>3. SQLAlchemy ORM 방식</b></summary>

```python
from sqlalchemy import func
# Employee, Department 모델이 미리 정의되어 있다고 가정
from models import Employee, Department

# ORM 객체를 사용하여 쿼리
query = session.query(func.avg(Employee.salary)).join(Department).filter(Department.name == 'Engineering')

avg_salary = query.scalar()
print(f"Engineering 부서 평균 연봉 (ORM): {avg_salary}")
```
- **특징**: 가장 간결합니다. `Employee.salary`, `Department.name` 등 실제 DB 컬럼명이 아닌 파이썬 클래스 속성명을 사용하여 작업하므로 코드의 추상화 수준이 매우 높습니다.
</details>

### 2.3. 최종 선택 가이드: 당신의 역할은 무엇인가?

| 역할 / 작업 유형 | 추천 도구 | 이유 |
| :--- | :--- | :--- |
| **웹/애플리케이션 개발자** | **SQLAlchemy ORM** (주력) + **Core** (보조) | 대부분의 CRUD 작업은 ORM으로 생산성을 극대화하고, 복잡한 리포트나 통계 기능은 Core를 사용하여 유연하게 쿼리를 작성하는 하이브리드 방식이 가장 효과적입니다. |
| **데이터 분석가 / 과학자** | **SQLAlchemy Core** (주력) + **Pandas `read_sql`** | 탐색적 데이터 분석(EDA)이나 피처 엔지니어링을 위해 복잡하고 비정형적인 쿼리를 동적으로 생성해야 하는 경우가 많습니다. Core는 SQL의 모든 기능을 파이썬으로 제어할 수 있게 해주므로 가장 적합합니다. |
| **데이터 엔지니어** | **SQLAlchemy Core** + **DB-API** | 대규모 ETL/ELT 파이프라인 구축 시, 스키마 조작이나 데이터 변환 로직은 Core로 명확하게 표현하고, `COPY`나 `LOAD DATA` 같은 DB 특화 고성능 적재 명령은 DB-API를 통해 직접 실행하는 것이 효율적입니다. |
| **간단한 자동화 스크립트** | **DB-API (`pymysql`)** | 외부 라이브러리 의존성을 최소화하고, 몇 개의 간단한 쿼리만 실행하면 되는 경우 가장 가볍고 빠른 선택입니다. |

**결론**: "어떤 도구가 최고인가?"라는 질문은 의미가 없습니다. "지금 해결하려는 문제에 가장 적합한 추상화 수준은 무엇인가?"를 기준으로 도구를 선택하는 것이 현명합니다. SQLAlchemy는 이 모든 스펙트럼을 지원하므로, 프로젝트의 특정 요구사항에 맞춰 ORM과 Core를 유연하게 넘나들며 사용하는 능력이 뛰어난 개발자의 핵심 역량 중 하나입니다.

## 3. 데이터 파이프라인 자동화 (프로덕션 레벨)

단순히 스크립트를 작성하는 것을 넘어, 데이터 파이프라인을 '자동화'한다는 것은 **사람의 개입 없이도 스스로 안정적으로 실행되고, 문제가 발생했을 때 이를 명확히 인지하고 대응할 수 있는 시스템**을 구축하는 것을 의미합니다. 이 섹션에서는 견고한 자동화 파이프라인을 구축하기 위한 핵심 원칙과 실용적인 구현 방법을 다룹니다.

### 3.1. 프로덕션 레벨 ETL 스크립트 설계

견고한 ETL 스크립트는 다음과 같은 특징을 가져야 합니다.

1.  **모듈성(Modularity)**: 각 단계(Extract, Transform, Load)가 명확히 분리되어야 테스트와 디버깅이 용이합니다.
2.  **설정 관리(Configuration Management)**: DB 접속 정보, API 키, 파일 경로 등 환경에 따라 변하는 값들을 코드에서 분리해야 합니다. (`.env` 파일과 `python-dotenv` 활용)
3.  **로깅(Logging)**: "언제 시작했고, 몇 건을 처리했으며, 어디서 실패했는지" 등 모든 실행 과정을 추적할 수 있는 상세한 로그를 남겨야 합니다.
4.  **에러 핸들링 및 재시도(Error Handling & Retry)**: 일시적인 네트워크 문제나 DB 오류에 대응할 수 있는 재시도 로직이 포함되어야 합니다.
5.  **멱등성(Idempotency)**: 스크립트가 여러 번 실행되어도 결과가 항상 동일하게 유지되어야 합니다. 이는 파이프라인 실패 후 재실행 시 데이터 중복이나 누락을 방지하는 핵심 원칙입니다.

#### 3.1.1. 멱등성 확보 전략 (심화)

-   **전체 재적재 (Full Refresh)**: 가장 간단한 방법. `Load` 단계 시작 시 대상 테이블을 `TRUNCATE` (또는 `DELETE FROM`) 한 후, 모든 데이터를 새로 삽입합니다. 데이터 양이 적고 계산 비용이 낮을 때 효과적입니다.
-   **증분 적재 (Incremental Loading)**: 마지막으로 처리한 시점 이후의 변경분만 가져와 처리합니다. 원본 데이터에 `updated_at` 같은 타임스탬프 컬럼이 필요합니다.
-   **Upsert (INSERT ... ON DUPLICATE KEY UPDATE)**: 대상 테이블에 데이터가 없으면 `INSERT`, 기본 키(PK)가 중복되면 `UPDATE`를 수행합니다. 데이터의 최신 상태를 유지하는 데 매우 효과적입니다. SQLAlchemy에서는 `sqlalchemy.dialects.mysql.insert` 등을 통해 구현할 수 있습니다.

#### 3.1.2. 견고한 ETL 스크립트 예시

```python
# robust_etl.py
import logging
import os
import sys
import time
import pandas as pd
from sqlalchemy import create_engine, text
from sqlalchemy.exc import OperationalError
from dotenv import load_dotenv

# --- 1. 설정 관리 ---
# 스크립트의 루트 경로를 기준으로 .env 파일 로드
BASE_DIR = os.path.dirname(os.path.abspath(__file__))
load_dotenv(os.path.join(BASE_DIR, '.env'))

DB_URL = f"mysql+pymysql://{os.getenv('DB_USER')}:{os.getenv('DB_PASSWORD')}@{os.getenv('DB_HOST')}/{os.getenv('DB_NAME')}"
SOURCE_TABLE = "raw_sales"
TARGET_TABLE = "daily_sales_summary"
MAX_RETRIES = 3
RETRY_DELAY = 5  # seconds

# --- 2. 로깅 설정 ---
logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s - %(levelname)s - [ETL_PIPELINE] - %(message)s',
    stream=sys.stdout, # 실제 환경에서는 파일 핸들러 사용
)

def extract(engine) -> pd.DataFrame:
    """데이터 소스에서 데이터를 추출합니다."""
    logging.info(f"Extracting data from '{SOURCE_TABLE}'...")
    query = f"SELECT product_id, sale_date, amount FROM {SOURCE_TABLE};"
    df = pd.read_sql(query, engine)
    logging.info(f"Extracted {len(df)} rows.")
    return df

def transform(df: pd.DataFrame) -> pd.DataFrame:
    """데이터를 비즈니스 요구사항에 맞게 변환합니다."""
    if df.empty:
        logging.warning("No data to transform.")
        return df
    logging.info("Transforming data...")
    df['sale_date'] = pd.to_datetime(df['sale_date']).dt.date
    # 일별, 상품별 매출 집계
    df_summary = df.groupby(['sale_date', 'product_id'])['amount'].sum().reset_index()
    df_summary.rename(columns={'amount': 'total_amount'}, inplace=True)
    logging.info(f"Transformed data into {len(df_summary)} summary rows.")
    return df_summary

def load(df: pd.DataFrame, engine):
    """변환된 데이터를 타겟 테이블에 적재합니다 (멱등성 보장)."""
    if df.empty:
        logging.warning("No data to load.")
        return

    logging.info(f"Loading data into '{TARGET_TABLE}'...")
    # 멱등성 확보: Staging 테이블과 원자적 교체(Atomic Swap) 전략
    # 1. 임시 테이블에 데이터 전체 쓰기
    temp_table = f"{TARGET_TABLE}_temp"
    df.to_sql(temp_table, engine, if_exists='replace', index=False)

    # 2. 트랜잭션 내에서 기존 테이블 삭제 및 임시 테이블 이름 변경
    with engine.begin() as connection:
        logging.info("Performing atomic swap of tables...")
        connection.execute(text(f"DROP TABLE IF EXISTS {TARGET_TABLE};"))
        connection.execute(text(f"ALTER TABLE {temp_table} RENAME TO {TARGET_TABLE};"))
    logging.info(f"Successfully loaded {len(df)} rows into '{TARGET_TABLE}'.")

def main():
    """ETL 파이프라인의 메인 실행 함수."""
    logging.info("Starting ETL pipeline run...")
    engine = None
    for attempt in range(MAX_RETRIES):
        try:
            engine = create_engine(DB_URL)
            
            # ETL 실행
            raw_df = extract(engine)
            transformed_df = transform(raw_df)
            load(transformed_df, engine)
            
            logging.info("ETL pipeline run completed successfully.")
            return # 성공 시 함수 종료
            
        except OperationalError as e:
            logging.warning(f"Attempt {attempt + 1} failed due to a database connection error: {e}")
            if attempt + 1 == MAX_RETRIES:
                logging.error("Max retries reached. ETL pipeline failed.")
                # send_alert("ETL Pipeline Failed: Cannot connect to DB")
                raise
            time.sleep(RETRY_DELAY * (2 ** attempt)) # Exponential backoff
        except Exception as e:
            logging.error(f"An unexpected error occurred: {e}", exc_info=True)
            # send_alert(f"ETL Pipeline Failed: {e}")
            raise
        finally:
            if engine:
                engine.dispose()

if __name__ == "__main__":
    main()
```

### 3.2. 스케줄러를 넘어 워크플로우 관리로

간단한 스크립트는 Cron이나 Windows Task Scheduler로 충분하지만, 파이프라인이 복잡해지면 한계에 부딪힙니다.
-   **의존성 관리**: "Task A가 성공해야 Task B를 실행"과 같은 작업 간 의존성을 표현하기 어렵습니다.
-   **재시도 및 에러 핸들링**: 스케줄러 자체는 실패한 작업을 자동으로 재시도하거나, 실패 시 알림을 보내는 기능이 제한적입니다.
-   **모니터링 및 로깅**: 여러 작업의 실행 상태와 로그를 중앙에서 확인하기 어렵습니다.

이러한 문제를 해결하는 것이 **워크플로우 관리 시스템(Workflow Management System)** 이며, 가장 대표적인 도구가 **Apache Airflow**입니다.

#### 3.2.1. 왜 Airflow를 사용하는가?

Airflow는 데이터 파이프라인을 **DAG(Directed Acyclic Graph, 방향성 비순환 그래프)** 라는 코드로 정의합니다. 이를 통해 다음과 같은 장점을 얻습니다.

-   **시각화**: 파이프라인의 구조와 실행 상태를 웹 UI에서 한눈에 파악할 수 있습니다.
-   **강력한 스케줄링**: 단순한 시간 기반 스케줄링을 넘어, 외부 이벤트나 다른 DAG의 성공을 트리거로 작업을 시작할 수 있습니다.
-   **중앙화된 관리**: 모든 파이프라인의 로그, 실행 이력, 설정 등을 중앙에서 관리합니다.
-   **확장성**: 수많은 외부 시스템(AWS, GCP, Spark, Kubernetes 등)과의 연동을 위한 오퍼레이터(Operator)를 제공합니다.

#### 3.2.2. 간단한 Airflow DAG 예시

위의 `robust_etl.py` 스크립트를 Airflow에서 실행하는 DAG 예시입니다.

```python
# dags/my_etl_dag.py
from __future__ import annotations

import pendulum
from airflow.models.dag import DAG
from airflow.operators.bash import BashOperator

with DAG(
    dag_id="daily_sales_etl_pipeline",
    schedule="0 1 * * *",  # 매일 새벽 1시에 실행
    start_date=pendulum.datetime(2023, 1, 1, tz="Asia/Seoul"),
    catchup=False, # 시작일 이후 실행되지 않은 DAG는 실행하지 않음
    tags=["etl", "sales"],
) as dag:
    run_etl_task = BashOperator(
        task_id="run_robust_etl_script",
        # 가상환경의 파이썬을 명시적으로 지정하여 실행
        bash_command="/path/to/your/venv/bin/python /path/to/your/project/robust_etl.py",
    )
```
이처럼 Airflow를 사용하면, 스크립트 자체는 데이터 처리 로직에만 집중하고, 실행 스케줄, 재시도, 알림 등 **운영에 관한 모든 책임은 Airflow에 위임**할 수 있습니다. 이것이 바로 현대적인 데이터 파이프라인 자동화의 핵심 패러다임입니다.
