## 1. 크롤러에 생명 불어넣기

지금까지 우리는 크롤러를 개발하고, 도커를 이용해 어떤 환경에서든 실행할 수 있도록 포장했습니다. 하지만 여전히 누군가가 서버에 접속해서 `docker run ...` 명령을 직접 실행해야만 크롤러가 동작합니다.

**스케줄링(Scheduling)**은 이 마지막 수동 단계를 자동화하여, 정해진 시간(e.g., 매일 새벽 3시, 매주 월요일 오전 9시)에 크롤러가 스스로 실행되도록 만드는 과정입니다. 스케줄링을 통해 비로소 우리의 크롤러는 사람의 개입 없이도 데이터를 꾸준히 쌓아나가는 **완전한 자동화 시스템**이 됩니다.

## 2. 전통의 강자: `cron`

`cron`은 Linux나 macOS 같은 Unix 계열 운영체제에 기본적으로 내장된 매우 간단하고 강력한 작업 스케줄러입니다. `crontab`이라는 설정 파일에 "언제, 어떤 명령을 실행할지"를 적어두면, `cron` 데몬이 시간에 맞춰 해당 명령을 실행해줍니다.

**`crontab` 문법:**
```
# ┌───────────── 분 (0 - 59)
# │ ┌───────────── 시 (0 - 23)
# │ │ ┌───────────── 일 (1 - 31)
# │ │ │ ┌───────────── 월 (1 - 12)
# │ │ │ │ ┌───────────── 요일 (0 - 6) (0: 일요일, 6: 토요일)
# │ │ │ │ │
# * * * * * [실행할 명령어]
```

**예시:**
- `0 3 * * * /path/to/command` : 매일 새벽 3시 0분에 실행
- `*/15 * * * * /path/to/command` : 매 15분마다 실행
- `0 9 * * 1-5 /path/to/command` : 매주 월요일부터 금요일(평일) 오전 9시 0분에 실행

**Docker 컨테이너 스케줄링:**
`crontab -e` 명령으로 편집기를 열고, 다음과 같이 `docker run` 명령을 등록할 수 있습니다.
```crontab
# 매일 새벽 2시에 mycrawler-image 컨테이너를 실행하고, 결과를 로그 파일에 기록
# && 앞의 cd 명령으로 프로젝트 디렉토리로 이동하는 것이 중요합니다.
0 2 * * * cd /home/user/mycrawler && docker run --rm -v $(pwd)/data:/app/data mycrawler-image:latest >> /home/user/mycrawler/logs/cron.log 2>&1
```
- `>> cron.log 2>&1` : 명령어의 실행 결과(표준 출력)와 에러(표준 에러)를 모두 로그 파일에 추가(append)하라는 의미입니다. 스케줄링된 작업의 성공/실패 여부를 추적하기 위해 **로그 기록은 필수**입니다.

**장점:** 간단하고, 가볍고, 별도의 설치가 필요 없습니다.
**단점:** 실패 시 자동 재시도, 작업 간 의존성 설정, 중앙 모니터링 등 고급 기능이 없습니다.

## 3. 데이터 엔지니어링의 표준: Apache Airflow

Airflow는 `cron`과 같은 단순한 스케줄러를 넘어, 복잡한 **데이터 워크플로우(Workflow)를 만들고, 스케줄링하고, 모니터링하는 플랫폼**입니다. Airflow에서는 파이썬 코드로 워크플로우를 **DAG(Directed Acyclic Graph, 방향성 비순환 그래프)**라는 형태로 정의합니다.

**왜 Airflow를 사용하는가?**
- **의존성 관리:** A 작업이 성공해야만 B 작업을 실행하도록 설정할 수 있습니다. (e.g., `크롤링` → `데이터_전처리` → `모델_학습`)
- **재시도 및 알림:** 작업 실패 시 자동으로 몇 번 더 재시도하고, 계속 실패하면 슬랙이나 이메일로 알림을 보낼 수 있습니다.
- **강력한 UI:** 웹 대시보드를 통해 모든 워크플로우의 실행 상태, 로그, 성공/실패 여부를 한눈에 파악하고 관리할 수 있습니다.
- **확장성:** 수천 개의 복잡한 워크플로우도 관리할 수 있습니다.

**Scrapy 크롤러를 위한 간단한 Airflow DAG 예시:**
```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

with DAG(
    dag_id='daily_scrapy_crawler',
    start_date=datetime(2023, 8, 17),
    schedule_interval='@daily',  # 매일 자정에 실행 (cron 표현식 '0 0 * * *'도 가능)
    catchup=False,
) as dag:
    
    crawl_task = BashOperator(
        task_id='run_scrapy_docker',
        # cron에서 사용했던 것과 동일한 쉘 명령을 실행
        bash_command="""
        cd /home/user/mycrawler
        docker run --rm -v $(pwd)/data:/app/data mycrawler-image:latest
        """
    )
```

## 4. `cron` vs. Airflow: 언제 무엇을 쓸까?

| 구분 | `cron` | `Airflow` |
| --- | --- | --- |
| **적합한 작업** | 단일 독립 작업, 간단한 스크립트 | 여러 단계의 의존성을 가진 복잡한 파이프라인 |
| **모니터링** | 로그 파일을 직접 확인해야 함 | 강력한 웹 UI 대시보드 제공 |
| **에러 처리** | 직접 구현해야 함 | 자동 재시도, 실패 알림 등 내장 기능 풍부 |
| **설정 난이도** | 매우 쉬움 | Docker, DB 등 관련 지식이 필요하여 복잡함 |

**결론:** **간단한 크롤러 하나를 주기적으로 실행**하는 것이 목표라면 **`cron`**으로 충분합니다. 하지만 **여러 데이터 소스를 처리하고, 전처리, 분석까지 이어지는 파이프라인을 구축**하고 싶다면 **Airflow**가 정답입니다.

---

**핵심 요약:** 스케줄링은 크롤러를 자동화 시스템으로 만드는 마지막 단계입니다. **간단한 작업은 `cron`**으로 시작하되, **안정적이고 복잡한 데이터 파이프라인을 위해서는 Airflow와 같은 워크플로우 관리 도구**의 도입을 고려해야 합니다.
