## 1. 아키텍처란 무엇이며 왜 중요한가?

웹 크롤링 아키텍처는 데이터 수집 시스템의 '설계도'입니다. 어떤 부품(컴포넌트)을 사용하고, 각 부품이 어떤 순서로 상호작용할지 정의합니다. 프로젝트의 규모와 복잡도에 맞는 올바른 아키텍처를 초기에 선택하는 것은 매우 중요합니다. 좋은 설계는 확장성, 유지보수성, 안정성을 보장하지만, 잘못된 설계는 프로젝트가 복잡해질수록 큰 기술 부채를 남깁니다.

## 2. 기본 파이프라인 아키텍처

가장 직관적이고 간단한 순차적 처리 구조입니다.

**흐름:**
`URL 목록` → `[요청]` → `HTML 응답` → `[파싱]` → `추출된 데이터` → `[저장]`

- **요청 (Request):** `requests` 라이브러리를 사용해 URL에 HTTP 요청을 보냅니다.
- **파싱 (Parse):** `BeautifulSoup`으로 응답받은 HTML을 파싱 가능한 객체로 변환하고, 원하는 데이터를 추출합니다.
- **저장 (Store):** 추출된 데이터를 CSV, JSON, 간단한 DB 등의 형태로 저장합니다.

**장점:**
- 구조가 단순하고 이해하기 쉽습니다.
- 몇 개 안 되는 페이지를 일회성으로 수집하는 작업에 적합하며, 구현이 빠릅니다.

**단점:**
- **확장성 한계:** URL이 많아지면 처리 속도가 느리고, 중간에 오류 발생 시 전체 프로세스가 중단될 수 있습니다.
- **유지보수 어려움:** 로직이 복잡해질수록 하나의 파일에 모든 코드가 섞여(스파게티 코드) 수정이 어려워집니다.

**개념적 예시:**
```python
import requests
from bs4 import BeautifulSoup
import csv

urls = ["http://example.com/page1", "http://example.com/page2"]
results = []

for url in urls:
    response = requests.get(url) # 요청
    soup = BeautifulSoup(response.text, 'html.parser') # 파싱
    title = soup.find('h1').text
    results.append({'title': title})

# 저장
with open('output.csv', 'w', newline='', encoding='utf-8') as f:
    writer = csv.DictWriter(f, fieldnames=['title'])
    writer.writeheader()
    writer.writerows(results)
```

## 3. Scrapy 프레임워크 아키텍처

Scrapy는 크롤링 시스템을 위한 전문적인 '프레임워크'입니다. 즉, 잘 설계된 구조와 규칙을 미리 제공하여 개발자가 비즈니스 로직(데이터 추출)에만 집중할 수 있도록 돕습니다.

**주요 컴포넌트 및 흐름:**
- **Engine:** 전체 데이터 흐름을 제어하는 핵심 엔진
- **Scheduler:** 크롤링할 URL들을 관리하고 Engine에 전달
- **Downloader:** Scheduler로부터 URL을 받아 웹 페이지를 다운로드 (비동기 방식)
- **Spiders:** Downloader가 전달한 페이지를 파싱하고 데이터를 추출(yield)하는 사용자 작성 코드
- **Item Pipelines:** Spider가 추출한 데이터를 받아 정제, 유효성 검사, DB 저장 등 후처리를 담당

**장점:**
- **비동기 처리:** 요청을 보내고 응답을 기다리는 동안 다른 작업을 처리하여 성능이 매우 뛰어납니다.
- **모듈성:** 데이터 추출(Spider)과 데이터 저장(Pipeline) 로직이 명확히 분리되어 유지보수가 용이합니다.
- **확장성:** 대규모 크롤링에 적합하며, Middleware 등을 통해 프록시, User-Agent 변경 등 다양한 기능을 쉽게 추가할 수 있습니다.

**단점:**
- 초기 학습 곡선이 기본 파이프라인보다 가파릅니다.
- 간단한 일회성 작업에는 과하게 느껴질 수 있습니다.

## 4. 어떤 아키텍처를 선택해야 하는가?

| 상황 | 추천 아키텍처 | 이유 |
| --- | --- | --- |
| 특정 웹툰의 오늘 자 한 편만 다운로드 | **기본 파이프라인** | 작업이 단순하고 즉시 결과가 필요하며, 확장의 필요성이 낮음 |
| 뉴스 사이트의 모든 기사를 매일 수집 | **Scrapy 프레임워크** | 대량의 URL을 효율적으로 처리해야 하고, 데이터 후처리 및 저장이 중요하며, 장기적인 운영이 필요함 |
| 쇼핑몰의 상위 10개 상품 정보 수집 | **기본 파이프라인** | 수집 대상이 명확하고 규모가 작아 빠른 구현이 유리함 |
| 특정 키워드로 검색된 모든 블로그 글 수집 | **Scrapy 프레임워크** | 수집 대상이 많고, 각 블로그의 구조가 다를 수 있어 Spider의 분리가 유리하며, 재시도 등 안정성이 중요함 |

**핵심 요약:** 프로젝트의 최종 목표와 규모를 먼저 생각하세요. **작고 빠른 일회성 작업은 기본 파이프라인**으로 충분하지만, **지속적이고 안정적인 대규모 데이터 수집 시스템을 원한다면 Scrapy**가 정답입니다.
