## 1. 모듈 (Module)

**모듈(Module)**은 파이썬 코드를 논리적으로 묶어 놓은 파일입니다. 하나의 `.py` 파일이 하나의 모듈이 됩니다. 모듈을 사용하면 코드를 여러 파일로 분리하여 관리할 수 있으며, 코드의 재사용성을 높이고 이름 공간(namespace) 충돌을 방지할 수 있습니다.

### 1.1 모듈 생성 및 `import`

모듈을 생성하고 다른 파이썬 파일에서 `import` 문을 사용하여 모듈 내의 함수, 변수, 클래스 등을 가져와 사용할 수 있습니다. 파이썬은 모듈을 찾을 때 `sys.path`에 정의된 경로들을 순서대로 탐색합니다.

**예시: `my_module.py` 파일 생성**

```python
# my_module.py

PI = 3.14159

def add(a, b):
    return a + b

def subtract(a, b):
    return a - b

class MyClass:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"Hello from MyClass, {self.name}!"
```

**예시: `main.py`에서 `my_module.py` 사용**

```python
# main.py

# 1. 모듈 전체 임포트
import my_module

print(f"PI 값: {my_module.PI}")
print(f"덧셈 결과: {my_module.add(10, 5)}")
my_obj = my_module.MyClass("Alice")
print(my_obj.greet())

# 2. 특정 요소만 임포트
from my_module import subtract, MyClass

print(f"뺄셈 결과: {subtract(10, 5)}")
my_obj2 = MyClass("Bob")
print(my_obj2.greet())

# 3. 별칭(alias)을 사용하여 임포트
import my_module as mm

print(f"PI 값 (별칭): {mm.PI}")

# 4. 모든 요소 임포트 (권장하지 않음: 이름 충돌 가능성)
from my_module import *
print(f"PI 값 (from *): {PI}")
print(f"덧셈 결과 (from *): {add(20, 10)}")

# 이름 충돌 예시 (from * 사용 시 주의점)
# my_module에 add 함수가 있고, main.py에도 add 함수가 있다면
# from my_module import * 는 main.py의 add 함수를 덮어쓸 수 있습니다.
# def add(a, b):
#     return a + b + 100 # main.py의 add 함수
# print(f"덮어쓰인 덧셈 결과: {add(1, 2)}") # my_module의 add가 호출될 수 있음
```

- **`import` vs `from ... import ...`:**
    - `import module_name`: 모듈 전체를 임포트하며, 사용할 때는 `module_name.function_name`과 같이 모듈 이름을 접두사로 붙여야 합니다. 이름 충돌을 피할 수 있습니다.
    - `from module_name import item1, item2`: 모듈 내의 특정 요소만 임포트하며, 사용할 때는 접두사 없이 `item1`과 같이 직접 사용할 수 있습니다. 코드가 간결해지지만, 이름 충돌 가능성이 있습니다.

### 1.2 `if __name__ == "__main__":`의 의미와 활용

파이썬 스크립트가 직접 실행될 때와 모듈로 임포트될 때를 구분하여 코드를 실행할 수 있도록 하는 관용적인 표현입니다.

- `__name__` 변수는 파이썬 인터프리터가 자동으로 설정하는 특별한 변수입니다.
    - 스크립트가 직접 실행될 때는 `__name__`의 값이 `"__main__"`이 됩니다.
    - 스크립트가 다른 모듈에 의해 임포트될 때는 `__name__`의 값이 해당 모듈의 이름이 됩니다.

**예시: `my_module.py` 수정**

```python
# my_module.py

PI = 3.14159

def add(a, b):
    return a + b

def subtract(a, b):
    return a - b

class MyClass:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"Hello from MyClass, {self.name}!"

# 이 부분이 직접 실행될 때만 동작합니다.
if __name__ == "__main__":
    print("my_module.py가 직접 실행되었습니다.")
    print(f"PI 값: {PI}")
    print(f"10 + 5 = {add(10, 5)}")
    test_obj = MyClass("Tester")
    print(test_obj.greet())
```

**예시: `main.py`에서 `my_module.py` 임포트**

```python
# main.py

import my_module

print("main.py가 실행되었습니다.")
print(f"my_module의 덧셈 함수 사용: {my_module.add(20, 10)}")
# my_module.py의 if __name__ == "__main__": 블록은 실행되지 않습니다.
```

- **활용:** 모듈이 라이브러리처럼 사용될 때는 특정 테스트 코드나 예시 코드가 실행되지 않도록 하고, 모듈 자체를 실행할 때만 해당 코드가 동작하도록 할 때 유용합니다.

## 2. 패키지 (Package)

**패키지(Package)**는 모듈들을 계층적으로 조직화하는 방법입니다. 파이썬의 디렉토리 구조를 사용하여 모듈들을 그룹화하며, 패키지 내에는 다른 서브 패키지나 모듈이 포함될 수 있습니다. 패키지는 일반적인 디렉토리와 달리 `__init__.py` 파일을 포함하여 파이썬에게 해당 디렉토리가 패키지임을 알립니다.

### 2.1 디렉토리 구조를 이용한 코드 관리

예시 디렉토리 구조:

```
my_project/
├── main.py
└── my_package/
    ├── __init__.py
    ├── module_a.py
    └── sub_package/
        ├── __init__.py
        └── module_b.py
```

### 2.2 `__init__.py`의 역할

`__init__.py` 파일은 파이썬에게 해당 디렉토리가 패키지임을 알리는 역할을 합니다. 이 파일은 비어 있을 수도 있고, 패키지가 임포트될 때 초기화 코드를 실행하거나, 패키지 내의 특정 모듈들을 외부로 노출(`__all__` 변수)하는 등의 역할을 할 수 있습니다.

- **패키지 초기화:** 패키지가 임포트될 때 `__init__.py` 내부의 코드가 한 번 실행됩니다.
- **`__all__` 변수:** `from package import *` 문을 사용할 때 임포트될 모듈의 이름을 정의합니다. 이 변수가 없으면 `*` 임포트 시 모든 하위 모듈이 임포트되지 않습니다.

**예시: `my_package/__init__.py`**

```python
# my_package/__init__.py

print("my_package가 초기화되었습니다.")

# 외부로 노출할 모듈 정의
__all__ = ['module_a', 'sub_package'] # __all__에 sub_package도 추가

# 또는 하위 모듈의 특정 함수를 바로 임포트하여 패키지 레벨에서 사용 가능하게 함
from .module_a import add_one

# my_package/sub_package/module_b.py
# from .sub_package.module_b import process_data # __init__.py에서 직접 노출도 가능
```

**예시: `my_package/module_a.py`**

```python
# my_package/module_a.py

def add_one(num):
    return num + 1

def multiply_by_two(num):
    return num * 2
```

**예시: `my_project/main.py`에서 패키지 사용**

```python
# main.py

import my_package.module_a
from my_package import add_one # __init__.py에서 노출했으므로 가능

print(f"모듈을 통한 호출: {my_package.module_a.add_one(5)}")
print(f"패키지 레벨 호출: {add_one(10)}")
```

### 2.3 절대 경로와 상대 경로 임포트

패키지 내에서 모듈을 임포트할 때는 절대 경로 또는 상대 경로를 사용할 수 있습니다.

- **절대 경로 임포트:** 프로젝트의 루트 디렉토리(또는 `sys.path`에 있는 디렉토리)를 기준으로 경로를 지정합니다. 명확하고 혼동이 적습니다.

    ```python
    # my_package/sub_package/module_b.py 에서 module_a.py 임포트
    # from my_package.module_a import multiply_by_two
    ```

- **상대 경로 임포트:** 현재 모듈의 위치를 기준으로 경로를 지정합니다. `.`은 현재 패키지, `..`은 상위 패키지를 의미합니다. 주로 패키지 내부에서 모듈 간의 임포트에 사용됩니다.

    ```python
    # my_package/sub_package/module_b.py 에서 module_a.py 임포트
    from ..module_a import multiply_by_two

    # my_package/sub_package/module_b.py
    def process_data(num):
        return multiply_by_two(num) + 1
    ```

- **권장 사항:** 일반적으로 패키지 내부에서는 상대 경로 임포트를 사용하는 것이 좋습니다. 패키지의 이름이 변경되거나, 패키지가 다른 위치로 이동해도 임포트 경로를 수정할 필요가 없기 때문입니다.

## 3. 의존성 관리

파이썬 프로젝트는 종종 외부 라이브러리나 프레임워크에 의존합니다. 이러한 의존성(dependencies)을 체계적으로 관리하는 것은 프로젝트의 안정성과 재현성을 보장하는 데 매우 중요합니다.

### 3.1 `requirements.txt` 파일 생성 및 사용법

`requirements.txt` 파일은 프로젝트가 의존하는 모든 외부 패키지와 그 버전을 명시하는 텍스트 파일입니다. 이를 통해 다른 개발자가 프로젝트를 설정하거나, 배포 환경을 구축할 때 필요한 모든 의존성을 쉽게 설치할 수 있습니다.

**`requirements.txt` 예시:**

```
# requirements.txt

numpy==1.24.3
pandas>=1.5.0,<2.0.0
requests~=2.28.1
django
```

- `==`: 정확한 버전 지정
- `>=`: 최소 버전 지정
- `<=`: 최대 버전 지정
- `~=`: 호환 가능한 릴리스 지정 (예: `2.28.1`은 `2.28.x` 버전 중 최신 버전)

**사용법:**

1.  **의존성 설치:** `pip install -r requirements.txt`
    - 이 명령은 `requirements.txt` 파일에 명시된 모든 패키지를 자동으로 설치합니다.

2.  **현재 환경의 의존성 목록 생성:** `pip freeze > requirements.txt`
    - 현재 파이썬 가상 환경에 설치된 모든 패키지와 그 정확한 버전을 `requirements.txt` 파일로 저장합니다. 이는 프로젝트의 의존성을 고정(pinning)하여 재현 가능한 환경을 만드는 데 매우 중요합니다.

- **가상 환경(Virtual Environment) 사용:** 의존성 관리를 위해 **가상 환경**을 사용하는 것이 강력히 권장됩니다. 가상 환경은 프로젝트별로 독립적인 파이썬 환경을 제공하여, 서로 다른 프로젝트 간의 패키지 충돌을 방지합니다. `venv` 모듈을 사용하여 가상 환경을 생성하고 활성화할 수 있습니다.

    ```bash
    # 가상 환경 생성
    python -m venv venv_name

    # 가상 환경 활성화 (Windows)
    .\venv_name\Scripts\activate

    # 가상 환경 활성화 (macOS/Linux)
    source venv_name/bin/activate

    # 가상 환경 비활성화
    deactivate
    ```

### 3.2 고급 의존성 관리 (Editable Installs, pyproject.toml)

#### 3.2.1 Editable Installs (`pip install -e .`)

로컬에서 개발 중인 패키지를 다른 프로젝트에서 바로 임포트하여 사용할 수 있도록 하는 기능입니다. 패키지 소스 코드를 수정하면, 별도의 재설치 없이 변경 사항이 즉시 반영됩니다. 이는 패키지 개발 및 테스트 과정에서 매우 유용합니다.

```bash
# 프로젝트 루트 디렉토리에서 실행
pip install -e .
```

#### 3.2.2 `pyproject.toml`과 현대적인 패키징

`requirements.txt`는 간단한 의존성 관리에 유용하지만, 더 복잡한 프로젝트나 라이브러리 개발에서는 `pyproject.toml` 파일을 사용하여 패키징 및 의존성을 관리하는 것이 현대적인 파이썬의 추세입니다. `pyproject.toml`은 PEP 518에 따라 빌드 시스템 요구 사항을 지정하는 표준이며, Poetry, Hatch, PDM과 같은 현대적인 패키징 도구들이 이를 활용합니다.

`pyproject.toml`은 의존성 관리뿐만 아니라, 프로젝트 메타데이터, 빌드 설정, 테스트 설정 등 다양한 정보를 통합하여 관리할 수 있게 합니다. 이는 `setup.py`와 `requirements.txt`의 역할을 통합하고 확장하는 개념입니다.

**`pyproject.toml` (Poetry 예시):**

```toml
# pyproject.toml

[tool.poetry]
name = "my-awesome-project"
version = "0.1.0"
description = "A short description of my project."
authors = ["Your Name <you@example.com>"]

[tool.poetry.dependencies]
python = "^3.9"
numpy = "^1.24.0"
pandas = "^1.5.0"
requests = "^2.28.1"

[build-system]
requires = ["poetry-core>=1.0.0"]
build-backend = "poetry.core.masonry.api"
```

- **장점:**
  - **통합 관리:** 의존성, 프로젝트 메타데이터, 빌드 설정 등을 한 파일에서 관리합니다.
  - **환경 재현성:** `poetry.lock`과 같은 락(lock) 파일을 통해 정확한 의존성 버전을 고정하여 환경 재현성을 높입니다.
  - **개발자 경험:** Poetry와 같은 도구는 가상 환경 관리, 패키지 설치, 빌드 및 배포 과정을 간소화하여 개발자 경험을 향상시킵니다.

복잡한 프로젝트나 라이브러리를 개발할 때는 `pyproject.toml`과 함께 Poetry, Hatch 등의 도구를 사용하는 것을 고려해볼 수 있습니다.

#### 3.2.3 패키지 배포 (Deployment)

개발한 파이썬 패키지를 다른 사람들과 공유하거나, 다른 프로젝트에서 재사용하기 위해서는 PyPI(Python Package Index)와 같은 패키지 저장소에 배포하는 과정이 필요합니다. `pyproject.toml`을 사용하는 현대적인 패키징 도구(예: Poetry)는 배포 과정을 간소화합니다.

-   **배포 과정 (Poetry 예시):**
    1.  **빌드:** `poetry build` 명령을 사용하여 배포 가능한 패키지 파일(`.whl` 및 `.tar.gz`)을 생성합니다.
    2.  **게시:** `poetry publish` 명령을 사용하여 PyPI(또는 TestPyPI)에 패키지를 업로드합니다.

-   **실무적 의미:**
    -   자신이 개발한 유용한 함수나 클래스를 모듈화하여 패키지로 만들고 배포하는 것은 오픈소스 기여의 첫걸음이자, 팀 내에서 코드 재사용성을 극대화하는 중요한 방법입니다.
    -   CI/CD 파이프라인에 패키지 빌드 및 배포 단계를 자동화하여, 코드 변경 시 자동으로 새로운 버전의 패키지가 배포되도록 설정할 수 있습니다.
