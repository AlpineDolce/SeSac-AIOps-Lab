## 1. 쿼리 속의 쿼리: 서브쿼리(Subquery) 심화

서브쿼리(Subquery)는 다른 SQL 문 내부에 포함된 `SELECT` 문입니다. 메인 쿼리에 필요한 데이터를 제공하거나, 복잡한 조건을 정의하는 데 사용됩니다. 서브쿼리는 괄호 `()`로 묶이며, 메인 쿼리보다 먼저 실행됩니다.

### 1.1. 서브쿼리의 개념과 유형

*   **개념:** 하나의 쿼리 안에 또 다른 쿼리가 중첩되어 있는 형태입니다. 내부 쿼리(서브쿼리)의 결과가 외부 쿼리(메인 쿼리)의 입력으로 사용됩니다.
*   **유형:** 서브쿼리가 반환하는 결과의 형태에 따라 여러 유형으로 나눌 수 있습니다.

#### 1.1.1. 스칼라 서브쿼리 (단일 값 반환)

단일 로우의 단일 컬럼, 즉 하나의 값만 반환하는 서브쿼리입니다. `SELECT` 절, `WHERE` 절, `HAVING` 절 등 단일 값이 필요한 모든 곳에서 사용할 수 있습니다.

```sql
-- 전체 직원의 평균 급여보다 많이 받는 직원 조회
SELECT employee_id, first_name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);
```

> **스칼라 서브쿼리의 성능 고려사항:**
> 스칼라 서브쿼리는 매우 유용하지만, 사용 위치에 따라 성능에 큰 영향을 미칠 수 있습니다.
>
> *   **`WHERE` 절 또는 `HAVING` 절:** 이 경우 서브쿼리는 메인 쿼리 실행 전에 한 번만 실행되어 단일 값을 반환하므로, 성능 오버헤드가 크지 않습니다. 위 예시처럼 전체 평균 급여를 구하는 경우 효율적입니다.
> *   **`SELECT` 절:** `SELECT` 절에 스칼라 서브쿼리를 사용하면, **메인 쿼리의 각 로우마다 서브쿼리가 반복적으로 실행될 수 있습니다.** 이는 N+1 쿼리 문제와 유사한 성능 저하를 유발할 수 있습니다. 특히 대규모 데이터셋에서는 심각한 병목 현상이 될 수 있습니다.
>
> ```sql
> -- SELECT 절에 스칼라 서브쿼리 사용 예시 (성능 저하 가능성 있음)
> SELECT
>     employee_id,
>     first_name,
>     salary,
>     (SELECT AVG(salary) FROM employees WHERE department_id = e.department_id) AS dept_avg_salary -- 각 직원 로우마다 서브쿼리 실행
> FROM
>     employees e;
> ```
>
> **대안:** `SELECT` 절에서 각 로우에 대한 집계 값을 가져와야 할 경우, 스칼라 서브쿼리 대신 **`JOIN`** 또는 **윈도우 함수(Window Functions)**를 사용하는 것이 훨씬 효율적입니다.
>
> *   **`JOIN` 활용:** 중간 집계 결과를 인라인 뷰(Inline View)로 만들고 `JOIN`하여 사용합니다.
> *   **윈도우 함수 활용:** `AVG(salary) OVER (PARTITION BY department_id)`와 같이 윈도우 함수를 사용하면 각 로우에 대해 그룹별 평균을 효율적으로 계산할 수 있습니다. (자세한 내용은 [07_윈도우함수와_CTE.md](./07_윈도우함수와_CTE.md) 참조)
>
> 항상 `EXPLAIN` 명령을 통해 쿼리 실행 계획을 분석하고, 성능 병목 지점을 찾아 최적의 방법을 선택하는 습관을 들이는 것이 중요합니다.

#### 1.1.2. 로우 서브쿼리 (단일 로우 반환)

단일 로우의 여러 컬럼 값을 반환하는 서브쿼리입니다. 주로 `WHERE` 절에서 비교 연산자와 함께 사용됩니다.

```sql
-- 특정 부서(예: department_id가 1인 부서)의 최고 급여를 받는 직원 조회
SELECT employee_id, first_name, salary, department_id
FROM employees
WHERE (department_id, salary) = (SELECT department_id, MAX(salary) FROM employees WHERE department_id = 1);
```

> **로우 서브쿼리 활용 시 주의사항:**
> 로우 서브쿼리는 여러 컬럼을 동시에 비교할 때 유용하지만, 다음과 같은 점을 고려해야 합니다.
>
> *   **단일 로우 반환 보장:** 로우 서브쿼리는 반드시 **단일 로우**를 반환해야 합니다. 만약 서브쿼리가 두 개 이상의 로우를 반환하면 오류가 발생합니다. `MAX()`, `MIN()`과 같이 집계 함수를 사용하거나, `LIMIT 1`을 명시하여 단일 로우를 보장해야 합니다.
> *   **성능 고려:** 로우 서브쿼리도 스칼라 서브쿼리와 마찬가지로 메인 쿼리의 각 로우에 대해 반복적으로 실행될 수 있는 상관 서브쿼리 형태로 사용될 경우 성능 저하를 유발할 수 있습니다. 특히 `IN` 연산자와 함께 사용될 때 `EXISTS`나 `JOIN`으로 대체하는 것을 고려해야 합니다. (자세한 내용은 [1.3.3. `EXISTS` vs `IN` 성능 고려사항](#133-exists-vs-in-성능-고려사항-실무적-최적화-전략) 참조)
> *   **가독성:** 복잡한 로우 서브쿼리는 가독성을 해칠 수 있습니다. 경우에 따라 `JOIN`이나 CTE를 사용하여 쿼리를 분리하는 것이 더 명확할 수 있습니다.

#### 1.1.3. 테이블 서브쿼리 (다중 로우/컬럼 반환)

여러 로우와 여러 컬럼을 반환하는 서브쿼리입니다. 주로 `FROM` 절에서 인라인 뷰(Inline View)로 사용되거나, `WHERE` 절의 `IN`, `EXISTS` 등과 함께 사용됩니다.

```sql
-- 각 부서의 평균 급여보다 많이 받는 직원 조회
SELECT e.first_name, e.salary, e.department_id
FROM employees e
JOIN (
    SELECT department_id, AVG(salary) AS avg_dept_salary
    FROM employees
    GROUP BY department_id
) AS dept_avg ON e.department_id = dept_avg.department_id
WHERE e.salary > dept_avg.avg_dept_salary;
```

> **테이블 서브쿼리의 활용과 성능:**
> 테이블 서브쿼리는 복잡한 쿼리를 단계별로 나누어 처리할 때 매우 유용합니다. 특히 `FROM` 절에서 사용될 때 **인라인 뷰(Inline View)**라고 불리며, 중간 계산 결과를 임시 테이블처럼 활용할 수 있게 합니다.
>
> *   **활용성:**
>     *   **중간 집계:** 복잡한 집계 쿼리의 중간 결과를 생성하여 메인 쿼리에서 재사용할 수 있습니다. (위 예시처럼 부서별 평균 급여를 먼저 계산하여 활용)
>     *   **데이터 전처리:** 원본 테이블에 직접 접근하기 전에 필요한 데이터만 필터링하거나 가공하여 메인 쿼리의 복잡도를 줄일 수 있습니다.
>     *   **가독성 향상:** 복잡한 쿼리를 논리적인 단위로 분리하여 쿼리 전체의 가독성을 높이는 데 기여합니다.
>
> *   **성능 고려사항:**
>     *   **옵티마이저의 역할:** 데이터베이스 옵티마이저는 인라인 뷰를 최적화하여 실제로는 서브쿼리를 별도의 임시 테이블로 만들지 않고 메인 쿼리와 통합하여 실행하는 경우가 많습니다. 하지만 항상 그런 것은 아니므로, `EXPLAIN`을 통해 실행 계획을 확인하는 것이 중요합니다.
>     *   **`CTE`로의 전환:** 테이블 서브쿼리가 복잡해지거나 여러 번 재사용되어야 할 경우, `CTE(Common Table Expression)`로 리팩토링하는 것을 강력히 권장합니다. CTE는 가독성과 재사용성 측면에서 인라인 뷰보다 훨씬 유리하며, 옵티마이저가 더 효율적인 실행 계획을 세울 기회를 제공할 수 있습니다. (자세한 내용은 [1.4. CTE (Common Table Expression)](#14-cte-common-table-expression-복잡한-쿼리의-구조화와-재사용) 참조)
>     *   **인덱스 활용:** 인라인 뷰 내부의 쿼리도 인덱스를 효율적으로 사용할 수 있도록 설계해야 합니다. 인라인 뷰의 결과가 대규모일 경우, 메인 쿼리와의 `JOIN` 성능에 영향을 미칠 수 있습니다.

### 1.2. 서브쿼리 활용 예시

서브쿼리는 다양한 SQL 절에서 활용되어 복잡한 데이터 조회 요구사항을 해결합니다.

#### 1.2.1. `WHERE` 절에서 서브쿼리 사용 (`IN`, `NOT IN`, `ANY`, `ALL`)

*   `IN`: 서브쿼리 결과 집합에 값이 포함되는지 확인.
*   `NOT IN`: 서브쿼리 결과 집합에 값이 포함되지 않는지 확인.
*   `ANY`: 서브쿼리 결과 집합의 어떤 값이라도 조건에 맞으면 참.
*   `ALL`: 서브쿼리 결과 집합의 모든 값이 조건에 맞으면 참.

```sql
-- 프로젝트에 참여하는 직원 조회
SELECT employee_id, first_name
FROM employees
WHERE employee_id IN (SELECT employee_id FROM project_assignments);

-- 프로젝트에 참여하지 않는 직원 조회
SELECT employee_id, first_name
FROM employees
WHERE employee_id NOT IN (SELECT employee_id FROM project_assignments);

-- 어떤 부서의 최소 급여보다 많이 받는 직원 조회
SELECT employee_id, first_name, salary
FROM employees
WHERE salary > ANY (SELECT MIN(salary) FROM employees GROUP BY department_id);

-- 모든 부서의 최대 급여보다 많이 받는 직원 조회 (즉, 전체 최고 급여보다 많이 받는 직원)
SELECT employee_id, first_name, salary
FROM employees
WHERE salary > ALL (SELECT MAX(salary) FROM employees GROUP BY department_id);
```

> **`IN` 및 `NOT IN` 사용 시 주의사항:**
> `IN` 연산자는 특정 값 목록에 포함되는지 여부를 확인할 때 매우 유용합니다. 하지만 `NOT IN`과 함께 사용할 때는 특히 주의해야 할 점이 있습니다.
>
> *   **`IN`의 성능:** 서브쿼리의 결과 집합이 **작을 때** `IN`은 효율적입니다. 서브쿼리가 먼저 실행되어 모든 결과를 메모리에 로드한 후 메인 쿼리와 비교하기 때문입니다. 하지만 결과 집합이 매우 커지면 메모리 부하가 커지고 성능이 저하될 수 있습니다. 이 경우 `EXISTS`로 대체하는 것을 고려해야 합니다. (자세한 내용은 [1.3.3. `EXISTS` vs `IN` 성능 고려사항](#133-exists-vs-in-성능-고려사항-실무적-최적화-전략) 참조)
> *   **`NOT IN`과 `NULL` 값:** `NOT IN` 연산자는 서브쿼리 결과에 `NULL` 값이 하나라도 포함되어 있으면, `NOT IN` 조건 전체가 `FALSE`를 반환하는 치명적인 문제가 있습니다. 이는 예상치 못한 결과를 초래하여 데이터 분석의 정확성을 해칠 수 있습니다.
>     ```sql
>     -- 예시: project_assignments 테이블에 employee_id가 NULL인 로우가 있다면, 이 쿼리는 아무 결과도 반환하지 않을 수 있음
>     SELECT employee_id, first_name
>     FROM employees
>     WHERE employee_id NOT IN (SELECT employee_id FROM project_assignments);
>     ```
>     따라서 `NOT IN` 대신 **`NOT EXISTS`** 또는 **`LEFT JOIN ... IS NULL`** 패턴을 사용하는 것이 훨씬 안전하고 예측 가능합니다. 이는 `NULL` 값으로 인한 문제를 회피하고 정확한 결과를 보장합니다.
> *   **`ANY`와 `ALL`의 활용:** `ANY`와 `ALL`은 `IN`이나 `EXISTS`보다 사용 빈도가 낮지만, 특정 비교 조건(예: `> ANY`, `< ALL`)에서 유용하게 사용될 수 있습니다. 하지만 가독성 측면에서는 `IN`이나 `EXISTS`가 더 선호되는 경우가 많습니다.

#### 1.2.2. `FROM` 절에서 서브쿼리 사용 (인라인 뷰)

서브쿼리의 결과를 임시 테이블(인라인 뷰)처럼 사용하여 메인 쿼리에서 조회합니다. 복잡한 중간 계산 결과를 활용할 때 유용합니다.

```sql
-- 각 부서의 평균 급여를 계산한 후, 그 결과를 사용하여 직원 정보와 함께 조회
SELECT
    e.first_name, e.last_name,
    d.department_name,
    dept_avg.avg_salary
FROM
    employees e
JOIN
    departments d ON e.department_id = d.department_id
JOIN
    (SELECT department_id, AVG(salary) AS avg_salary FROM employees GROUP BY department_id) AS dept_avg
    ON e.department_id = dept_avg.department_id;
```

> **인라인 뷰(Inline View)의 활용과 최적화:**
> `FROM` 절에서 사용되는 서브쿼리를 **인라인 뷰(Inline View)**라고 합니다. 이는 쿼리 내에서 임시적인 가상 테이블을 생성하여 복잡한 쿼리를 단계별로 나누어 처리할 때 매우 유용합니다.
>
> *   **개념:** 인라인 뷰는 메인 쿼리가 실행되기 전에 먼저 실행되어 하나의 결과 집합을 생성하고, 메인 쿼리는 이 결과 집합을 마치 실제 테이블처럼 사용하여 `JOIN`하거나 필터링합니다.
> *   **장점:**
>     *   **모듈화 및 가독성:** 복잡한 쿼리를 논리적인 단위로 분리하여 쿼리 전체의 가독성을 높입니다. 각 서브쿼리가 어떤 역할을 하는지 명확히 파악할 수 있습니다.
>     *   **중간 결과 재사용:** 복잡한 집계나 계산의 중간 결과를 인라인 뷰로 만들어 메인 쿼리에서 쉽게 재사용할 수 있습니다.
>     *   **데이터 전처리:** 원본 테이블에 직접 접근하기 전에 필요한 데이터만 미리 필터링하거나 가공하여 메인 쿼리의 복잡도를 줄일 수 있습니다.
> *   **성능 고려사항:**
>     *   **옵티마이저의 역할:** 현대 데이터베이스의 옵티마이저는 인라인 뷰를 최적화하여 실제로는 서브쿼리를 별도의 임시 테이블로 만들지 않고 메인 쿼리와 통합하여 실행하는 경우가 많습니다 (View Merging). 하지만 항상 그런 것은 아니므로, `EXPLAIN`을 통해 실행 계획을 확인하는 것이 중요합니다.
>     *   **임시 테이블 생성:** 경우에 따라서는 옵티마이저가 인라인 뷰의 결과를 물리적인 임시 테이블로 생성할 수 있습니다. 이 경우 디스크 I/O가 발생하여 성능 저하를 유발할 수 있습니다.
>     *   **별칭(Alias) 필수:** `FROM` 절의 서브쿼리에는 반드시 별칭(Alias)을 부여해야 합니다. (예: `AS dept_avg`)
> *   **`CTE`로의 전환:** 인라인 뷰가 복잡해지거나 여러 번 재사용되어야 할 경우, `CTE(Common Table Expression)`로 리팩토링하는 것을 강력히 권장합니다. CTE는 가독성과 재사용성 측면에서 인라인 뷰보다 훨씬 유리하며, 옵티마이저가 더 효율적인 실행 계획을 세울 기회를 제공할 수 있습니다. (자세한 내용은 [1.4. CTE (Common Table Expression)](#14-cte-common-table-expression-복잡한-쿼리의-구조화와-재사용) 참조)
>
> 인라인 뷰는 복잡한 쿼리를 구조화하는 강력한 도구이지만, 성능에 대한 이해와 `EXPLAIN`을 통한 검증이 필수적입니다.

#### 1.2.3. `SELECT` 절에서 서브쿼리 사용

스칼라 서브쿼리만 `SELECT` 절에서 사용할 수 있습니다. 각 로우에 대해 서브쿼리가 실행되어 단일 값을 반환합니다.

```sql
-- 각 직원의 급여와 해당 직원이 속한 부서의 평균 급여를 함께 조회
SELECT
    e.first_name, e.salary,
    (SELECT AVG(salary) FROM employees WHERE department_id = e.department_id) AS dept_avg_salary
FROM
    employees e;
```

> **`SELECT` 절 스칼라 서브쿼리의 성능 함정:**
> `SELECT` 절에 스칼라 서브쿼리를 사용하는 것은 매우 직관적이고 편리해 보이지만, **성능 측면에서는 가장 주의해야 할 패턴 중 하나입니다.**
>
> *   **N+1 쿼리 문제와 유사:** `SELECT` 절의 스칼라 서브쿼리는 메인 쿼리의 각 로우마다 한 번씩 실행됩니다. 즉, 메인 쿼리가 N개의 로우를 반환한다면, 서브쿼리는 N번 실행됩니다. 이는 데이터베이스에 N개의 추가적인 쿼리 요청을 발생시켜 심각한 성능 저하를 유발할 수 있습니다. 특히 메인 테이블의 로우 수가 많거나, 서브쿼리 자체가 복잡할수록 병목 현상이 심화됩니다.
> *   **인덱스 활용의 어려움:** 서브쿼리 내에서 외부 쿼리의 컬럼을 참조하는 상관 서브쿼리 형태가 되기 때문에, 인덱스를 효율적으로 활용하기 어렵거나 아예 사용하지 못하는 경우가 많습니다.
>
> **언제 사용하고, 언제 피해야 할까?**
> *   **사용을 고려할 때:**
>     *   메인 쿼리의 결과 로우 수가 **매우 적을 때** (수십 건 이내).
>     *   서브쿼리가 **매우 단순하고 빠르게 실행될 때**.
>     *   다른 대안(JOIN, 윈도우 함수)으로 구현하기가 지나치게 복잡하거나 불가능할 때.
> *   **사용을 피하고 대안을 고려할 때 (대부분의 경우):**
>     *   메인 쿼리의 결과 로우 수가 많을 때.
>     *   서브쿼리가 복잡하거나, 대량의 데이터를 처리해야 할 때.
>
> **주요 대안:**
> 1.  **`JOIN` 활용:** 스칼라 서브쿼리가 계산하는 값을 미리 집계하여 인라인 뷰(또는 CTE)로 만들고, 이를 메인 테이블과 `JOIN`하는 것이 훨씬 효율적입니다. 데이터베이스는 `JOIN` 연산을 최적화하는 데 매우 능숙합니다.
>     ```sql
>     -- JOIN을 활용한 대안 (더 효율적)
>     SELECT
>         e.first_name, e.salary, das.avg_dept_salary
>     FROM
>         employees e
>     JOIN
>         (SELECT department_id, AVG(salary) AS avg_dept_salary FROM employees GROUP BY department_id) AS das
>         ON e.department_id = das.department_id;
>     ```
> 2.  **윈도우 함수 (Window Functions):** `SELECT` 절에서 그룹별 집계 값을 가져와야 할 때 가장 강력하고 효율적인 대안입니다. 윈도우 함수는 로우 수를 줄이지 않으면서 그룹 내의 집계 값을 각 로우에 추가할 수 있습니다.
>     ```sql
>     -- 윈도우 함수를 활용한 대안 (가장 효율적)
>     SELECT
>         e.first_name, e.salary,
>         AVG(e.salary) OVER (PARTITION BY e.department_id) AS dept_avg_salary
>     FROM
>         employees e;
>     ```
>
> **결론:** `SELECT` 절의 스칼라 서브쿼리는 편리하지만, 성능 문제를 야기할 가능성이 높으므로, 항상 `JOIN`이나 윈도우 함수와 같은 대안을 우선적으로 고려하고 `EXPLAIN`으로 성능을 검증하는 습관을 들여야 합니다.

### 1.3. 상관 서브쿼리 (Correlated Subquery): 외부 쿼리와의 연동

상관 서브쿼리는 외부 쿼리의 로우에 따라 서브쿼리가 반복적으로 실행되는 형태입니다. 외부 쿼리의 컬럼을 서브쿼리 내에서 참조합니다. 비상관 서브쿼리보다 성능이 떨어질 수 있으므로 주의해서 사용해야 합니다.

> **상관 서브쿼리의 이해와 성능:**
> 상관 서브쿼리(Correlated Subquery)는 이름 그대로 메인 쿼리(외부 쿼리)와 **상관 관계**를 가집니다. 즉, 서브쿼리가 외부 쿼리의 컬럼 값을 참조하며, 외부 쿼리의 각 로우에 대해 서브쿼리가 **반복적으로 실행**됩니다.
>
> *   **동작 방식:**
>     1.  메인 쿼리에서 하나의 로우를 가져옵니다.
>     2.  가져온 로우의 값을 사용하여 서브쿼리를 실행합니다.
>     3.  서브쿼리 결과에 따라 메인 쿼리의 로우를 처리합니다.
>     4.  메인 쿼리의 다음 로우에 대해 1~3단계를 반복합니다.
> *   **비상관 서브쿼리와의 차이:**
>     *   **비상관 서브쿼리:** 메인 쿼리와 독립적으로 한 번만 실행되어 결과를 반환합니다. (예: `WHERE salary > (SELECT AVG(salary) FROM employees)`) 이 결과는 메인 쿼리 전체에서 재사용됩니다.
>     *   **상관 서브쿼리:** 메인 쿼리의 각 로우에 대해 매번 실행됩니다. 따라서 메인 쿼리의 로우 수가 많을수록 서브쿼리 실행 횟수가 기하급수적으로 늘어나 성능 저하의 주요 원인이 됩니다.
> *   **성능 특성:**
>     *   **N*M 문제:** 메인 쿼리가 N개의 로우를 가지고 서브쿼리가 M번의 연산을 필요로 한다면, 총 N*M의 연산이 발생할 수 있습니다. 이는 대규모 데이터셋에서 치명적인 성능 병목이 됩니다.
>     *   **인덱스 활용의 어려움:** 서브쿼리가 외부 쿼리의 컬럼을 참조하기 때문에, 옵티마이저가 인덱스를 효율적으로 사용하기 어렵거나 아예 사용하지 못하는 경우가 많습니다.
>
> **언제 사용하고, 언제 피해야 할까?**
> *   **사용을 고려할 때:**
>     *   `EXISTS` 또는 `NOT EXISTS`와 함께 사용될 때 (서브쿼리가 조건에 맞는 첫 로우를 찾으면 즉시 중단되므로 효율적일 수 있음).
>     *   각 그룹 내에서 특정 조건을 만족하는 로우를 찾아야 할 때 (예: 각 부서에서 최고 급여를 받는 직원).
>     *   다른 대안(JOIN, 윈도우 함수)으로 구현하기가 지나치게 복잡하거나 불가능할 때.
> *   **사용을 피하고 대안을 고려할 때 (대부분의 경우):**
>     *   성능이 중요한 쿼리.
>     *   메인 쿼리의 로우 수가 많을 때.
>
> **주요 대안:**
> 대부분의 상관 서브쿼리는 `JOIN` (특히 `LEFT JOIN`과 `GROUP BY`를 조합), `CTE`, 또는 **윈도우 함수**로 대체하여 성능을 크게 향상시킬 수 있습니다. 윈도우 함수는 특히 그룹 내 순위, 최대/최소 값 등을 찾을 때 상관 서브쿼리보다 훨씬 효율적입니다. (자세한 내용은 [07_윈도우함수와_CTE.md](./07_윈도우함수와_CTE.md) 참조)
>
> 항상 `EXPLAIN` 명령을 통해 쿼리 실행 계획을 분석하고, 상관 서브쿼리가 성능 병목의 원인인지 확인하는 습관을 들이는 것이 중요합니다.

#### 1.3.1. `EXISTS`와 `NOT EXISTS` 활용

`EXISTS`는 서브쿼리가 반환하는 로우가 하나라도 있으면 `TRUE`를 반환하고, 없으면 `FALSE`를 반환합니다. 서브쿼리의 실제 데이터는 중요하지 않고, 존재 여부만 확인할 때 사용합니다.

```sql
-- 프로젝트에 참여하는 직원 조회 (EXISTS 사용)
SELECT employee_id, first_name
FROM employees e
WHERE EXISTS (SELECT 1 FROM project_assignments pa WHERE pa.employee_id = e.employee_id);

-- 프로젝트에 참여하지 않는 직원 조회 (NOT EXISTS 사용)
SELECT employee_id, first_name
FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM project_assignments pa WHERE pa.employee_id = e.employee_id);
```

> **`EXISTS`와 `NOT EXISTS`의 효율성:**
> `EXISTS`와 `NOT EXISTS`는 서브쿼리의 결과가 존재하는지 여부만 확인하므로, 서브쿼리가 조건에 맞는 첫 번째 로우를 찾으면 즉시 실행을 중단합니다. 이러한 **단락 평가(Short-circuit Evaluation)** 특성 덕분에 대규모 데이터셋에서 매우 효율적일 수 있습니다.
>
> *   **`EXISTS`의 장점:**
>     *   **성능:** 특히 상관 서브쿼리(Correlated Subquery)에서 `IN` 연산자보다 성능상 유리한 경우가 많습니다. `IN`은 서브쿼리의 모든 결과를 메모리에 로드해야 하지만, `EXISTS`는 존재 여부만 확인하므로 불필요한 데이터 로딩을 피할 수 있습니다.
>     *   **`NULL` 안전성:** `IN`과 달리 `NULL` 값으로 인한 예상치 못한 결과 문제를 일으키지 않습니다. `EXISTS`는 `NULL`을 포함한 로우의 존재 여부를 정확히 판단합니다.
> *   **`NOT EXISTS`의 활용:**
>     *   `NOT EXISTS`는 특정 조건에 해당하는 데이터가 **존재하지 않는** 경우를 찾을 때 사용됩니다. 이는 `LEFT JOIN ... IS NULL` 패턴과 함께 `NOT IN`의 안전한 대안으로 널리 사용됩니다.
>     *   **예시:** "어떤 부서에도 속하지 않은 직원"을 찾을 때 `NOT EXISTS`를 사용하면 명확하고 효율적입니다.
>
> **언제 `EXISTS`를 사용할까?**
> 주로 "~가 있는/없는" 데이터를 필터링할 때 사용합니다. 예를 들어, "주문 이력이 있는 고객", "특정 상품을 구매한 적 없는 고객" 등을 찾을 때 `EXISTS` 또는 `NOT EXISTS`가 적합합니다. `SELECT` 절에서 서브쿼리의 실제 값을 가져와야 하는 경우에는 `EXISTS`를 사용할 수 없으며, `JOIN`이나 스칼라 서브쿼리(성능 주의)를 고려해야 합니다.
>
> `EXPLAIN` 명령을 통해 `EXISTS` 쿼리의 실행 계획을 분석하여 최적의 성능을 확보하는 것이 중요합니다. (자세한 내용은 [1.3.3. `EXISTS` vs `IN` 성능 고려사항](#133-exists-vs-in-성능-고려사항-실무적-최적화-전략) 참조)

#### 1.3.2. 비교 분석용 상관 서브쿼리

각 그룹 내에서 특정 조건을 만족하는 로우를 찾을 때 유용합니다.

```sql
-- 각 부서에서 가장 높은 급여를 받는 직원 조회
SELECT employee_id, first_name, salary, department_id
FROM employees e1
WHERE salary = (SELECT MAX(salary) FROM employees e2 WHERE e1.department_id = e2.department_id);
```

> **비교 분석용 상관 서브쿼리의 활용과 대안:**
> 이 유형의 상관 서브쿼리는 "각 그룹(예: 부서, 카테고리) 내에서 특정 조건(예: 최고값, 최저값, 평균 이상)을 만족하는 로우"를 찾을 때 매우 직관적으로 사용될 수 있습니다. 위 예시는 "각 부서에서 가장 높은 급여를 받는 직원"을 찾는 대표적인 패턴입니다.
>
> *   **활용 사례:**
>     *   각 상품 카테고리별로 가장 많이 팔린 상품 찾기
>     *   각 고객 그룹별로 가장 최근에 구매한 고객 찾기
>     *   각 지역별로 평균 매출을 초과하는 지점 찾기
>
> *   **성능 문제점:**
>     *   이러한 상관 서브쿼리는 메인 쿼리의 각 로우에 대해 서브쿼리가 반복적으로 실행되므로, 메인 테이블의 로우 수가 많을수록 성능 저하가 심각해집니다. 특히 서브쿼리 내에서 집계 함수(`MAX`, `AVG` 등)가 사용될 경우, 매번 집계 연산을 수행해야 하므로 오버헤드가 더욱 커집니다.
>     *   `EXPLAIN`을 통해 실행 계획을 확인하면, `type`이 `ALL`이나 `index`로 나타나고 `Extra`에 `Using where`와 같은 메시지가 보일 수 있으며, `rows` 값이 매우 높게 나타날 수 있습니다.
>
> *   **주요 대안 (성능 최적화):**
>     대부분의 경우, 비교 분석용 상관 서브쿼리는 **윈도우 함수(Window Functions)**를 사용하여 훨씬 효율적으로 구현할 수 있습니다. 윈도우 함수는 한 번의 스캔으로 그룹 내의 모든 로우에 대한 계산을 수행할 수 있기 때문입니다.
>     ```sql
>     -- 윈도우 함수를 활용한 대안 (각 부서에서 가장 높은 급여를 받는 직원 조회)
>     SELECT employee_id, first_name, salary, department_id
>     FROM (
>         SELECT
>             employee_id, first_name, salary, department_id,
>             RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
>         FROM employees
>     ) AS ranked_employees
>     WHERE rnk = 1;
>     ```
>     이 외에도 `JOIN`과 `GROUP BY`를 조합하는 방법도 대안이 될 수 있습니다.
>
> **결론:** 비교 분석용 상관 서브쿼리는 직관적이지만 성능상 비효율적인 경우가 많습니다. 따라서 실무에서는 윈도우 함수나 `JOIN`과 `GROUP BY` 조합과 같은 더 효율적인 대안을 우선적으로 고려하고, `EXPLAIN`을 통해 쿼리 성능을 반드시 검증해야 합니다.

#### 1.3.3. `EXISTS` vs `IN` 성능 고려사항 (실무적 최적화 전략)

`EXISTS`와 `IN`은 서브쿼리의 결과를 기반으로 메인 쿼리를 필터링할 때 사용됩니다. 두 연산자는 때때로 상호 교환 가능하지만, 내부적인 동작 방식과 성능 특성이 매우 다르므로, 데이터 분석가는 상황에 따라 가장 효율적인 것을 선택하는 전략적 판단이 중요합니다.

*   **`IN` 연산자:**
    *   **동작 방식:** 서브쿼리가 먼저 독립적으로 실행되어 모든 결과를 메모리에 로드합니다. 이후 메인 쿼리의 각 로우에 대해 서브쿼리 결과 집합 내에 값이 존재하는지 비교합니다.
    *   **성능 특성:** 서브쿼리의 결과 집합이 **작을 때** 효율적입니다. 결과 집합이 너무 크면 메모리 부하가 커지고 성능이 저하될 수 있습니다.
    *   **주의사항:** 서브쿼리 결과에 `NULL` 값이 포함되어 있으면, `IN` 연산은 예상치 못한 결과를 반환할 수 있습니다. (예: `WHERE column IN (SELECT sub_column FROM ...)`에서 `sub_column`에 `NULL`이 있으면, `column`이 `NULL`이 아닌 어떤 값과도 매칭되지 않을 수 있습니다.)

*   **`EXISTS` 연산자:**
    *   **동작 방식:** 메인 쿼리의 각 로우에 대해 서브쿼리를 실행합니다. 서브쿼리는 조건에 맞는 첫 번째 로우를 찾으면 즉시 `TRUE`를 반환하고 실행을 멈춥니다. 서브쿼리의 실제 데이터는 중요하지 않고, 존재 여부만 확인합니다.
    *   **성능 특성:** 서브쿼리의 결과 집합이 **크거나**, 서브쿼리 내에 `LIMIT`와 같은 최적화가 가능한 경우 효율적입니다. 특히 **상관 서브쿼리**일 때 `IN`보다 유리한 경우가 많습니다. `EXISTS`는 조건에 맞는 로우가 하나라도 발견되면 즉시 중단하기 때문입니다.

**실무적 선택 가이드라인:**

1.  **서브쿼리가 비상관(Uncorrelated)이고 결과 집합이 작을 때:** `IN`을 사용합니다. (예: 특정 부서 ID 목록에 속하는 직원 찾기)
    ```sql
    -- IN 사용 예시 (비상관 서브쿼리, 결과 집합이 작을 때 유리)
    SELECT employee_id, first_name
    FROM employees
    WHERE employee_id IN (SELECT employee_id FROM project_assignments WHERE project_status = 'Active');
    ```

2.  **서브쿼리가 상관(Correlated)이거나 결과 집합이 클 때:** `EXISTS`를 사용합니다. (예: 각 직원이 참여하는 프로젝트가 하나라도 있는지 확인)
    ```sql
    -- EXISTS 사용 예시 (상관 서브쿼리, 결과 집합이 클 때 유리)
    SELECT employee_id, first_name
    FROM employees e
    WHERE EXISTS (SELECT 1 FROM project_assignments pa WHERE pa.employee_id = e.employee_id);
    ```

3.  **`NOT IN` 대신 `NOT EXISTS` 또는 `LEFT JOIN ... IS NULL`:**
    `NOT IN`은 서브쿼리 결과에 `NULL`이 하나라도 있으면 전체 결과가 `FALSE`가 되는 문제가 있습니다. 따라서 `NOT IN` 대신 `NOT EXISTS`나 `LEFT JOIN ... IS NULL` 패턴을 사용하는 것이 더 안전하고 예측 가능합니다.
    ```sql
    -- NOT EXISTS 사용 예시 (NOT IN보다 안전하고 효율적)
    SELECT employee_id, first_name
    FROM employees e
    WHERE NOT EXISTS (SELECT 1 FROM project_assignments pa WHERE pa.employee_id = e.employee_id);

    -- LEFT JOIN ... IS NULL 사용 예시 (NOT IN 대체)
    SELECT e.employee_id, e.first_name
    FROM employees e
    LEFT JOIN project_assignments pa ON e.employee_id = pa.employee_id
    WHERE pa.employee_id IS NULL;
    ```

**최종 조언:**
어떤 연산자가 더 효율적인지는 데이터의 양, 분포, 인덱스 유무, 그리고 데이터베이스 옵티마이저의 특성에 따라 달라질 수 있습니다. 따라서 항상 `EXPLAIN` 명령을 사용하여 쿼리 실행 계획을 분석하고, 실제 환경에서 성능 테스트를 수행하여 최적의 방법을 찾는 것이 중요합니다.

**데이터 분석가는 쿼리의 논리적 정확성뿐만 아니라, 성능 효율성까지 고려하여 최적의 쿼리를 작성하는 능력을 갖춰야 합니다.

### 1.4. CTE (Common Table Expression): 복잡한 쿼리의 구조화와 재사용

서브쿼리 안에 또 다른 서브쿼리가 포함되는 다중 레벨 서브쿼리는 복잡한 비즈니스 로직을 해결할 수 있지만, 다음과 같은 심각한 단점이 있습니다.

*   **가독성 저하:** 쿼리의 중첩 구조가 깊어질수록 코드를 이해하기 매우 어려워집니다.
*   **디버깅의 어려움:** 각 서브쿼리를 독립적으로 실행하고 테스트하기가 까다롭습니다.
*   **재사용성 부재:** 동일한 서브쿼리가 여러 번 필요할 경우 코드가 중복됩니다.

**실무에서는 복잡한 서브쿼리, 특히 `FROM` 절에 사용되는 인라인 뷰(Inline View)나 2단계 이상 중첩되는 서브쿼리는 `CTE(Common Table Expression)`를 사용하여 리팩토링하는 것을 강력히 권장합니다.** CTE는 쿼리의 가독성, 재사용성, 유지보수성을 혁신적으로 개선하는 현대 SQL의 필수 기법입니다.

CTE는 쿼리를 여러 개의 명명된 논리적 단계로 분리하여, 각 단계의 결과를 다음 단계에서 참조할 수 있게 합니다. 이는 복잡한 쿼리를 마치 프로그래밍 언어의 함수처럼 모듈화하여 작성하는 것과 유사합니다.

**CTE의 주요 장점:**
*   **가독성 향상:** 복잡한 쿼리를 논리적인 단위로 분리하여 단계별로 이해하기 쉽게 만듭니다.
*   **재사용성:** 한 번 정의된 CTE는 동일한 쿼리 내에서 여러 번 참조될 수 있어 코드 중복을 줄입니다.
*   **유지보수성:** 쿼리 로직이 명확해져 오류를 찾고 수정하기 용이합니다.
*   **재귀 쿼리 구현:** 계층적 데이터(예: 조직도, 댓글 스레드)를 처리하는 재귀 쿼리를 구현할 수 있게 합니다.

> **CTE가 쿼리 개발 및 유지보수에 미치는 영향:**
> CTE는 단순한 문법적 편의를 넘어, 복잡한 SQL 쿼리를 마치 프로그래밍 언어의 함수처럼 모듈화하고 구조화하는 데 핵심적인 역할을 합니다. 이는 특히 대규모 데이터 분석 프로젝트나 데이터 웨어하우스 환경에서 빛을 발합니다.
>
> *   **디버깅 용이성:** 복잡한 쿼리에서 오류가 발생했을 때, CTE를 사용하면 각 단계별로 쿼리를 독립적으로 실행하여 중간 결과를 확인하고 문제의 원인을 빠르게 파악할 수 있습니다. 이는 중첩 서브쿼리에서는 불가능하거나 매우 어렵습니다.
> *   **협업 효율성:** 여러 분석가나 개발자가 하나의 복잡한 쿼리를 함께 작업할 때, CTE를 통해 각자의 담당 부분을 명확히 분리하고 이해하기 쉽게 만들 수 있습니다. 이는 코드 리뷰를 용이하게 하고, 소통 오류를 줄여줍니다.
> *   **테스트 용이성:** 각 CTE를 독립적인 단위로 테스트할 수 있으므로, 쿼리 전체의 정확성을 검증하는 데 도움이 됩니다.
> *   **성능 최적화 기회:** 옵티마이저가 CTE를 인라인 뷰처럼 처리하는 경우가 많지만, CTE로 로직을 명확히 분리하면 옵티마이저가 더 효율적인 실행 계획을 수립할 기회를 얻을 수 있습니다. 특히 동일한 CTE가 여러 번 참조될 경우, 데이터베이스는 이를 한 번만 계산하고 결과를 재사용하여 성능을 향상시킬 수 있습니다 (DBMS에 따라 다름).
>
> CTE는 현대 SQL의 필수적인 기법이며, 이를 능숙하게 사용하는 것은 데이터 분석가의 쿼리 작성 역량을 한 단계 높이는 중요한 지표입니다.

**[나쁜 예: 중첩 서브쿼리]**
```sql
-- 각 부서의 평균 급여보다 많이 받는 직원들 중에서,
-- 'Development' 부서에 속한 직원들의 정보를 조회
SELECT *
FROM (
    SELECT e.employee_id, e.first_name, e.salary, e.department_id
    FROM employees e
    JOIN (
        SELECT department_id, AVG(salary) AS avg_dept_salary
        FROM employees
        GROUP BY department_id
    ) AS dept_avg ON e.department_id = dept_avg.department_id
    WHERE e.salary > dept_avg.avg_dept_salary
) AS high_salary_employees
WHERE department_id = 1; -- 'Development' 부서 ID가 1이라고 가정
```

**[좋은 예: CTE 활용]**
```sql
WITH
DepartmentAvgSalary AS (
    -- 1단계: 부서별 평균 급여 계산
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id
),
HighSalaryEmployees AS (
    -- 2단계: 부서 평균 급여보다 많이 받는 직원 필터링
    SELECT e.employee_id, e.first_name, e.salary, e.department_id
    FROM employees e
    JOIN DepartmentAvgSalary das ON e.department_id = das.department_id
    WHERE e.salary > das.avg_salary
)
-- 3단계: 최종 결과 조회
SELECT *
FROM HighSalaryEmployees
WHERE department_id = 1; -- 'Development' 부서 ID가 1이라고 가정
```

**CTE 사용 시 성능 고려사항 (실무적 관점):**
CTE는 가독성을 높이지만, 항상 성능 향상을 의미하지는 않습니다. 데이터베이스 옵티마이저는 CTE를 인라인 뷰처럼 처리하는 경우가 많으므로, CTE를 사용한다고 해서 자동으로 성능이 좋아지는 것은 아닙니다. 하지만 다음과 같은 경우 CTE가 성능 최적화에 도움이 될 수 있습니다.

*   **복잡한 로직의 분리:** 복잡한 계산이나 필터링 로직을 CTE로 분리하면, 옵티마이저가 각 단계를 더 잘 이해하고 최적화할 기회를 얻을 수 있습니다.
*   **재귀 CTE:** 계층적 쿼리에서 재귀 CTE는 다른 방법으로는 구현하기 어렵거나 비효율적인 쿼리를 가능하게 합니다.
*   **코드 재사용:** 동일한 중간 결과를 여러 번 참조해야 할 때, CTE를 사용하면 중복 계산을 피할 수 있어 성능상 이점을 얻을 수 있습니다 (단, DBMS에 따라 CTE가 매번 재실행될 수도 있으므로 `EXPLAIN`으로 확인 필요).

> **CTE와 성능: 옵티마이저의 역할과 `EXPLAIN`의 중요성:**
> CTE는 쿼리 가독성과 유지보수성을 크게 향상시키지만, 성능 측면에서는 만능이 아닙니다. 데이터베이스 옵티마이저는 CTE를 만나면 이를 어떻게 처리할지 결정합니다. 대부분의 경우 옵티마이저는 CTE를 마치 서브쿼리처럼 메인 쿼리에 **인라인(inline)**하여 하나의 큰 쿼리로 최적화하려고 시도합니다. 즉, CTE를 사용했다고 해서 반드시 별도의 임시 테이블이 생성되거나 성능이 향상되는 것은 아닙니다.
>
> *   **성능 향상 가능성:**
>     *   **명확한 로직 분리:** 복잡한 로직을 CTE로 명확히 분리하면, 옵티마이저가 쿼리의 의도를 더 잘 파악하고 효율적인 실행 계획을 수립할 수 있습니다.
>     *   **재사용 시 중복 계산 방지:** 일부 DBMS에서는 동일한 CTE가 여러 번 참조될 경우, CTE의 결과를 한 번만 계산하고 캐시하여 재사용함으로써 성능 이점을 얻을 수 있습니다. 하지만 이는 DBMS의 구현 방식과 옵티마이저의 판단에 따라 달라지므로, **반드시 `EXPLAIN`으로 확인해야 합니다.**
> *   **성능 저하 가능성:**
>     *   **불필요한 임시 테이블 생성:** 드물게 옵티마이저가 CTE를 비효율적으로 처리하여 불필요한 임시 테이블을 생성하게 되면 성능 저하가 발생할 수 있습니다.
>     *   **복잡한 CTE:** 너무 많은 CTE를 중첩하거나 CTE 자체가 지나치게 복잡하면 옵티마이저가 최적의 실행 계획을 찾는 데 어려움을 겪을 수 있습니다.
>
> **결론적으로, CTE를 사용한 후에는 항상 `EXPLAIN` 명령을 통해 쿼리 실행 계획을 분석하는 것이 필수적입니다.** `EXPLAIN` 결과를 통해 `type`, `rows`, `Extra` 컬럼 등을 확인하여 CTE가 의도한 대로 최적화되었는지, `Using temporary`나 `Using filesort`와 같은 성능 저하 요인이 발생하지 않았는지 검증해야 합니다. 이를 통해 CTE의 가독성 이점과 함께 최적의 쿼리 성능을 확보할 수 있습니다.

**데이터 분석가의 역할:** CTE는 쿼리 작성의 모범 사례이지만, 실제 성능은 데이터베이스 시스템과 쿼리 내용에 따라 달라질 수 있습니다. 따라서 CTE를 적용한 후에도 반드시 `EXPLAIN` 명령을 통해 쿼리 실행 계획을 분석하고, 필요한 경우 추가적인 인덱스 튜닝이나 다른 최적화 기법을 고려해야 합니다.

## 2. 윈도우 함수 (Window Functions): 고급 분석의 시작

윈도우 함수는 SQL 쿼리에서 로우들의 집합(윈도우)에 대해 계산을 수행하지만, `GROUP BY`처럼 로우를 그룹화하여 단일 로우로 줄이지 않고, 각 로우에 대해 개별적으로 결과를 반환합니다. 이는 순위, 이동 평균, 누적 합계 등 복잡한 분석을 수행할 때 매우 유용합니다.

**개념:** `OVER` 절과 함께 사용되어 특정 범위(윈도우) 내의 로우들에 대해 집계 또는 분석 함수를 적용합니다. 결과는 각 로우에 대해 반환되며, 로우의 수는 변하지 않습니다.

> *   **`GROUP BY`와의 결정적 차이:**
>     *   **`GROUP BY`:** 로우들을 그룹으로 묶고, 각 그룹에 대해 하나의 요약된 로우를 반환합니다. 즉, **결과 로우의 수가 줄어듭니다.** (예: 부서별 평균 급여)
>     *   **윈도우 함수:** 로우들을 그룹(파티션)으로 나누어 계산을 수행하지만, **원본 로우의 수는 그대로 유지**하면서 각 로우에 계산된 값을 추가합니다. (예: 각 직원의 급여 옆에 해당 부서의 평균 급여를 표시)
> *   **왜 중요한가?**
>     *   **데이터의 맥락 유지:** `GROUP BY`는 데이터를 요약하면서 개별 로우의 상세 정보를 잃어버리지만, 윈도우 함수는 개별 로우의 맥락을 유지한 채 그룹 내에서의 상대적인 위치나 특성을 분석할 수 있게 합니다.
>     *   **복잡한 분석 간소화:** 순위, 누적 합계, 이동 평균, 전/후 로우 값 비교 등 `GROUP BY`나 `SELF JOIN`으로는 구현하기 어렵거나 매우 복잡했던 분석을 단일 쿼리로 간결하게 해결할 수 있습니다.
>     *   **성능 향상:** 많은 경우 상관 서브쿼리나 복잡한 `JOIN`보다 훨씬 효율적으로 동작하여 쿼리 성능을 향상시킵니다.
>
> 윈도우 함수를 능숙하게 다루는 것은 단순한 데이터 조회자를 넘어, 데이터의 숨겨진 패턴과 트렌드를 발견하고 비즈니스 인사이트를 도출하는 '시니어' 데이터 분석가로 성장하는 핵심 역량입니다.

**주요 활용 분야 및 실무 분석 시나리오:**
*   **순위 계산 (`RANK`, `DENSE_RANK`, `ROW_NUMBER`):**
    *   **시나리오:** "부서별로 급여를 가장 많이 받는 상위 3명의 직원을 찾아라."
    *   **활용:** `ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC)`를 사용하여 순위를 매긴 후, `WHERE` 절(또는 서브쿼리/CTE)에서 순위가 3 이하인 직원만 필터링합니다.
*   **그룹 내 비율 계산 (`SUM` over partition):**
    *   **시나리오:** "각 직원의 급여가 소속된 부서의 총 급여에서 차지하는 비중(%)은 얼마인가?"
    *   **활용:** `salary / SUM(salary) OVER (PARTITION BY department_id)`를 사용하여 부서 내 급여 비중을 계산합니다.
*   **누적 합계 계산 (`SUM` over order by):**
    *   **시나리오:** "일별 매출 데이터에서, 월별 누적 매출액의 추이를 보고 싶다."
    *   **활용:** `SUM(daily_sales) OVER (PARTITION BY month ORDER BY date)`를 사용하여 날짜 순으로 누적 매출을 계산합니다.
*   **시계열 데이터 분석 (`LAG`, `LEAD`):**
    *   **시나리오:** "전월 대비 매출 성장률(MoM Growth)을 계산하라."
    *   **활용:** `LAG(monthly_sales, 1, 0) OVER (ORDER BY month)`를 사용하여 전월 매출을 가져온 후, `(이번달 매출 - 전월 매출) / 전월 매출` 공식을 적용합니다.
*   **이동 평균 계산 (`AVG` over frame):**
    *   **시나리오:** "주식 가격 데이터의 7일 이동 평균을 계산하여 가격 변동성의 추세를 완만하게 보고 싶다."
    *   **활용:** `AVG(price) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`를 사용하여 이동 평균을 계산합니다.

> **윈도우 함수를 활용한 비즈니스 인사이트 도출:**
> 윈도우 함수는 단순한 데이터 조작을 넘어, 비즈니스 문제를 해결하고 의미 있는 인사이트를 도출하는 데 강력한 도구입니다. 각 활용 분야가 실제 비즈니스 시나리오에서 어떻게 적용되는지 이해하는 것이 중요합니다.
>
> *   **순위 계산:** 고객 등급 분류 (구매액 기준 상위 10%), 제품 판매 순위, 웹사이트 페이지뷰 순위 등 핵심 지표를 기반으로 한 순위 분석에 활용됩니다. 이를 통해 우수 고객, 인기 제품, 핵심 콘텐츠 등을 식별할 수 있습니다.
> *   **그룹 내 비율 계산:** 특정 부서의 예산 중 각 팀이 차지하는 비율, 전체 매출 중 특정 제품군이 차지하는 비율 등 부분과 전체의 관계를 파악하여 자원 배분이나 전략 수립에 기여합니다.
> *   **누적 합계 계산:** 월별/분기별 매출 목표 달성 현황, 캠페인 기간 동안의 누적 전환율, 사용자 유입 추이 등 시간 경과에 따른 누적 성과를 분석하여 추세 파악 및 예측에 활용됩니다.
> *   **시계열 데이터 분석:** 전일 대비 주가 변동, 전월 대비 사용자 이탈률, 특정 이벤트 발생 전후의 지표 변화 등 시간적 관계를 가진 데이터에서 변화율, 성장률, 패턴 등을 분석하여 비즈니스 의사결정의 근거를 마련합니다.
> *   **이동 평균 계산:** 주식 시장의 기술적 분석, 센서 데이터의 노이즈 제거, 트래픽 데이터의 추세선 파악 등 데이터의 단기적인 변동성을 완화하고 장기적인 추세를 파악하는 데 사용됩니다. 이는 예측 모델링의 전처리 단계에서도 중요하게 활용됩니다.
>
> 이처럼 윈도우 함수는 다양한 비즈니스 질문에 대한 답을 SQL만으로 효율적으로 찾아낼 수 있게 해주며, 데이터 분석가가 비즈니스 가치를 창출하는 데 핵심적인 역할을 합니다.

**예시:**

    RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS salary_rank_in_dept

## 3. `CASE` 문: 조건부 로직의 구현

`CASE` 문은 SQL 쿼리 내에서 조건부 로직을 구현할 때 사용합니다. 특정 조건에 따라 다른 값을 반환하거나, 데이터를 분류할 때 매우 유용합니다. 데이터 분석가가 데이터를 다양한 관점에서 분류하고 분석하는 데 필수적인 도구입니다.

> **`CASE` 문: 데이터에 비즈니스 규칙을 입히는 마법사:**
> `CASE` 문은 SQL 쿼리 내에서 조건부 로직을 구현하는 가장 강력하고 유연한 도구입니다. 데이터 분석가는 `CASE` 문을 통해 원본 데이터에 비즈니스 규칙을 적용하고, 데이터를 의미 있는 범주로 재분류하며, 복잡한 분석을 위한 전처리 작업을 수행할 수 있습니다.
>
> *   **활용 분야:**
>     *   **데이터 분류 및 세그먼테이션:** 고객의 구매액, 방문 횟수, 활동 기간 등에 따라 고객 등급(VIP, 일반, 휴면)을 나누거나, 상품을 인기 상품, 비인기 상품 등으로 분류할 때 사용합니다.
>     *   **지표 계산:** 특정 조건에 따라 다른 계산식을 적용하여 지표를 산출할 때 (예: 주말 매출과 주중 매출을 다르게 계산).
>     *   **데이터 정제 및 변환:** `NULL` 값이나 특정 오류 값을 다른 값으로 대체하거나, 코드화된 데이터를 사람이 이해하기 쉬운 텍스트로 변환할 때 유용합니다.
>     *   **보고서 및 대시보드:** 보고서에 필요한 특정 컬럼을 동적으로 생성하거나, 피벗 테이블 형태로 데이터를 재구성할 때 핵심적으로 사용됩니다.
>     *   **조건부 집계:** `COUNT(CASE WHEN ... THEN 1 END)`와 같이 집계 함수와 결합하여 특정 조건에 맞는 로우만 집계할 때 사용합니다. (자세한 내용은 [04_데이터_집계와_그룹화.md](./04_데이터_집계와_그룹화.md)의 조건부 집계 섹션 참조)
>
> *   **`IF` 함수와의 비교 (MySQL):**
>     MySQL에는 `IF(condition, value_if_true, value_if_false)`와 같은 간결한 조건 함수가 있지만, `CASE` 문은 여러 조건을 중첩하거나 복잡한 논리 연산을 포함할 수 있어 훨씬 유연하고 강력합니다. `IF` 함수는 간단한 이분법적 조건에 적합하며, `CASE` 문은 다중 조건 및 복합적인 비즈니스 로직에 더 적합합니다.
>
> `CASE` 문을 능숙하게 다루는 것은 데이터 분석가가 비즈니스 요구사항을 SQL 쿼리로 정확하게 구현하고, 데이터에서 새로운 가치를 창출하는 데 필수적인 역량입니다.

### 3.1. `CASE` 문의 기본: 단순 vs 검색

`CASE` 문은 크게 두 가지 형태로 나뉩니다.

#### 3.1.1. 단순 `CASE` (값 비교)

특정 컬럼의 값이 미리 정의된 값들과 일치하는지 비교할 때 사용합니다. `WHEN` 절에 비교할 값을 명시합니다.

특정 컬럼의 값이 미리 정의된 값들과 일치하는지 비교할 때 사용합니다. `WHEN` 절에 비교할 값을 명시합니다.

```sql
-- job_id에 따라 직무 등급 분류
SELECT
    first_name, job_id,
    CASE job_id
        WHEN 'DEV' THEN 'Developer'
        WHEN 'MGR' THEN 'Manager'
        WHEN 'HR' THEN 'Human Resources'
        ELSE 'Other'
    END AS job_category
FROM employees;
```

> **단순 `CASE`의 활용:**
> 단순 `CASE` 문은 특정 컬럼의 코드화된 값(Code Value)을 사람이 이해하기 쉬운 설명으로 변환하거나, 미리 정의된 카테고리로 분류할 때 매우 유용합니다.
>
> *   **코드 변환:** 데이터베이스에는 공간 효율성이나 일관성을 위해 `job_id`와 같이 축약된 코드로 저장되는 경우가 많습니다. 단순 `CASE`를 사용하면 이러한 코드를 보고서나 분석 결과에 필요한 'Developer', 'Manager'와 같은 전체 이름으로 쉽게 변환할 수 있습니다.
> *   **데이터 표준화:** 여러 시스템에서 가져온 데이터의 코드가 다를 경우, 단순 `CASE`를 사용하여 하나의 표준화된 값으로 통일할 수 있습니다.
> *   **가독성:** `IF` 함수(MySQL)나 복잡한 `OR` 조건 대신 단순 `CASE`를 사용하면 쿼리의 가독성이 훨씬 높아집니다.
> *   **`ELSE` 절의 중요성:** `CASE` 문에 `ELSE` 절을 명시하지 않으면, `WHEN` 조건에 해당하지 않는 모든 로우에 대해 `NULL`이 반환됩니다. 이는 의도치 않은 결과를 초래할 수 있으므로, `ELSE` 절을 사용하여 모든 경우를 명시적으로 처리하거나, `NULL`이 반환되는 것을 인지하고 있어야 합니다.

#### 3.1.2. 검색 `CASE` (조건 비교)

`WHEN` 절에 다양한 조건 표현식을 사용하여 더 복잡한 로직을 구현할 때 사용합니다. `IF-ELSE IF` 문과 유사합니다.

```sql
-- 급여 범위에 따라 급여 등급 분류
SELECT
    first_name, salary,
    CASE
        WHEN salary >= 70000 THEN 'A'
        WHEN salary >= 60000 THEN 'B'
        WHEN salary >= 50000 THEN 'C'
        ELSE 'D'
    END AS salary_grade
FROM employees;
```

> **검색 `CASE`의 유연성과 `WHEN` 절 순서의 중요성:**
> 검색 `CASE` 문은 `WHEN` 절에 다양한 조건 표현식을 사용할 수 있어, 단순 `CASE`보다 훨씬 유연하고 복잡한 비즈니스 로직을 구현할 수 있습니다.
>
> *   **유연한 조건:** `AND`, `OR`, `BETWEEN`, `LIKE` 등 다양한 연산자를 사용하여 복합적인 조건을 정의할 수 있습니다. 이는 데이터 분류, 세그먼테이션, 복잡한 지표 계산 등에 매우 강력합니다.
> *   **`WHEN` 절 순서의 중요성:** 검색 `CASE` 문은 `WHEN` 절의 조건을 **위에서부터 아래로 순차적으로 평가**합니다. 그리고 **가장 먼저 참(TRUE)이 되는 `WHEN` 절의 결과만 반환하고 나머지 `WHEN` 절은 평가하지 않습니다.** 이 특성 때문에 `WHEN` 절의 순서가 결과에 결정적인 영향을 미칠 수 있습니다.
>     ```sql
>     -- 예시: WHEN 절 순서에 따른 결과 차이
>     SELECT
>         salary,
>         CASE
>             WHEN salary >= 50000 THEN 'Middle'
>             WHEN salary >= 70000 THEN 'High' -- 이 조건은 salary >= 70000인 경우에도 'Middle'로 분류될 수 있음
>             ELSE 'Low'
>         END AS salary_category_bad_order
>     FROM employees;
>     ```
>     위 예시에서 `salary`가 70000 이상인 경우에도 첫 번째 `WHEN salary >= 50000` 조건이 먼저 참이 되므로 'Middle'로 분류될 수 있습니다. 따라서 **더 넓은 범위의 조건이나 더 일반적인 조건은 뒤에, 더 좁은 범위의 조건이나 더 특수한 조건은 앞에 배치**해야 합니다.
>     ```sql
>     -- 올바른 WHEN 절 순서
>     SELECT
>         salary,
>         CASE
>             WHEN salary >= 70000 THEN 'High'
>             WHEN salary >= 50000 THEN 'Middle'
>             ELSE 'Low'
>         END AS salary_category_good_order
>     FROM employees;
>     ```
> *   **`ELSE` 절의 중요성:** 단순 `CASE`와 마찬가지로, `ELSE` 절을 명시하지 않으면 `WHEN` 조건에 해당하지 않는 모든 로우에 대해 `NULL`이 반환됩니다. 의도치 않은 `NULL`을 방지하기 위해 항상 `ELSE` 절을 고려해야 합니다.
>
> 검색 `CASE` 문은 데이터 분석가가 비즈니스 로직을 SQL 쿼리에 직접 반영하는 데 필수적인 도구입니다. `WHEN` 절의 순서와 `ELSE` 절의 활용에 유의하여 정확하고 예측 가능한 쿼리를 작성하는 것이 중요합니다.

### 3.2. 중첩 `CASE`와 복합 조건: 복잡한 비즈니스 로직

`CASE` 문 안에 또 다른 `CASE` 문을 중첩하거나, `WHEN` 절에 `AND`, `OR` 등의 논리 연산자를 사용하여 복합적인 조건을 만들 수 있습니다.

```sql
-- 부서와 급여를 기준으로 복합적인 등급 분류
SELECT
    first_name, department_id, salary,
    CASE
        WHEN department_id = 1 THEN
            CASE
                WHEN salary >= 65000 THEN 'Dept1_High'
                ELSE 'Dept1_Low'
            END
        WHEN department_id = 2 AND salary >= 58000 THEN 'Dept2_High'
        WHEN department_id = 2 AND salary < 58000 THEN 'Dept2_Low'
        ELSE 'Other_Dept'
    END AS complex_grade
FROM employees;
```

> **중첩 `CASE`와 복합 조건의 활용 및 주의사항:**
> 중첩 `CASE` 문이나 `WHEN` 절에 복합 조건을 사용하는 것은 매우 복잡한 비즈니스 로직을 SQL 쿼리 내에서 구현할 수 있게 해줍니다. 이는 특히 데이터 분류, 세그먼테이션, 또는 특정 지표 계산 시 여러 기준을 동시에 고려해야 할 때 유용합니다.
>
> *   **활용 사례:**
>     *   **다차원 분류:** 고객을 지역, 연령대, 구매 패턴 등 여러 기준에 따라 세분화된 그룹으로 분류할 때.
>     *   **복잡한 규칙 기반 지표:** 특정 상품의 할인율을 고객 등급과 구매 시점에 따라 다르게 적용하여 최종 가격을 계산할 때.
>     *   **데이터 품질 검증:** 여러 컬럼의 조합이 특정 규칙을 위반하는지 검사하고, 위반 유형에 따라 다른 메시지를 반환할 때.
>
> *   **가독성 및 유지보수성 고려:**
>     *   **과도한 중첩 지양:** 중첩 `CASE` 문이 너무 깊어지거나 `WHEN` 절의 복합 조건이 지나치게 길어지면 쿼리의 가독성이 급격히 떨어지고 유지보수가 어려워집니다. 다른 개발자나 분석가가 쿼리를 이해하고 수정하는 데 많은 시간이 소요될 수 있습니다.
>     *   **주석 활용:** 복잡한 로직에는 반드시 상세한 주석을 달아 각 조건이 의미하는 바와 의도를 명확히 설명해야 합니다.
>     *   **`CTE` 또는 뷰 활용:** 복잡한 `CASE` 로직을 포함하는 쿼리가 자주 사용되거나, 여러 단계의 계산이 필요하다면, 해당 로직을 `CTE(Common Table Expression)`나 **뷰(View)**로 분리하여 쿼리의 복잡도를 낮추고 재사용성을 높이는 것을 고려해야 합니다. 이는 쿼리 전체의 가독성과 유지보수성을 크게 향상시킵니다.
>     *   **데이터 모델링 재고:** 만약 `CASE` 문이 너무 복잡해진다면, 데이터 모델 자체가 비즈니스 로직을 충분히 반영하지 못하고 있을 가능성도 있습니다. 이 경우 데이터 모델링을 재고하여 비즈니스 규칙을 데이터베이스 스키마에 더 잘 녹여내는 방법을 고민해볼 수 있습니다.
>
> 복잡한 `CASE` 문은 강력하지만, 그만큼 신중하게 설계하고 관리해야 합니다. 가독성과 유지보수성을 항상 염두에 두고, 필요한 경우 다른 SQL 기능이나 데이터 모델링 개선을 통해 쿼리를 최적화하는 것이 중요합니다.

### 3.3. `CASE` 문을 활용한 피벗 테이블: 데이터 재구성

`CASE` 문과 집계 함수를 함께 사용하여 로우 데이터를 컬럼 데이터로 변환하는 피벗(Pivot) 테이블을 만들 수 있습니다. 이는 특정 카테고리별로 데이터를 요약하여 보고서를 생성할 때 매우 유용합니다.

```sql
-- 부서별, 직무별 직원 수를 피벗 테이블 형태로 조회
SELECT
    d.department_name,
    COUNT(CASE WHEN e.job_id = 'DEV' THEN 1 END) AS Developers,
    COUNT(CASE WHEN e.job_id = 'MGR' THEN 1 END) AS Managers,
    COUNT(CASE WHEN e.job_id = 'HR' THEN 1 END) AS HR_Staff,
    COUNT(*) AS Total_Employees
FROM
    departments d
LEFT JOIN
    employees e ON d.department_id = e.department_id
GROUP BY
    d.department_name
ORDER BY
    d.department_name;
```

> **`CASE` 문을 활용한 피벗 테이블: 보고서 작성의 핵심:**
> 피벗(Pivot) 테이블은 로우(Row) 형태로 나열된 데이터를 컬럼(Column) 형태로 재구성하여, 특정 카테고리별로 데이터를 요약하고 비교 분석할 때 매우 유용합니다. `CASE` 문과 집계 함수를 결합하는 방식은 SQL에서 피벗 테이블을 구현하는 가장 일반적이고 강력한 방법입니다.
>
> *   **개념:**
>     *   **로우(Row) 데이터:** 각 이벤트나 개별 항목이 하나의 로우로 기록된 형태 (예: 각 직원의 `job_id`가 로우로 나열).
>     *   **피벗(Pivot) 테이블:** 특정 컬럼의 고유 값들이 새로운 컬럼으로 전환되고, 해당 컬럼에 대한 집계 값이 채워진 형태 (예: `job_id`의 'DEV', 'MGR', 'HR'이 각각 'Developers', 'Managers', 'HR_Staff' 컬럼으로 전환).
>
> *   **활용 사례:**
>     *   **보고서 생성:** 월별/분기별 매출 보고서에서 각 제품 카테고리별 매출을 컬럼으로 나열하여 한눈에 비교할 때.
>     *   **설문조사 분석:** 각 질문에 대한 응답 유형별(예: 매우 만족, 만족, 보통) 응답자 수를 컬럼으로 보여줄 때.
>     *   **성과 지표 비교:** 각 팀별로 남성 직원 수, 여성 직원 수, 신입 직원 수 등을 컬럼으로 나열하여 비교할 때.
>
> *   **성능 고려사항 및 대안:**
>     *   **대규모 데이터셋:** 피벗 테이블은 `GROUP BY`와 집계 함수를 사용하므로, 원본 데이터셋이 매우 클 경우 성능 저하가 발생할 수 있습니다. 특히 `COUNT(CASE WHEN ...)`와 같은 조건부 집계는 모든 로우를 스캔해야 하므로 인덱스를 효율적으로 사용하기 어렵습니다.
>     *   **컬럼 수의 고정:** `CASE` 문을 사용한 피벗 테이블은 미리 컬럼의 개수와 이름을 알아야 합니다. 즉, `job_id`의 종류가 동적으로 변하는 경우에는 쿼리를 수정해야 하는 단점이 있습니다.
>     *   **대안:**
>         *   **`EXPLAIN` 분석:** 항상 `EXPLAIN`을 통해 쿼리 실행 계획을 분석하고, 성능 병목 지점을 찾아 최적화합니다.
>         *   **요약 테이블:** 자주 사용되는 피벗 테이블 형태의 보고서라면, 배치 작업을 통해 미리 계산된 요약 테이블(Summary Table)을 생성하여 조회 성능을 극대화할 수 있습니다.
>         *   **BI 도구 활용:** Tableau, Power BI, Looker 등 BI(Business Intelligence) 도구는 데이터베이스에서 원본 데이터를 가져와 GUI 환경에서 유연하게 피벗 테이블을 생성하고 시각화하는 기능을 제공합니다. 복잡한 피벗 로직을 SQL에서 직접 구현하기보다 BI 도구의 기능을 활용하는 것이 더 효율적일 수 있습니다.
>         *   **DBMS별 `PIVOT` 함수:** 일부 DBMS(Oracle, SQL Server)는 `PIVOT` 함수를 직접 지원하여 `CASE` 문보다 더 간결하게 피벗 테이블을 생성할 수 있습니다. MySQL은 `PIVOT` 함수를 직접 지원하지 않습니다.
>
> `CASE` 문을 활용한 피벗 테이블은 데이터 분석가가 보고서와 대시보드를 통해 비즈니스 인사이트를 효과적으로 전달하는 데 필수적인 기술입니다. 성능과 유연성을 고려하여 적절한 구현 방식을 선택하는 것이 중요합니다.
