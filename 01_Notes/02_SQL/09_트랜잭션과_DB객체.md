## 1. 트랜잭션: 데이터 일관성과 무결성 보장

트랜잭션은 데이터베이스의 논리적인 작업 단위입니다. 여러 개의 SQL 문이 하나의 논리적인 작업으로 묶여 처리되며, 모든 작업이 성공적으로 완료되거나(COMMIT) 실패하면 모두 취소(ROLLBACK)되어 데이터의 일관성과 무결성을 보장합니다.

### 1.1. ACID 원칙: 트랜잭션의 기본

트랜잭션은 ACID라는 네 가지 속성을 만족해야 합니다.

#### 1.1.1. Atomicity (원자성): 모두 아니면 전무

트랜잭션 내의 모든 연산은 완전히 성공하거나, 아니면 완전히 실패하여 아무것도 적용되지 않아야 합니다. 부분적인 성공은 없습니다.

*   **예시:** 은행 계좌 이체 (A 계좌에서 출금, B 계좌로 입금)
    *   A에서 출금 성공, B에서 입금 실패 -> 전체 트랜잭션 실패, A 계좌 출금 취소
    *   A에서 출금 성공, B에서 입금 성공 -> 전체 트랜잭션 성공

#### 1.1.2. Consistency (일관성): 제약조건 유지

트랜잭션이 실행을 성공적으로 완료하면, 데이터베이스는 항상 일관된 상태를 유지해야 합니다. 모든 제약조건(PRIMARY KEY, FOREIGN KEY, NOT NULL 등)을 만족해야 합니다.

*   **예시:** 외래 키 제약조건이 있는 테이블에 유효하지 않은 외래 키 값을 삽입하려는 시도는 트랜잭션에 의해 거부되어 데이터 일관성을 유지합니다.

#### 1.1.3. Isolation (격리성): 동시성 제어

여러 트랜잭션이 동시에 실행될 때, 각 트랜잭션은 다른 트랜잭션의 영향을 받지 않고 독립적으로 실행되는 것처럼 보여야 합니다. 마치 순차적으로 실행되는 것처럼 동작합니다.

*   **예시:** 여러 사용자가 동시에 같은 계좌에서 돈을 인출하려 할 때, 각 인출 작업은 서로에게 영향을 주지 않고 독립적으로 처리되어야 합니다.

#### 1.1.4. Durability (영속성): 영구 저장

트랜잭션이 성공적으로 `COMMIT`되면, 해당 변경 사항은 시스템 오류(전원 손실 등)에도 불구하고 영구적으로 데이터베이스에 반영되어야 합니다.

*   **예시:** 계좌 이체가 `COMMIT`되면, 데이터베이스 서버가 다운되더라도 이체 결과는 유지되어야 합니다.

### 1.2. 격리 수준 (Isolation Levels): 동시성 제어

동시에 실행되는 트랜잭션 간의 데이터 가시성(Visibility)을 제어하여 데이터 일관성과 동시성 간의 균형을 맞춥니다. 격리 수준이 높을수록 데이터 일관성은 높아지지만, 동시성은 낮아져 성능 저하가 발생할 수 있습니다.

*   **`READ UNCOMMITTED`:**
    *   가장 낮은 격리 수준. 다른 트랜잭션이 `COMMIT`하지 않은 데이터(Dirty Read)도 읽을 수 있습니다.
    *   성능은 가장 좋지만, 데이터 일관성이 매우 낮아 거의 사용되지 않습니다.
*   **`READ COMMITTED`:**
    *   다른 트랜잭션이 `COMMIT`한 데이터만 읽을 수 있습니다. Dirty Read는 방지됩니다.
    *   하지만 한 트랜잭션 내에서 같은 쿼리를 두 번 실행했을 때 다른 결과가 나올 수 있습니다 (Non-Repeatable Read).
*   **`REPEATABLE READ`:**
    *   한 트랜잭션 내에서 같은 쿼리를 여러 번 실행해도 항상 동일한 결과를 보장합니다 (Non-Repeatable Read 방지).
    *   하지만 새로운 로우가 삽입되는 경우(Phantom Read)는 방지하지 못할 수 있습니다.
    *   MySQL의 기본 격리 수준입니다.
*   **`SERIALIZABLE`:**
    *   가장 높은 격리 수준. 모든 종류의 읽기 이상(Dirty Read, Non-Repeatable Read, Phantom Read)을 방지합니다.
    *   트랜잭션이 순차적으로 실행되는 것처럼 동작하여 데이터 일관성은 최고지만, 동시성이 가장 낮아 성능 저하가 가장 큽니다.

```sql
-- 현재 세션의 격리 수준 확인
SELECT @@transaction_isolation;

-- 격리 수준 설정 (예시: READ COMMITTED로 설정)
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 트랜잭션 시작
START TRANSACTION;

-- SQL 문 실행
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;

-- 변경 사항 확인 (필요시)
SELECT * FROM accounts WHERE account_id IN (1, 2);

-- 변경 사항 영구 반영
COMMIT;

-- 변경 사항 취소
-- ROLLBACK;
```

**MySQL `autocommit` 설정:**
MySQL은 기본적으로 `autocommit`이 활성화되어 있어, 각 SQL 문이 개별적인 트랜잭션으로 자동 커밋됩니다. 명시적으로 트랜잭션을 제어하려면 `START TRANSACTION`을 사용하거나, 세션 또는 연결 수준에서 `SET autocommit = 0;`으로 자동 커밋을 비활성화해야 합니다. 파이썬 `pymysql` 드라이버의 경우 `pymysql.connect(autocommit=False)` 옵션을 통해 연결 시점에 자동 커밋을 끌 수 있습니다.

### 1.3. 격리 수준 (Isolation Levels)과 동시성 문제 (데이터 부정합 방지)

데이터베이스에서 여러 트랜잭션이 동시에 실행될 때, 트랜잭션 간의 상호작용으로 인해 데이터의 일관성이 깨질 수 있습니다. 이를 **동시성 문제(Concurrency Problems)**라고 하며, SQL 표준은 이러한 문제를 방지하기 위한 네 가지 격리 수준(Isolation Levels)을 정의합니다. 격리 수준이 높을수록 데이터 일관성은 강화되지만, 동시성은 저하되어 성능에 영향을 미칠 수 있습니다.

**주요 동시성 문제:**

1.  **Dirty Read (더티 읽기):**
    *   **정의:** 한 트랜잭션이 아직 커밋되지 않은(변경 중인) 다른 트랜잭션의 데이터를 읽는 현상입니다. 만약 변경 중인 트랜잭션이 롤백되면, 읽었던 데이터는 유효하지 않은(더티한) 데이터가 됩니다.
    *   **발생 격리 수준:** `READ UNCOMMITTED`
    *   **해결 방안:** `READ COMMITTED` 이상의 격리 수준을 사용합니다.

2.  **Non-Repeatable Read (반복 불가능 읽기):**
    *   **정의:** 한 트랜잭션 내에서 같은 로우를 두 번 이상 읽을 때, 그 사이에 다른 트랜잭션이 해당 로우의 값을 변경하고 커밋하여, 처음 읽었던 값과 나중에 읽은 값이 달라지는 현상입니다.
    *   **발생 격리 수준:** `READ COMMITTED`
    *   **해결 방안:** `REPEATABLE READ` 이상의 격리 수준을 사용합니다.

3.  **Phantom Read (환영 읽기):**
    *   **정의:** 한 트랜잭션 내에서 특정 조건으로 로우 집합을 두 번 이상 쿼리할 때, 그 사이에 다른 트랜잭션이 해당 조건에 맞는 새로운 로우를 삽입하고 커밋하여, 처음 쿼리했던 결과 집합에는 없던 로우가 나중에 나타나는 현상입니다.
    *   **발생 격리 수준:** `REPEATABLE READ`
    *   **해결 방안:** `SERIALIZABLE` 격리 수준을 사용합니다. (MySQL의 `REPEATABLE READ`는 넥스트 키 락(Next-Key Lock)을 사용하여 Phantom Read를 방지합니다.)

**격리 수준별 동시성 문제 방지 여부:**

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
| :--- | :--- | :--- | :--- |
| `READ UNCOMMITTED` | 발생 | 발생 | 발생 |
| `READ COMMITTED` | 방지 | 발생 | 발생 |
| `REPEATABLE READ` | 방지 | 방지 | 발생 (MySQL은 방지) |
| `SERIALIZABLE` | 방지 | 방지 | 방지 |

**실무에서 격리 수준 선택 시 고려사항:**
*   **`READ COMMITTED`:** 대부분의 웹 애플리케이션에서 가장 많이 사용되는 격리 수준입니다. Dirty Read를 방지하면서도 `REPEATABLE READ`나 `SERIALIZABLE`보다 동시성이 높아 성능상 이점이 있습니다. 데이터 일관성보다 동시성이 더 중요한 경우에 적합합니다.
*   **`REPEATABLE READ`:** MySQL의 기본 격리 수준입니다. `Non-Repeatable Read`와 `Phantom Read`를 방지하여 강력한 일관성을 제공합니다. 복잡한 분석 쿼리나 배치 작업에서 데이터 일관성이 중요할 때 유용합니다.
*   **`SERIALIZABLE`:** 가장 강력한 일관성을 제공하지만, 동시성이 매우 낮아 성능 저하가 심합니다. 동시성 트랜잭션이 거의 없거나, 데이터의 완벽한 일관성이 절대적으로 요구되는 금융 거래와 같은 극히 제한적인 시나리오에서만 사용을 고려합니다.

**데이터 분석가의 역할:** 데이터 분석가는 쿼리 작성 시 현재 데이터베이스의 격리 수준을 이해하고, 분석 결과의 정확성과 신뢰성에 미치는 영향을 고려해야 합니다. 특히 시계열 데이터 분석이나 특정 시점의 스냅샷 분석 시에는 격리 수준이 분석 결과에 미치는 영향을 인지하고 있어야 합니다.

### 1.4. 교착상태 (Deadlock): 발생 원인과 해결 (동시성 제어의 난제)

> **현업 데이터 분석가의 관점 한 줄 요약:**
> 교착상태는 데이터베이스 동시성 제어의 복잡성을 보여주는 대표적인 사례입니다. 쿼리 성능 튜닝만큼이나 중요한 것이 트랜잭션 관리이며, 교착상태의 원인을 이해하고 이를 예방하거나 효율적으로 처리하는 전략은 안정적인 데이터 시스템 운영에 필수적입니다.

교착상태(Deadlock)는 두 개 이상의 트랜잭션이 서로가 점유하고 있는 리소스(로우, 테이블, 인덱스 등)를 얻기 위해 무한정 대기하는 상태를 말합니다. 데이터베이스 시스템은 교착상태를 감지하면 일반적으로 한 트랜잭션(희생자, victim)을 강제로 종료(Rollback)하여 다른 트랜잭션이 진행될 수 있도록 합니다. 교착상태는 동시성 제어에서 가장 복잡하고 해결하기 어려운 문제 중 하나입니다.

*   **발생 원인:**
    *   **상호 배제 (Mutual Exclusion):** 한 번에 하나의 트랜잭션만 리소스를 사용할 수 있음.
    *   **점유와 대기 (Hold and Wait):** 리소스를 점유한 상태에서 다른 리소스를 기다림.
    *   **비선점 (No Preemption):** 리소스를 강제로 뺏을 수 없음.
    *   **순환 대기 (Circular Wait):** 트랜잭션들이 서로 순환적으로 리소스를 기다림.
*   **해결 전략:**
    *   **트랜잭션 짧게 유지:** 트랜잭션의 길이를 최소화하여 리소스 점유 시간을 줄입니다.
    *   **일관된 리소스 접근 순서:** 모든 트랜잭션이 동일한 순서로 리소스에 접근하도록 규칙을 정합니다.
    *   **인덱스 활용:** 쿼리 성능을 최적화하여 잠금(Lock) 시간을 줄입니다.
    *   **`FOR UPDATE` / `FOR SHARE` 사용:** 명시적인 잠금을 사용하여 동시성 문제를 제어합니다.
    *   **교착상태 재시도 로직:** 애플리케이션 레벨에서 교착상태 발생 시 트랜잭션을 재시도하는 로직을 구현합니다.


## 2. 뷰(View) 활용: 가상 테이블을 통한 데이터 추상화 (데이터 접근의 유연성 및 보안)

뷰(View)는 하나 이상의 테이블이나 다른 뷰를 기반으로 생성되는 **가상 테이블**입니다. 뷰 자체는 데이터를 물리적으로 저장하지 않고, 뷰가 정의된 `SELECT` 문을 실행할 때마다 원본 테이블에서 데이터를 가져옵니다. 데이터 분석가에게 뷰는 복잡한 쿼리를 단순화하고, 특정 목적에 맞는 데이터셋을 제공하며, 데이터 접근을 제어하는 데 매우 유용합니다.

### 2.1. 뷰의 개념과 필요성

*   **개념:** 뷰는 데이터베이스 객체 중 하나로, 미리 정의된 쿼리 결과를 테이블처럼 사용할 수 있게 합니다. 사용자는 뷰를 통해 원본 테이블의 특정 부분만 보거나, 여러 테이블이 `JOIN`된 결과를 하나의 테이블처럼 조회할 수 있습니다.
*   **필요성:**
    *   **쿼리 단순화 및 재사용성:** 복잡하고 긴 `JOIN`이나 서브쿼리를 포함하는 쿼리를 뷰로 정의해두면, 사용자는 뷰를 단순한 테이블처럼 조회할 수 있어 쿼리 작성이 훨씬 쉬워지고, 동일한 복잡한 쿼리를 반복해서 작성할 필요가 없어집니다.
    *   **보안 강화:** 특정 컬럼이나 로우만 노출하는 뷰를 생성하여 사용자에게 필요한 데이터만 보여주고, 민감한 정보(예: 급여, 주민등록번호)에 대한 직접적인 접근을 제한할 수 있습니다. 이는 데이터 보안 및 규제 준수에 필수적입니다.
    *   **데이터 일관성 및 추상화:** 여러 사용자가 동일한 뷰를 사용함으로써 일관된 데이터 뷰를 제공합니다. 또한, 기본 테이블 구조가 변경되더라도 뷰만 수정하면 되므로, 뷰를 사용하는 애플리케이션 코드 변경을 최소화할 수 있습니다.
    *   **데이터 분석 편의성:** 분석가에게 특정 분석 목적에 맞게 정제되거나 집계된 형태의 데이터를 뷰로 제공하여, 분석 효율성을 높일 수 있습니다.

### 2.2. 뷰 생성, 수정, 삭제 (`CREATE VIEW`, `ALTER VIEW`, `DROP VIEW`)

```sql
-- 뷰 생성 예시: 고소득 직원 뷰
CREATE VIEW HighSalaryEmployeesView AS
SELECT employee_id, first_name, last_name, salary, department_id
FROM employees
WHERE salary >= 70000;

-- 뷰 조회 (일반 테이블처럼 사용)
SELECT * FROM HighSalaryEmployeesView;

-- 뷰 수정 예시: 급여 기준 변경
ALTER VIEW HighSalaryEmployeesView AS
SELECT employee_id, first_name, last_name, salary, department_id
FROM employees
WHERE salary >= 75000;

-- 뷰 삭제 예시
DROP VIEW HighSalaryEmployeesView;
```

### 2.3. 뷰의 장점과 단점 (실무적 고려사항)

*   **장점:**
    *   **단순성:** 복잡한 쿼리를 숨겨 사용자에게 단순한 인터페이스를 제공합니다.
    *   **보안:** 특정 사용자에게 필요한 데이터만 보여주고, 기본 테이블에 대한 직접적인 접근을 제한합니다.
    *   **유연성:** 기본 테이블 구조가 변경되어도 뷰만 수정하면 되므로, 애플리케이션 코드 변경을 최소화할 수 있습니다.
    *   **재사용성:** 한 번 정의된 뷰는 여러 쿼리나 애플리케이션에서 재사용될 수 있습니다.
*   **단점 및 성능 고려사항:**
    뷰는 편리하지만, 성능상 주의해야 할 점이 있습니다. 뷰는 가상 테이블이므로, 뷰를 조회할 때마다 뷰 정의에 포함된 원본 쿼리가 실행됩니다. 이는 특히 복잡한 뷰나 여러 뷰가 중첩된 경우 성능 저하를 유발할 수 있습니다.

    *   **성능 저하 가능성:**
        *   **쿼리 재실행:** 뷰를 조회할 때마다 뷰 정의 쿼리가 매번 실행되므로, 원본 쿼리가 복잡하거나 대량의 데이터를 처리한다면 성능 오버헤드가 발생합니다.
        *   **옵티마이저의 한계:** 복잡한 뷰는 데이터베이스 옵티마이저가 최적의 실행 계획을 수립하는 데 어려움을 겪을 수 있습니다. 이로 인해 비효율적인 쿼리 실행이 발생할 수 있습니다.
        *   **인덱스 활용의 어려움:** 뷰 자체에는 인덱스를 생성할 수 없으며, 원본 테이블의 인덱스를 활용해야 합니다. 뷰 정의 쿼리가 인덱스를 효율적으로 사용하지 못하면 성능이 저하됩니다.
    *   **업데이트 제한:** 특정 조건(예: `JOIN`을 포함하는 뷰, 집계 함수를 포함하는 뷰, `DISTINCT`를 포함하는 뷰)에서는 뷰를 통해 데이터를 `INSERT`, `UPDATE`, `DELETE`할 수 없습니다. 이는 뷰가 원본 테이블의 로우와 1:1로 매핑되지 않기 때문입니다.

*   **Materialized View (구체화된 뷰)와의 비교:**
    일부 DBMS(PostgreSQL, Oracle, SQL Server 등)에서는 **Materialized View (구체화된 뷰)**를 지원합니다. Materialized View는 뷰의 쿼리 결과를 물리적으로 저장해두는 테이블과 유사한 객체입니다. 따라서 조회 시 원본 쿼리를 재실행할 필요 없이 저장된 데이터를 바로 읽어오므로, 복잡한 집계나 `JOIN`이 포함된 뷰의 성능을 획기적으로 향상시킬 수 있습니다. MySQL은 Materialized View를 직접 지원하지 않으므로, 요약 테이블(Summary Table) 전략을 통해 유사한 효과를 얻을 수 있습니다.

### 2.4. 실무 활용 사례 (보고서용 뷰, 보안 뷰, 분석 편의성)

*   **보고서용 뷰:** 특정 보고서나 대시보드에서 자주 사용되는 복잡한 집계 쿼리나 `JOIN` 쿼리를 뷰로 정의하여, 보고서 생성 시 뷰만 조회하도록 합니다. (예: 월별 매출 요약 뷰, 부서별 성과 지표 뷰, 고객 세그먼트별 구매 행동 뷰)
*   **보안 뷰:** 민감한 정보(예: 주민등록번호, 개인 연락처, 급여)가 포함된 테이블에서 특정 컬럼을 제외하거나, 특정 조건에 맞는 로우만 보여주는 뷰를 생성하여 일반 사용자에게 제공합니다. 이를 통해 데이터 접근 권한을 세밀하게 제어하고 데이터 유출 위험을 줄일 수 있습니다.
*   **분석가를 위한 뷰 활용법 (나만의 쿼리 바로가기):**
    데이터 분석가는 매번 복잡한 `JOIN`과 `WHERE` 조건을 반복해서 작성하는 경우가 많습니다. 이때 뷰를 **"자주 사용하는 복잡한 쿼리를 저장해두는 나만의 바로가기"**처럼 활용할 수 있습니다. 
    *   **예시:** 사용자 정보, 주문 정보, 상품 정보를 `JOIN`하고, 특정 기간과 조건을 필터링한 결과를 `my_analysis_view`라는 뷰로 생성해 둡니다.
    *   **효과:** 이후 분석 작업에서는 `SELECT * FROM my_analysis_view` 한 줄만으로 필요한 데이터셋을 즉시 가져올 수 있습니다. 이는 BI 도구(태블로, Power BI 등)에 데이터를 연결하거나, Python/R 코드에서 데이터를 불러올 때 매우 편리하며, 반복적인 작업을 줄여 분석의 본질에 더 집중할 수 있게 해줍니다.

**실무적 조언:**
뷰는 데이터베이스의 강력한 기능이지만, 성능과 관리의 복잡성을 항상 고려해야 합니다. 특히 대규모 데이터 환경에서는 뷰의 성능을 `EXPLAIN`으로 주기적으로 확인하고, 필요에 따라 Materialized View(또는 요약 테이블)로의 전환을 고려하는 것이 중요합니다.

## 3. 사용자 정의 함수 (UDF) 및 저장 프로시저 (Stored Procedure): 재사용 가능한 로직 캡슐화

데이터베이스 내에서 재사용 가능한 로직을 캡슐화하는 방법은 크게 사용자 정의 함수(UDF)와 저장 프로시저(Stored Procedure)로 나눌 수 있습니다. 이들은 복잡한 비즈니스 로직을 데이터베이스 레벨에서 처리하고, 코드의 재사용성 및 유지보수성을 높이는 데 유용합니다.

**사용자 정의 함수(UDF)와 저장 프로시저(Stored Procedure)의 주요 차이점 (실무적 선택 가이드):**
| 구분 | 사용자 정의 함수 (UDF) | 저장 프로시저 (Stored Procedure) |
| :--- | :--- | :--- |
| **반환 값** | 항상 단일 값을 반환 (필수) | 값을 반환할 수도 있고(OUT 매개변수), 반환하지 않을 수도 있음 |
| **SQL 문 허용** | `SELECT` 문만 허용 (데이터 변경 불가, DML/DDL 사용 불가) | `SELECT`, `INSERT`, `UPDATE`, `DELETE` 등 모든 DML 및 DDL 문 허용 |
| **호출 방식** | SQL 쿼리 내에서 표현식처럼 사용 (`SELECT my_function(...)`, `WHERE my_function(...) > 0`) | `CALL` 문을 사용하여 호출 (`CALL my_procedure(...)`) |
| **트랜잭션** | 트랜잭션 제어 불가 (호출하는 쿼리의 트랜잭션에 포함되어 독립적인 COMMIT/ROLLBACK 불가) | 트랜잭션 제어 가능 (`START TRANSACTION`, `COMMIT`, `ROLLBACK` 등 트랜잭션 제어 구문 사용 가능) |
| **주요 용도** | 값 계산, 데이터 변환, 복잡한 수식 처리, 데이터 정제 | 복잡한 비즈니스 로직 구현, 배치 작업, 데이터 관리 작업, 여러 단계의 작업 처리 |
| **성능 고려** | 쿼리 내에서 로우별로 실행될 수 있어 대량 데이터 처리 시 성능 저하 가능성. 인덱스 활용 어려움. | 복잡한 로직을 한 번에 처리하여 네트워크 오버헤드 감소. 미리 컴파일되어 성능 이점. |

일반적으로 데이터를 조회하고 계산하는 용도에는 UDF가 적합하며, 데이터를 변경하거나 여러 단계를 거치는 복잡한 작업을 수행할 때는 저장 프로시저가 더 적합합니다. 실무에서는 이 둘의 차이점을 명확히 이해하고 적절히 활용하는 것이 중요합니다.

### 3.1 저장 프로시저 (Stored Procedure): 비즈니스 로직 캡슐화

저장 프로시저는 일련의 SQL 문을 미리 컴파일하여 데이터베이스에 저장해 둔 객체입니다. 복잡한 비즈니스 로직, 여러 SQL 문의 조합, 트랜잭션 처리 등에 사용됩니다. 값을 반환할 수도 있고, 반환하지 않을 수도 있습니다.

#### 3.1.1 기본 저장 프로시저: 매개변수 활용

```sql
DELIMITER //

CREATE PROCEDURE GetEmployeesInDepartment (IN dept_id INT)
BEGIN
    SELECT employee_id, first_name, last_name, salary
    FROM employees
    WHERE department_id = dept_id;
END //

DELIMITER ;

-- 프로시저 호출 예시
CALL GetEmployeesInDepartment(1);
```

#### 3.1.2. 복잡한 비즈니스 로직 프로시저: 성과 평가 및 보상

```sql
DELIMITER //

CREATE PROCEDURE ProcessEmployeePerformance (IN emp_id INT, IN performance_score DECIMAL(3, 2))
BEGIN
    DECLARE current_salary DECIMAL(10, 2);
    DECLARE new_salary DECIMAL(10, 2);
    DECLARE salary_increase_rate DECIMAL(3, 2);

    -- 현재 급여 조회
    SELECT salary INTO current_salary FROM employees WHERE employee_id = emp_id;

    -- 성과 점수에 따른 급여 인상률 결정
    IF performance_score >= 0.9 THEN
        SET salary_increase_rate = 0.10; -- 10% 인상
    ELSEIF performance_score >= 0.7 THEN
        SET salary_increase_rate = 0.05; -- 5% 인상
    ELSE
        SET salary_increase_rate = 0.00; -- 인상 없음
    END IF;

    -- 새로운 급여 계산 및 업데이트
    SET new_salary = current_salary * (1 + salary_increase_rate);
    UPDATE employees SET salary = new_salary WHERE employee_id = emp_id;

    -- 로그 기록 (예시)
    INSERT INTO audit_log (log_message) VALUES (CONCAT('Employee ', emp_id, ' salary updated from ', current_salary, ' to ', new_salary));

    SELECT CONCAT('Employee ', emp_id, ' salary updated to ', new_salary) AS Result;
END //

DELIMITER ;

-- 프로시저 호출 예시
CALL ProcessEmployeePerformance(1, 0.95);
```

### 3.2. 사용자 정의 함수 (UDF): 재사용 가능한 로직

UDF는 SQL 쿼리 내에서 호출되어 값을 반환하는 함수입니다. 주로 계산이나 데이터 변환 등 특정 값을 반환하는 로직에 사용됩니다.

#### 3.2.1. 함수 생성 기초: 간단한 함수 만들기

```sql
DELIMITER //

CREATE FUNCTION GetEmployeeFullName (emp_id INT)
RETURNS VARCHAR(100)
READS SQL DATA
BEGIN
    DECLARE full_name VARCHAR(100);
    SELECT CONCAT(first_name, ' ', last_name) INTO full_name
    FROM employees
    WHERE employee_id = emp_id;
    RETURN full_name;
END //

DELIMITER ;

-- 함수 생성 시 DELIMITER를 사용하는 이유:
-- MySQL 클라이언트는 기본적으로 세미콜론(;)을 쿼리의 끝으로 인식합니다. 
-- 함수나 프로시저 정의 내부에는 여러 개의 세미콜론이 포함될 수 있으므로, 
-- DELIMITER 명령어를 사용하여 임시로 구분자를 변경하여 MySQL 클라이언트가 
-- 전체 함수 정의를 하나의 명령문으로 인식하도록 합니다. 
-- 함수 정의가 끝나면 다시 DELIMITER ; 로 원래 구분자로 되돌립니다.

-- 함수 사용 예시
SELECT GetEmployeeFullName(1) AS EmployeeName;
```

#### 3.2.2. 복잡한 비즈니스 로직 함수: 종합 평가 함수

```sql
DELIMITER //

CREATE FUNCTION CalculateEmployeeBonus (emp_id INT)
RETURNS DECIMAL(10, 2)
READS SQL DATA
BEGIN
    DECLARE emp_salary DECIMAL(10, 2);
    DECLARE bonus DECIMAL(10, 2);

    SELECT salary INTO emp_salary FROM employees WHERE employee_id = emp_id;

    IF emp_salary >= 70000 THEN
        SET bonus = emp_salary * 0.15;
    ELSEIF emp_salary >= 50000 THEN
        SET bonus = emp_salary * 0.10;
    ELSE
        SET bonus = emp_salary * 0.05;
    END IF;

    RETURN bonus;
END //

DELIMITER ;

-- 함수 사용 예시
SELECT employee_id, first_name, salary, CalculateEmployeeBonus(employee_id) AS bonus_amount
FROM employees;
```

## 4. 트리거 (Trigger): 데이터 변경 자동화 (신중한 사용 필요)

트리거는 특정 테이블에서 `INSERT`, `UPDATE`, `DELETE`와 같은 이벤트가 발생할 때 자동으로 실행되는 특별한 종류의 저장 프로시저입니다. 데이터 무결성 유지, 자동 로깅, 복잡한 비즈니스 규칙 강제 등에 사용될 수 있습니다.

**트리거의 장점과 단점 (실무적 고려사항 및 강력한 경고):**

*   **장점:**
    *   **데이터 무결성 강화:** 애플리케이션 로직과 관계없이 데이터베이스 레벨에서 비즈니스 규칙을 강제하여 데이터 일관성을 보장합니다. 모든 데이터 변경 경로에 대해 일관된 규칙을 적용할 수 있습니다.
    *   **자동화:** 특정 이벤트 발생 시 자동으로 작업을 수행하여 수동 개입을 줄이고, 애플리케이션 코드에서 반복적인 로직을 제거할 수 있습니다.

*   **단점 및 위험성 (매우 중요!):**
    *   **디버깅의 어려움 (가장 큰 문제):** 트리거는 암묵적으로, 눈에 보이지 않게 실행됩니다. 이로 인해 데이터 변경 시 예상치 못한 동작이나 오류가 발생했을 때, 그 원인이 트리거 때문이라는 것을 파악하기가 매우 어렵습니다. 이는 심각한 장애로 이어질 수 있으며, 문제 해결에 많은 시간과 노력을 소모하게 합니다.
    *   **성능 저하:** `INSERT`, `UPDATE`, `DELETE` 문이 실행될 때마다 트리거 로직이 추가로 실행되므로, 복잡한 트리거는 데이터 변경 작업의 성능에 직접적인 영향을 미칩니다. 특히 대량의 데이터 변경 작업 시 심각한 병목 현상을 유발할 수 있습니다.
    *   **복잡한 종속성:** 여러 트리거가 서로 얽혀 있거나, 트리거가 다른 테이블에 영향을 주는 경우, 시스템 전체의 종속성이 복잡해져 유지보수가 극도로 어려워집니다. 트리거 간의 실행 순서나 상호작용을 예측하기 어렵습니다.
    *   **예측 불가능성:** 개발자나 분석가가 트리거의 존재를 인지하지 못하고 작업할 경우, 의도하지 않은 데이터 변경이 발생하여 데이터 정합성을 깨뜨리거나, 예상치 못한 결과를 초래할 수 있습니다.
    *   **테스트의 어려움:** 트리거는 데이터베이스 내부에서 동작하므로, 단위 테스트나 통합 테스트를 수행하기가 까다롭습니다.

**실무 가이드라인:**
**트리거는 강력한 기능이지만, 위와 같은 심각한 단점 때문에 실무에서는 사용을 최소화하거나 피하는 것이 좋습니다.** 특히 복잡한 비즈니스 로직을 트리거로 구현하는 것은 매우 위험합니다. 데이터 로깅이나 간단한 값 업데이트와 같이 매우 제한적이고 명확한 용도로만 신중하게 사용해야 합니다. 대부분의 비즈니스 로직은 애플리케이션 레벨에서 구현하는 것이 디버깅, 테스트, 유지보수 측면에서 훨씬 유리합니다.

**대안:**
*   **저장 프로시저 (Stored Procedure):** 데이터 변경 로직을 명시적인 저장 프로시저로 만들고, 애플리케이션에서 이 프로시저를 호출하도록 설계하는 것이 훨씬 안전하고 관리하기 좋습니다. 프로시저는 명시적으로 호출되므로 동작을 예측하기 쉽습니다.
*   **애플리케이션 레벨 로직:** 대부분의 비즈니스 규칙은 애플리케이션 코드 내에서 처리하는 것이 디버깅과 유지보수 측면에서 더 유리합니다. 애플리케이션은 비즈니스 로직을 구현하기 위한 더 풍부한 도구와 프레임워크를 제공합니다.
*   **데이터베이스 제약조건:** 간단한 데이터 무결성 규칙(예: NOT NULL, UNIQUE, CHECK, FOREIGN KEY)은 데이터베이스 제약조건을 사용하여 구현하는 것이 가장 효율적이고 안전합니다.

## 5. 데이터베이스 스냅샷 (Snapshot): 특정 시점의 데이터 보존 및 분석 (데이터 복구 및 감사)

데이터베이스 스냅샷은 특정 시점의 데이터베이스 상태를 읽기 전용으로 보존하는 기능입니다. 이는 주로 데이터 복구, 보고서 생성, 감사, 또는 특정 시점의 데이터 분석을 위해 사용됩니다. MySQL 자체는 SQL Server나 Oracle처럼 내장된 '데이터베이스 스냅샷' 기능을 직접 제공하지 않지만, 유사한 목적을 달성하기 위한 여러 방법이 있습니다.

**MySQL에서 스냅샷과 유사한 목적을 달성하는 방법:**

1.  **`mysqldump`를 이용한 논리적 백업:**
    가장 일반적인 방법으로, 특정 시점의 데이터베이스 스키마와 데이터를 SQL 파일로 덤프(dump)하는 것입니다. 이는 논리적 백업이며, 이 파일을 사용하여 다른 시점에 데이터베이스를 복원하거나 분석할 수 있습니다.
    ```bash
    # 특정 데이터베이스의 스냅샷 생성
    mysqldump -u [username] -p [database_name] > [database_name]_snapshot_YYYYMMDD.sql

    # 특정 테이블의 스냅샷 생성
    mysqldump -u [username] -p [database_name] [table_name] > [table_name]_snapshot_YYYYMMDD.sql
    ```
    **장점:** 사용하기 쉽고, 다른 MySQL 버전이나 서버로 이식하기 용이합니다. 특정 테이블이나 데이터만 선택적으로 백업/복원하기 용이합니다.
    **단점:** 대규모 데이터베이스의 경우 덤프 및 복원 시간이 오래 걸릴 수 있습니다. 덤프 시점의 데이터 일관성을 보장하기 위해 `--single-transaction` 옵션을 사용하는 것이 좋습니다.

2.  **파일 시스템 스냅샷 (LVM, ZFS 등):**
    운영체제 레벨에서 파일 시스템 스냅샷 기능을 활용하는 방법입니다. LVM(Logical Volume Manager)이나 ZFS와 같은 파일 시스템은 특정 시점의 볼륨 스냅샷을 생성할 수 있습니다. MySQL 데이터 파일이 저장된 볼륨의 스냅샷을 찍으면, 해당 시점의 데이터베이스 상태를 그대로 보존할 수 있습니다.
    **장점:** 매우 빠르고, 데이터베이스 크기에 관계없이 일관된 스냅샷을 생성할 수 있습니다. 데이터베이스 서버의 부하가 적습니다.
    **단점:** 파일 시스템 수준의 기능이므로, 데이터베이스가 일관된 상태(예: 모든 트랜잭션이 커밋된 상태)에서 스냅샷을 찍어야 합니다. MySQL 서버를 잠시 멈추거나(FLUSH TABLES WITH READ LOCK) `XtraBackup`과 같은 도구를 사용하여 일관성을 보장해야 합니다.

3.  **복제(Replication) 슬레이브 활용:**
    MySQL 복제 환경에서 슬레이브 서버를 사용하여 특정 시점의 데이터를 보존할 수 있습니다. 슬레이브 서버의 복제를 잠시 중단하고, 해당 시점의 데이터를 분석하거나 백업하는 용도로 활용할 수 있습니다.
    **장점:** 운영 중인 마스터 서버에 부하를 주지 않고 스냅샷을 얻을 수 있습니다. 재해 복구 시에도 활용될 수 있습니다.
    **단점:** 복제 환경 구축 및 관리가 필요하며, 슬레이브 서버의 자원 소모가 발생합니다.

4.  **데이터 웨어하우스/분석 플랫폼의 스냅샷 기능:**
    클라우드 기반의 데이터 웨어하우스(예: Amazon Redshift, Google BigQuery, Snowflake)는 자체적으로 스냅샷 또는 타임 트래블(Time Travel) 기능을 제공하여 특정 시점의 데이터를 쉽게 조회하고 복원할 수 있습니다. 데이터 분석 목적으로는 이러한 플랫폼의 기능을 활용하는 것이 가장 편리하고 효율적입니다.
    **장점:** 관리 용이성, 뛰어난 확장성, 특정 시점 데이터 조회 및 복원 기능 내장.
    **단점:** 비용 발생, 특정 플랫폼에 종속적.

**데이터 분석 실무에서의 활용:**
*   **시점별 데이터 분석:** 특정 이벤트(예: 마케팅 캠페인 시작 전후, 시스템 업데이트 전후)에 따른 데이터 변화를 분석하기 위해 스냅샷을 생성하고 비교 분석합니다. 이는 A/B 테스트 결과 분석이나 트렌드 변화 분석에 유용합니다.
*   **보고서 생성:** 월말, 분기말 등 특정 시점의 데이터를 기반으로 보고서를 생성해야 할 때 스냅샷을 활용하여 데이터 일관성을 보장합니다. 특히 장기적인 추세 분석이나 과거 데이터와의 비교에 필수적입니다.
*   **모델 학습/테스트:** 특정 시점의 데이터를 고정하여 머신러닝 모델을 학습시키거나 테스트하는 데 사용합니다. 데이터의 재현성을 보장하여 모델 개발의 신뢰도를 높입니다.
*   **감사 및 규제 준수:** 데이터 변경 이력을 추적하거나 규제 준수를 위해 특정 시점의 데이터 상태를 보존해야 할 때 유용합니다. 법적 요구사항에 따라 특정 기간 동안 데이터를 보존해야 하는 경우 스냅샷이 중요한 역할을 합니다.
