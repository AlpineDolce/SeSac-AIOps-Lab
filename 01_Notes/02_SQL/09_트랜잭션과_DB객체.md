## 1. 트랜잭션 (Transaction)

트랜잭션(Transaction)은 데이터베이스의 상태를 변화시키기 위해 수행하는 작업의 논리적인 단위를 의미합니다. 여러 개의 SQL 문이 하나의 논리적인 작업으로 묶여 처리될 때, 이 작업 전체가 성공적으로 완료되거나, 아니면 모두 실패하여 원래 상태로 되돌려져야 데이터의 일관성과 무결성이 보장됩니다.

### 1.1. 트랜잭션의 개념과 필요성

*   **개념:** 데이터베이스의 상태를 변화시키는 하나 이상의 SQL 문(DML)을 하나의 논리적인 작업 단위로 묶은 것입니다. 이는 데이터베이스의 일관된 상태를 유지하기 위한 필수적인 메커니즘입니다.
*   **필요성:**
    *   **데이터 일관성 유지:** 데이터베이스 내의 데이터가 항상 정확하고 유효한 상태를 유지하도록 합니다. 특히 여러 작업이 동시에 수행되거나 시스템 장애가 발생할 경우 데이터 손상을 방지합니다.
    *   **데이터 무결성 보장:** 데이터의 정확성, 일관성, 유효성을 보장하여 데이터 손상이나 오류를 방지합니다. 이는 데이터베이스의 제약조건(PRIMARY KEY, FOREIGN KEY, CHECK 등)과 함께 작동하여 데이터의 신뢰성을 높입니다.
    *   **동시성 제어:** 여러 사용자가 동시에 데이터에 접근할 때 발생할 수 있는 문제(예: 갱신 손실, 비반복 읽기, 유령 읽기)를 방지하고 데이터의 신뢰성을 확보합니다. 트랜잭션은 각 사용자가 독립적으로 데이터에 접근하는 것처럼 보이게 합니다.

**실무적 관점:** 트랜잭션은 데이터베이스를 사용하는 모든 애플리케이션에서 데이터의 신뢰성을 확보하는 가장 기본적인 메커니즘입니다. 특히 금융 거래, 재고 관리, 주문 처리 등 데이터의 정확성이 생명인 시스템에서는 트랜잭션 관리가 필수적입니다. 개발자는 비즈니스 로직에 따라 트랜잭션의 시작과 끝을 명확히 정의하고, 오류 발생 시 롤백 처리를 통해 데이터 일관성을 유지해야 합니다.

### 1.2. ACID 속성: 트랜잭션의 견고한 기반

모든 트랜잭션은 다음 네 가지 속성을 만족해야 합니다. 이 속성들은 트랜잭션이 안전하게 수행됨을 보장하며, 데이터베이스 시스템의 신뢰성을 결정하는 핵심 요소입니다.

*   **원자성 (Atomicity):**
    *   **정의:** 트랜잭션 내의 모든 작업은 완전히 성공하거나, 아니면 모두 실패하여 원래 상태로 되돌려져야 합니다. (All or Nothing)
    *   **예시:** 은행 계좌 이체 시, A 계좌에서 돈을 인출하고 B 계좌에 돈을 입금하는 두 작업은 하나의 원자적인 단위입니다. 만약 인출은 성공했지만 입금이 실패하면, 전체 트랜잭션은 실패로 간주되어 인출된 돈도 다시 A 계좌로 복구되어야 합니다.
    *   **구현:** `COMMIT` (모든 변경 사항 반영) 또는 `ROLLBACK` (모든 변경 사항 취소) 명령어를 통해 보장됩니다.

*   **일관성 (Consistency):**
    *   **정의:** 트랜잭션이 성공적으로 완료되면 데이터베이스는 항상 일관된 상태를 유지해야 합니다. 트랜잭션은 데이터베이스의 제약조건(PRIMARY KEY, FOREIGN KEY, CHECK 등), 트리거, 비즈니스 규칙 등을 위반해서는 안 됩니다.
    *   **예시:** 계좌 이체 트랜잭션 전후에 전체 계좌 잔액의 합은 항상 동일해야 합니다. 트랜잭션이 완료된 후에도 데이터베이스 스키마, 도메인, 무결성 제약 조건 등이 유효하게 유지되어야 합니다.
    *   **구현:** DBMS의 제약조건 관리, 트리거, 그리고 애플리케이션 레벨의 비즈니스 로직을 통해 보장됩니다.

*   **고립성 (Isolation):**
    *   **정의:** 여러 트랜잭션이 동시에 실행될 때, 각 트랜잭션은 다른 트랜잭션의 영향을 받지 않고 독립적으로 실행되는 것처럼 보여야 합니다. 즉, 동시성 문제를 방지합니다.
    *   **예시:** 여러 사용자가 동시에 동일한 상품의 재고를 조회하고 구매하려 할 때, 각 사용자는 다른 사용자의 구매 작업이 완료되기 전까지는 재고 수량의 중간 변경 상태를 보지 않아야 합니다.
    *   **구현:** 잠금(Locking), 다중 버전 동시성 제어(MVCC, Multi-Version Concurrency Control) 등의 메커니즘을 통해 구현되며, 트랜잭션 격리 수준에 따라 보장되는 정도가 달라집니다.

*   **영속성 (Durability):**
    *   **정의:** 트랜잭션이 성공적으로 완료(COMMIT)되면, 그 결과는 시스템 오류(예: 서버 다운, 전원 손실)에도 불구하고 영구적으로 데이터베이스에 반영되어야 합니다.
    *   **예시:** 계좌 이체 트랜잭션이 `COMMIT`된 후 서버가 갑자기 다운되더라도, 재시작 시 이체된 금액은 정상적으로 반영되어 있어야 합니다.
    *   **구현:** 트랜잭션 로그(Transaction Log 또는 Write-Ahead Log)에 변경 사항을 기록하고, 주기적으로 디스크에 데이터를 동기화(Flush)하는 방식으로 보장됩니다.

### 1.3. 트랜잭션 명령어: 흐름 제어

트랜잭션을 제어하는 주요 명령어는 다음과 같습니다. 이 명령어들을 통해 개발자는 데이터 변경 작업의 논리적인 단위를 명확히 정의하고 관리할 수 있습니다.

*   **`START TRANSACTION;` (또는 `BEGIN;`):**
    새로운 트랜잭션을 시작합니다. 이 명령어 이후에 실행되는 모든 DML(INSERT, UPDATE, DELETE) 작업은 현재 트랜잭션의 일부가 됩니다. `SELECT` 문은 트랜잭션의 일부가 될 수도 있고 아닐 수도 있습니다 (격리 수준에 따라 다름).
*   **`COMMIT;`:**
    현재 트랜잭션 내의 모든 변경 사항을 데이터베이스에 영구적으로 반영합니다. `COMMIT`이 성공하면 변경 사항은 다른 트랜잭션에서도 볼 수 있게 되며, `ROLLBACK`으로 되돌릴 수 없게 됩니다.
*   **`ROLLBACK;`:**
    현재 트랜잭션 내의 모든 변경 사항을 취소하고, 트랜잭션 시작 이전의 상태로 데이터베이스를 되돌립니다. 오류가 발생했거나 비즈니스 로직상 취소가 필요한 경우 사용됩니다.
*   **`SAVEPOINT savepoint_name;`:**
    트랜잭션 내에서 특정 지점을 저장합니다. `ROLLBACK TO savepoint_name;`을 사용하여 해당 저장 지점까지의 변경 사항만 취소할 수 있습니다. 이는 복잡한 트랜잭션 내에서 부분적인 롤백이 필요할 때 유용합니다.

```sql
-- 예시: 계좌 이체 트랜잭션 (오류 처리 포함)
START TRANSACTION;

-- 1. A 계좌에서 1000원 출금
UPDATE accounts SET balance = balance - 1000 WHERE account_id = 'A';

-- SAVEPOINT 설정 (부분 롤백 지점)
SAVEPOINT withdraw_a;

-- 2. B 계좌에 1000원 입금
UPDATE accounts SET balance = balance + 1000 WHERE account_id = 'B';

-- 가상의 오류 발생 조건
-- IF (SELECT balance FROM accounts WHERE account_id = 'B') < 0 THEN
--     ROLLBACK TO withdraw_a; -- B 계좌 입금만 취소하고 A 계좌 출금은 유지
--     -- 또는 ROLLBACK; -- 전체 트랜잭션 취소
-- END IF;

-- 모든 작업이 성공하면 COMMIT
COMMIT;
```

### 1.4. 트랜잭션 격리 수준 (Isolation Level): 동시성 제어의 깊이

여러 트랜잭션이 동시에 실행될 때, 데이터의 일관성을 유지하면서도 동시성을 높이기 위해 트랜잭션 격리 수준을 설정할 수 있습니다. 격리 수준이 높을수록 데이터 일관성은 강하게 보장되지만, 동시성은 떨어지고 잠금(Lock)으로 인한 성능 저하가 발생할 수 있습니다. ANSI/ISO SQL 표준은 네 가지 격리 수준을 정의합니다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 설명 |
| :--- | :--- | :--- | :--- | :--- |
| `READ UNCOMMITTED` | 발생 가능 | 발생 가능 | 발생 가능 | 다른 트랜잭션이 `COMMIT`하지 않은 데이터(Dirty Data)를 읽을 수 있습니다. 가장 낮은 격리 수준으로, 데이터 일관성이 거의 보장되지 않습니다. |
| `READ COMMITTED` | 방지 | 발생 가능 | 발생 가능 | 다른 트랜잭션이 `COMMIT`한 데이터만 읽을 수 있습니다. 한 트랜잭션 내에서 동일한 쿼리를 두 번 실행했을 때 다른 결과가 나올 수 있습니다. (Oracle, PostgreSQL의 기본 격리 수준) |
| `REPEATABLE READ` | 방지 | 방지 | 발생 가능 | 한 트랜잭션 내에서 동일한 쿼리를 여러 번 실행해도 항상 동일한 결과를 보장합니다. 하지만 새로운 로우가 삽입되는 경우(Phantom Read)는 방지하지 못할 수 있습니다. (MySQL의 기본 격리 수준) |
| `SERIALIZABLE` | 방지 | 방지 | 방지 | 가장 엄격한 격리 수준으로, 모든 종류의 읽기 불일치(Dirty Read, Non-Repeatable Read, Phantom Read)를 방지합니다. 트랜잭션들이 순차적으로 실행되는 것처럼 보이므로 동시성이 가장 낮고 성능 저하가 가장 큽니다. |

*   **각 문제점 상세 설명:**
    *   **Dirty Read (더티 읽기):** 다른 트랜잭션이 아직 `COMMIT`하지 않은 데이터를 읽는 현상. `ROLLBACK`될 수 있는 데이터를 읽게 되어 잘못된 판단을 내릴 수 있습니다.
    *   **Non-Repeatable Read (반복 불가능 읽기):** 한 트랜잭션 내에서 동일한 로우를 두 번 이상 읽을 때, 그 사이에 다른 트랜잭션이 해당 로우를 `UPDATE`하거나 `DELETE`하여 처음 읽은 결과와 나중에 읽은 결과가 달라지는 현상.
    *   **Phantom Read (유령 읽기):** 한 트랜잭션 내에서 특정 조건으로 로우 집합을 쿼리했을 때, 그 사이에 다른 트랜잭션이 해당 조건에 맞는 새로운 로우를 `INSERT`하여 다시 쿼리했을 때 이전에 없던 로우가 나타나는 현상.

*   **격리 수준 설정:**
    ```sql
    -- 현재 세션의 트랜잭션 격리 수준 확인 (DBMS마다 구문 상이)
    SELECT @@transaction_isolation; -- MySQL
    SHOW TRANSACTION ISOLATION LEVEL; -- PostgreSQL

    -- 현재 세션의 트랜잭션 격리 수준 설정
    SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

    -- 전역 트랜잭션 격리 수준 설정 (재시작 후 적용)
    SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;
    ```

**실무적 관점:** 대부분의 OLTP(Online Transaction Processing) 애플리케이션에서는 `READ COMMITTED` 또는 `REPEATABLE READ` 격리 수준을 사용합니다. `SERIALIZABLE`은 동시성 문제가 심각하여 성능 저하가 크므로 데이터 일관성이 절대적으로 중요한 특정 비즈니스 로직(예: 회계 시스템의 최종 정산)에만 제한적으로 사용합니다. 데이터 분석가는 주로 데이터를 읽는 역할을 하므로, 트랜잭션 격리 수준이 쿼리 결과의 정확성과 일관성에 어떤 영향을 미칠 수 있는지 이해하는 것이 중요합니다.

### 1.5. 트랜잭션 활용 시 주의사항 및 고급 기법

트랜잭션을 효과적으로 사용하기 위한 실무적인 팁과 고려사항입니다.

*   **트랜잭션 범위 최소화 (Short Transactions):**
    트랜잭션은 가능한 한 짧게 유지하여 잠금(Lock)으로 인한 동시성 문제를 최소화해야 합니다. 트랜잭션이 길어지면 락이 오래 유지되어 다른 트랜잭션의 대기 시간이 길어지고, 데드락 발생 가능성이 높아집니다.
*   **`COMMIT` 또는 `ROLLBACK` 필수:**
    `START TRANSACTION`으로 시작한 트랜잭션은 반드시 `COMMIT` 또는 `ROLLBACK`으로 명시적으로 종료해야 합니다. 그렇지 않으면 잠금이 해제되지 않아 다른 트랜잭션에 영향을 주거나, 데이터베이스 리소스(예: Undo Log Space)가 고갈될 수 있습니다.
*   **`AUTOCOMMIT` 모드 이해:**
    대부분의 SQL 클라이언트(CLI, GUI 툴)는 기본적으로 `AUTOCOMMIT` 모드입니다. 이 모드에서는 각 SQL 문(특히 DML)이 실행될 때마다 자동으로 하나의 트랜잭션으로 처리되어 즉시 `COMMIT`됩니다. 명시적으로 트랜잭션을 시작하려면 `SET AUTOCOMMIT = 0;`으로 설정하거나 `START TRANSACTION;`을 사용해야 합니다.
*   **오류 처리 및 롤백 로직:**
    트랜잭션 내에서 오류가 발생했을 때 `ROLLBACK`을 통해 데이터 일관성을 유지하는 로직을 반드시 애플리케이션 코드에 구현해야 합니다. `try-catch` 블록 등을 활용하여 예외 발생 시 `ROLLBACK`을 호출하도록 합니다.
*   **명시적 트랜잭션 vs 암시적 트랜잭션:**
    *   **명시적 트랜잭션:** `START TRANSACTION` 또는 `BEGIN`으로 시작하고 `COMMIT` 또는 `ROLLBACK`으로 명시적으로 종료하는 방식입니다. 개발자가 트랜잭션의 범위를 정확히 제어할 수 있어 권장됩니다.
    *   **암시적 트랜잭션:** `AUTOCOMMIT` 모드에서 각 DML 문이 자동으로 트랜잭션으로 처리되는 방식입니다. 단순한 단일 작업에는 편리하지만, 여러 DML이 논리적으로 묶여야 하는 경우에는 부적합합니다.
*   **분산 트랜잭션 (Distributed Transactions):**
    여러 개의 독립적인 데이터베이스 시스템에 걸쳐 하나의 논리적인 트랜잭션을 수행해야 할 때 사용됩니다. 2단계 커밋(2PC, Two-Phase Commit) 프로토콜 등을 통해 원자성을 보장하지만, 구현이 복잡하고 성능 오버헤드가 큽니다. 마이크로서비스 아키텍처 등에서 데이터 일관성을 유지하기 위한 대안으로 사가(Saga) 패턴 등이 고려되기도 합니다.
*   **읽기 전용 트랜잭션 (Read-Only Transactions):**
    데이터를 변경하지 않고 읽기만 하는 트랜잭션의 경우, `SET TRANSACTION READ ONLY;`와 같이 읽기 전용으로 선언하면 DBMS가 불필요한 잠금을 줄이고 최적화를 수행하여 성능을 향상시킬 수 있습니다. 이는 특히 분석 쿼리나 리포팅 작업에 유용합니다.

**실무 팁:** 트랜잭션은 데이터베이스 애플리케이션의 안정성과 신뢰성을 결정하는 가장 중요한 요소입니다. 비즈니스 로직의 특성을 정확히 이해하고, 적절한 격리 수준과 트랜잭션 관리 전략을 수립하는 것이 중요합니다. 특히 대규모 시스템에서는 트랜잭션 모니터링을 통해 잠금 경합, 데드락 등을 조기에 감지하고 해결하는 능력이 필수적입니다.

## 2. 데이터베이스 객체 (Database Objects)

데이터베이스 객체는 데이터를 저장하는 테이블 외에, 데이터베이스 내에 생성되는 모든 논리적인 구조물을 의미합니다. 이러한 객체들은 데이터베이스의 기능을 확장하고, 데이터 관리를 체계화하며, 보안을 강화하고, 개발 생산성을 높이는 데 핵심적인 역할을 합니다. 모든 객체의 정보는 데이터 딕셔너리(Data Dictionary) 또는 시스템 카탈로그(System Catalog)에 저장 및 관리됩니다.

### 2.1. 뷰 (VIEW): 데이터의 창

뷰(VIEW)는 하나 이상의 테이블이나 다른 뷰를 기반으로 정의되는 **가상의 테이블**입니다. 뷰는 실제 데이터를 저장하지 않고, 뷰에 접근할 때마다 정의된 `SELECT` 문이 실행되어 동적으로 결과를 생성합니다.

*   **핵심 개념:**
    *   **데이터 독립성:** 뷰는 기반 테이블의 구조가 변경되더라도 뷰의 정의만 수정하면 되므로, 응용 프로그램이 테이블 구조 변화에 영향을 덜 받게 하는 **논리적 데이터 독립성**을 제공합니다.
    *   **저장된 쿼리:** 뷰는 본질적으로 이름이 부여된 `SELECT` 쿼리입니다.

*   **장점:**
    *   **보안 강화:** 사용자에게는 테이블 전체가 아닌, 뷰를 통해 허용된 특정 행과 열만 노출하여 데이터 접근을 세밀하게 제어할 수 있습니다.
    *   **쿼리 단순화:** 복잡한 `JOIN`, 집계 함수, 서브쿼리 등을 뷰로 캡슐화하여, 사용자는 단순한 `SELECT` 문으로 원하는 데이터에 접근할 수 있습니다.
    *   **일관성 및 재사용성:** 동일한 로직의 쿼리가 여러 곳에서 필요할 때, 뷰를 중앙에서 관리하여 일관성을 유지하고 코드 중복을 방지합니다.

*   **종류 및 옵션:**
    *   **단순 뷰 (Simple View):** 하나의 테이블로 생성되며, `GROUP BY`, `JOIN` 등이 없고, 모든 `NOT NULL` 컬럼을 포함하는 뷰. DML(INSERT, UPDATE, DELETE) 작업이 가능합니다.
    *   **복합 뷰 (Complex View):** 여러 테이블을 `JOIN`하거나, 집계 함수, `DISTINCT` 등을 사용하여 생성된 뷰. 일반적으로 DML 작업에 제약이 따르거나 불가능합니다.
    *   **`WITH CHECK OPTION`:** 뷰에 대해 수행되는 DML 작업이 뷰의 `WHERE` 조건절에 위배되지 않도록 강제하는 옵션입니다. 데이터 일관성을 높이는 데 유용합니다.

*   **생성 및 활용:**
    ```sql
    -- 'Development' 부서의 연봉 7만 이상 직원 정보만 보여주는 뷰 (보안 및 단순화)
    CREATE OR REPLACE VIEW vw_dev_high_salary AS
    SELECT employee_id, first_name, last_name, salary
    FROM employees
    WHERE department_id = (SELECT department_id FROM departments WHERE department_name = 'Development')
      AND salary >= 70000
    WITH CHECK OPTION; -- 이 뷰를 통해 salary를 7만 미만으로 수정하거나 다른 부서 직원을 INSERT하는 것을 방지

    -- 사용
    SELECT * FROM vw_dev_high_salary;
    ```

*   **구체화된 뷰 (Materialized View):**
    일반 뷰와 달리 **실제 데이터를 저장**하는 객체입니다. 쿼리 결과를 물리적으로 저장해두기 때문에 조회 성능이 매우 빠릅니다. 데이터 웨어하우스(DW)나 복잡한 집계가 필요한 리포팅 환경에서 주로 사용됩니다. 단, 원본 테이블 데이터 변경 시 주기적인 **새로고침(Refresh)** 과정이 필요하며, 추가 저장 공간을 사용한다는 단점이 있습니다.

**실무적 관점:** 뷰는 API 개발 시 데이터 모델을 안정적으로 노출하거나, 데이터 분석가에게 복잡한 스키마를 숨기고 분석에 필요한 데이터 집합만 제공하는 용도로 매우 유용합니다. 성능이 중요한 경우, 일반 뷰의 쿼리 자체를 튜닝하거나 구체화된 뷰 도입을 검토해야 합니다.

### 2.2. 저장 프로시저 (Stored Procedure): 데이터베이스의 API

저장 프로시저는 특정 작업을 수행하기 위한 **SQL 문의 집합을 컴파일하여 데이터베이스에 저장**해 둔 객체입니다. 애플리케이션은 이 프로시저를 이름으로 호출하여 복잡한 로직을 실행할 수 있습니다.

*   **핵심 개념:**
    *   **서버 사이드 로직:** 비즈니스 로직의 일부를 클라이언트(애플리케이션)가 아닌 데이터베이스 서버에서 직접 실행합니다.
    *   **트랜잭션 제어:** 프로시저 내에서 트랜잭션을 시작, 커밋, 롤백하여 데이터의 원자성을 보장할 수 있습니다.

*   **장점:**
    *   **성능 향상:** 최초 실행 시 컴파일되어 실행 계획이 캐싱되므로, 반복 호출 시 성능이 빠릅니다.
    *   **네트워크 부하 감소:** 여러 SQL 문을 서버에 보내는 대신, 프로시저 호출 한 번으로 대체하여 네트워크 트래픽을 획기적으로 줄입니다.
    *   **보안 강화:** 사용자에게 테이블 접근 권한 없이 프로시저 실행 권한만 부여하여, 정해진 로직으로만 데이터를 조작하도록 강제할 수 있습니다. (예: `GRANT EXECUTE ON PROCEDURE ...`)
    *   **모듈화 및 유지보수:** 공통 비즈니스 로직(예: 회원 가입, 주문 처리)을 프로시저로 만들어 중앙에서 관리하므로 재사용성이 높고 유지보수가 용이합니다.

*   **매개변수 및 오류 처리 (MySQL 예시):**
    ```sql
    DELIMITER //
    CREATE PROCEDURE sp_transfer_funds(
        IN from_account INT,
        IN to_account INT,
        IN amount DECIMAL(10, 2),
        OUT result_message VARCHAR(255)
    )
    BEGIN
        -- 오류 발생 시 롤백을 위한 핸들러 선언
        DECLARE exit handler for sqlexception
        BEGIN
            ROLLBACK;
            SET result_message = '계좌 이체 중 오류가 발생하여 롤백되었습니다.';
        END;

        START TRANSACTION;

        -- 출금
        UPDATE accounts SET balance = balance - amount WHERE account_id = from_account;
        -- 입금
        UPDATE accounts SET balance = balance + amount WHERE account_id = to_account;

        COMMIT;
        SET result_message = '계좌 이체가 성공적으로 완료되었습니다.';
    END //
    DELIMITER ;

    -- 실행
    CALL sp_transfer_funds(101, 102, 500.00, @msg);
    SELECT @msg;
    ```

**실무적 관점:** 저장 프로시저는 데이터베이스 중심의 아키텍처(DB-centric architecture)에서 핵심적인 역할을 합니다. 복잡한 배치 작업, 데이터 마이그레이션, 정산 처리 등 트랜잭션 제어가 필수적인 백엔드 로직 구현에 널리 사용됩니다. 다만, 프로시저에 비즈니스 로직이 과도하게 집중되면 애플리케이션과의 의존성이 높아져 유지보수가 어려워지는 단점도 있습니다.

### 2.3. 사용자 정의 함수 (UDF, User-Defined Function): 쿼리의 확장

함수는 특정 계산이나 데이터 조작을 수행하고 **단일 값 또는 테이블을 반환**하는 객체입니다. 저장 프로시저와 달리 `SELECT` 문이나 `WHERE` 절 등 SQL 표현식 내에서 직접 사용될 수 있습니다.

*   **핵심 개념:**
    *   **값 반환:** 항상 `RETURN`을 통해 값을 반환해야 합니다.
    *   **부수 효과(Side Effect) 금지:** 원칙적으로 테이블의 데이터를 변경하는 DML(INSERT, UPDATE, DELETE) 문을 포함할 수 없습니다.

*   **장점:**
    *   **재사용성 및 가독성:** 복잡한 계산 로직(예: 이자 계산, 등급 변환)을 함수로 만들어 쿼리를 간결하고 가독성 높게 만들 수 있습니다.
    *   **모듈화:** 비즈니스 로직을 작은 함수 단위로 분리하여 개발 및 테스트가 용이합니다.

*   **종류 및 특성 (MySQL 예시):**
    *   **스칼라 함수 (Scalar Function):** 단일 값을 반환합니다.
        ```sql
        DELIMITER //
        CREATE FUNCTION fn_calculate_age(birth_date DATE)
        RETURNS INT
        DETERMINISTIC -- 동일한 입력에 항상 동일한 결과를 반환함을 명시 (성능 최적화에 도움)
        BEGIN
            RETURN TIMESTAMPDIFF(YEAR, birth_date, CURDATE());
        END //
        DELIMITER ;

        -- 사용
        SELECT employee_id, fn_calculate_age(hire_date) AS working_years FROM employees;
        ```
    *   **테이블 반환 함수 (Table-Valued Function):** (SQL Server, PostgreSQL 등에서 지원) 행의 집합, 즉 테이블을 반환하여 `FROM` 절에서 사용될 수 있습니다.

**실무적 관점:** 함수는 데이터 클렌징, 변환, 비즈니스 규칙 기반의 계산 등 데이터 분석 및 리포팅 쿼리 작성 시 매우 유용합니다. 프로시저가 '작업(Action)'을 수행한다면, 함수는 '값(Value)'을 계산하는 데 중점을 둡니다. 쿼리 내에서 자주 사용되는 함수는 성능에 영향을 미칠 수 있으므로, 로직을 최적화하는 것이 중요합니다.

### 2.4. 트리거 (Trigger): 데이터 변경의 감시자

트리거는 특정 테이블에 `INSERT`, `UPDATE`, `DELETE` 같은 DML 이벤트가 발생했을 때 **자동으로 실행**되도록 정의된 특수한 종류의 저장 프로시저입니다.

*   **핵심 개념:**
    *   **이벤트 기반 실행:** 사용자가 직접 호출하는 것이 아니라, 특정 이벤트에 의해 암시적으로 실행됩니다.
    *   **`OLD`와 `NEW`:**
        *   `INSERT`: `NEW`를 통해 새로 삽입될 행의 데이터에 접근할 수 있습니다.
        *   `DELETE`: `OLD`를 통해 삭제될 행의 데이터에 접근할 수 있습니다.
        *   `UPDATE`: `OLD`(변경 전)와 `NEW`(변경 후) 데이터 모두에 접근할 수 있습니다.

*   **장점:**
    *   **데이터 무결성 강제:** 복잡한 비즈니스 규칙(예: '직원 퇴사 시 관련 프로젝트에서 자동 제외')을 데이터베이스 레벨에서 강제할 수 있습니다.
    *   **감사 및 로깅 자동화:** 데이터 변경이 발생할 때마다 관련 정보를 별도의 로그 테이블에 자동으로 기록할 수 있습니다.
    *   **파생 데이터 자동 계산:** 특정 컬럼이 변경될 때 관련된 다른 컬럼의 값을 자동으로 갱신할 수 있습니다.

*   **실행 시점 및 예시 (MySQL):**
    *   `BEFORE`: DML 문이 실행되기 **전**에 트리거가 실행됩니다. 주로 입력될 값의 유효성을 검사하거나 변경하기 위해 사용됩니다.
    *   `AFTER`: DML 문이 실행된 **후**에 트리거가 실행됩니다. 주로 데이터 변경 후의 후속 작업(로깅, 다른 테이블 업데이트)에 사용됩니다.

    ```sql
    -- 주문 수량이 변경될 때마다 products 테이블의 재고량을 자동으로 업데이트하는 트리거
    DELIMITER //
    CREATE TRIGGER trg_update_stock
    AFTER INSERT ON order_details
    FOR EACH ROW
    BEGIN
        UPDATE products
        SET stock_quantity = stock_quantity - NEW.quantity
        WHERE product_id = NEW.product_id;
    END //
    DELIMITER ;
    ```

**실무적 관점:** 트리거는 매우 강력하지만, 로직이 눈에 보이지 않게 실행되므로 디버깅을 어렵게 하고 예기치 않은 연쇄 반응(Cascading Triggers)을 일으킬 수 있습니다. 과도한 사용은 데이터베이스 성능 저하의 주범이 될 수 있으므로, 반드시 필요한 핵심 무결성 규칙이나 감사 로깅에 제한적으로 사용하는 것이 좋습니다. 대부분의 비즈니스 로직은 애플리케이션 코드에서 명시적으로 처리하는 것이 권장됩니다.

### 2.5. 이벤트 스케줄러 (Event Scheduler): 자동화된 DB 작업

이벤트는 특정 시간 또는 주기마다 **자동으로 실행되도록 예약된 작업**입니다. 운영체제의 `Cron` 작업과 유사한 기능을 데이터베이스 내에서 제공합니다.

*   **핵심 개념:**
    *   **시간 기반 실행:** 특정 시점(`AT`) 또는 반복적인 간격(`EVERY`)으로 SQL 문, 프로시저 등을 실행합니다.
    *   **백그라운드 프로세스:** 데이터베이스의 스케줄러 스레드에 의해 백그라운드에서 실행됩니다.

*   **장점:**
    *   **유지보수 자동화:** 주기적인 데이터 백업, 오래된 로그 삭제, 인덱스 재구성 등의 작업을 자동화합니다.
    *   **통계 데이터 생성:** 야간이나 새벽 시간에 일별/월별 통계 데이터를 집계하여 요약 테이블을 생성하는 배치 작업을 수행할 수 있습니다.

*   **생성 및 관리 (MySQL 예시):**
    ```sql
    -- 이벤트 스케줄러 활성화 (필수)
    SET GLOBAL event_scheduler = ON;

    -- 매일 새벽 2시에 일일 매출 통계 테이블을 생성하는 이벤트
    CREATE EVENT evt_daily_sales_summary
    ON SCHEDULE EVERY 1 DAY
    STARTS TIMESTAMP(CURDATE() + INTERVAL 1 DAY + INTERVAL 2 HOUR) -- 내일 새벽 2시부터 시작
    DO
    BEGIN
        CALL sp_generate_daily_sales_report(CURDATE());
    END;

    -- 이벤트 확인 및 수정/삭제
    SHOW EVENTS;
    ALTER EVENT evt_daily_sales_summary DISABLE; -- 비활성화
    DROP EVENT evt_daily_sales_summary;
    ```

**실무적 관점:** 이벤트는 데이터 웨어하우스(DW) 환경에서 ETL(Extract, Transform, Load) 작업의 일부를 자동화하거나, OLTP 시스템에서 주기적인 정리 및 집계 작업을 수행하는 데 매우 유용합니다. 이벤트가 실패할 경우를 대비해 실행 로그를 기록하고 모니터링하는 체계를 갖추는 것이 중요합니다.

### 2.6. 시퀀스 (Sequence): 고유 번호 생성기

시퀀스는 **유일한 숫자 값을 순차적으로 생성**하는 독립적인 데이터베이스 객체입니다. 주로 테이블의 기본 키(Primary Key) 값을 중복 없이 안전하게 생성하기 위해 사용됩니다.

*   **핵심 개념:**
    *   **독립 객체:** 테이블에 종속되지 않고 독립적으로 존재하며, 여러 테이블에서 공유하여 사용할 수 있습니다.
    *   **동시성 제어:** 여러 세션이 동시에 값을 요청해도 잠금 없이 고유한 값을 할당하여 동시성이 뛰어납니다.

*   **MySQL의 `AUTO_INCREMENT`와의 비교:**
    *   **공통점:** 새로운 행이 추가될 때 고유한 번호를 자동으로 생성합니다.
    *   **차이점:** `AUTO_INCREMENT`는 테이블의 컬럼 속성이지만, 시퀀스는 별도의 객체입니다. 따라서 시퀀스는 더 유연한 설정(캐시, 순환 등)이 가능하고 여러 테이블에서 공유할 수 있습니다. (Oracle, PostgreSQL 등에서 표준 기능으로 제공)

*   **생성 및 사용 (Oracle, PostgreSQL 예시):**
    ```sql
    CREATE SEQUENCE seq_employee_id
    START WITH 1000      -- 시작 값
    INCREMENT BY 1       -- 증가 값
    MINVALUE 1000        -- 최소값
    MAXVALUE 999999      -- 최대값
    NOCYCLE              -- 순환하지 않음
    CACHE 20;            -- 메모리에 20개 값을 미리 할당하여 성능 향상

    -- 사용
    INSERT INTO employees (employee_id, first_name)
    VALUES (NEXTVAL('seq_employee_id'), 'John'); -- PostgreSQL
    -- VALUES (seq_employee_id.NEXTVAL, 'John'); -- Oracle
    ```

**실무적 관점:** MySQL 환경에서는 `AUTO_INCREMENT`가 대부분의 요구사항을 충족하지만, 복잡한 분산 환경이나 여러 테이블에 걸쳐 고유한 ID 체계가 필요한 경우 시퀀스의 개념이 유용할 수 있습니다. 다른 DBMS와의 호환성을 위해 시퀀스의 동작 방식을 이해해두는 것이 좋습니다.

### 2.7. 인덱스 (Index): 검색 성능의 핵심

인덱스는 테이블의 데이터에 대한 **빠른 검색을 위해 사용되는 자료구조**입니다. 책의 '찾아보기'와 같이, 특정 값을 가진 행이 디스크의 어느 위치에 있는지에 대한 포인터를 저장합니다. [08_성능튜닝과_인덱스.md](./08_성능튜닝과_인덱스.md)에서 자세히 다루지만, 객체로서의 특징은 다음과 같습니다.

*   **핵심 개념:**
    *   **검색 속도 vs DML 성능:** `SELECT` 쿼리의 성능을 극적으로 향상시키지만, `INSERT`, `UPDATE`, `DELETE` 시 인덱스도 함께 수정되어야 하므로 DML 성능은 저하됩니다. 이는 **읽기-쓰기 트레이드오프** 관계입니다.
    *   **데이터 구조:** 주로 B-Tree(Balanced-Tree) 구조로 구현되어, 데이터의 양에 관계없이 균일한 검색 속도를 보장합니다.

*   **주요 인덱스 종류:**
    *   **클러스터형 인덱스 (Clustered Index):** 테이블당 하나만 존재하며, 데이터 행 자체를 인덱스의 리프 노드에 저장합니다. 즉, 인덱스 순서와 데이터의 물리적 저장 순서가 일치합니다.
    *   **비클러스터형 인덱스 (Non-Clustered Index):** 테이블당 여러 개를 생성할 수 있으며, 데이터 위치에 대한 포인터(RID)를 별도로 저장합니다.
    *   **기타:** Full-Text Index, Spatial Index, Hash Index 등 데이터 유형과 검색 목적에 따라 다양한 인덱스가 존재합니다.

**실무적 관점:** 인덱스는 데이터베이스 성능 튜닝의 가장 기본적이면서도 강력한 도구입니다. 데이터 분석가는 `WHERE` 절이나 `JOIN` 조건에 자주 사용되는 컬럼을 파악하고, 실행 계획(Execution Plan)을 분석하여 비효율적인 쿼리의 원인이 인덱스 부재인지 확인하고 개선을 제안할 수 있어야 합니다. 불필요한 인덱스는 오히려 시스템 자원을 낭비하므로, 사용 빈도와 선택도(Selectivity)를 고려하여 신중하게 생성해야 합니다.
