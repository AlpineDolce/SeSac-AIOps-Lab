<h2>SQL 시작하기: 데이터 분석가를 위한 첫걸음</h2>

<h2>문서 목표</h2>
<p>이 문서는 데이터 분석가가 SQL을 시작하기 위한 첫 단계로, MySQL 데이터베이스 환경을 구축하고 SQL의 기본적인 개념과 명령어 분류를 이해하는 것을 목표로 합니다. 관계형 데이터베이스의 구조를 파악하고, 데이터베이스 관리 시스템(DBMS)과의 상호작용 방법을 학습하여 데이터 분석의 기반을 다집니다.</p>

> **현업 데이터 분석가의 관점 한 줄 요약:**
>
> 이 문서는 데이터 분석의 가장 기본이 되는 언어인 SQL을 시작하기 위한 실무 가이드입니다. 단순히 MySQL을 설치하는 것을 넘어, **왜 특정 설정을 사용해야 하는지(예: `utf8mb4`)**, **실무에서 CLI와 GUI 도구를 어떻게 조화롭게 사용하는지**, 그리고 **데이터베이스 권한 관리가 왜 중요한지**에 대한 깊이 있는 이해를 목표로 합니다. 이 가이드를 통해 여러분은 단순한 쿼리 작성자를 넘어, 데이터의 구조를 이해하고 효율적으로 데이터를 다루는 데이터 분석가로 성장하는 첫걸음을 내딛게 될 것입니다.

## 1. MySQL 설치: 단계별 가이드

MySQL은 세계에서 가장 널리 사용되는 오픈소스 관계형 데이터베이스 관리 시스템(RDBMS)입니다. 데이터 분석가에게는 데이터 저장, 관리, 분석을 위한 필수 도구입니다.

### 1.1. MySQL Installer 다운로드 및 설치 (빠른 개발 환경 구축)

MySQL을 설치하는 가장 쉬운 방법은 MySQL Installer를 사용하는 것입니다. 이 도구는 MySQL 서버뿐만 아니라 Workbench, Shell 등 관련 도구들을 한 번에 설치할 수 있도록 도와줍니다.

1.  **MySQL 공식 웹사이트 접속:** [MySQL Downloads Page](https://dev.mysql.com/downloads/installer/)에 접속합니다.
2.  **Installer 다운로드:** "MySQL Installer for Windows" 섹션에서 `mysql-installer-community-*.msi` 파일을 다운로드합니다. 일반적으로 웹 커뮤니티 버전을 선택합니다.
3.  **설치 유형 선택:** 다운로드한 파일을 실행하여 설치를 시작합니다.
    *   `Developer Default`: 개발에 필요한 모든 구성 요소(서버, 클라이언트, Workbench, Shell 등)를 설치합니다. **데이터 분석가에게 가장 권장되는 옵션입니다.**
    *   `Server only`: MySQL 서버만 설치합니다.
    *   `Client only`: MySQL 클라이언트 프로그램만 설치합니다.
    *   `Full`: 모든 MySQL 제품을 설치합니다.
    *   `Custom`: 설치할 구성 요소를 직접 선택합니다.
    데이터 분석가라면 `Developer Default`를 선택하는 것이 편리합니다.
4.  **구성 요소 확인 및 설치:** 선택한 설치 유형에 따라 필요한 구성 요소 목록이 표시됩니다. `Execute`를 클릭하여 설치를 진행합니다.

**실무 팁:**
*   **설치 전 시스템 요구사항 확인:** MySQL 버전별로 지원하는 운영체제와 하드웨어 요구사항이 다를 수 있으므로, 설치 전에 공식 문서를 확인하는 것이 좋습니다.
*   **관리자 권한:** 설치 과정에서 관리자 권한이 필요할 수 있으므로, 관리자 계정으로 로그인하거나 관리자 권한으로 설치 프로그램을 실행해야 합니다.
*   **기존 MySQL 설치 확인:** 이전에 MySQL이 설치되어 있었다면, 충돌을 피하기 위해 기존 설치를 완전히 제거하거나 다른 포트를 사용하도록 설정해야 합니다.

### 1.2. 서버 상세 구성 (Root 비밀번호, 포트 설정 등) (안정적인 MySQL 환경 설정)

설치 구성 요소가 모두 설치되면, MySQL 서버 및 기타 제품에 대한 설정 단계로 넘어갑니다. 이 단계에서 설정하는 값들은 MySQL 서버의 성능과 보안에 직접적인 영향을 미치므로 신중하게 진행해야 합니다.

1.  **High Availability (고가용성):** 특별한 설정이 없다면 `Standalone MySQL Server / Classic MySQL Replication`을 선택합니다. (대부분의 개발 환경에서는 단일 서버로 충분합니다.)
2.  **Type and Networking (유형 및 네트워킹):**
    *   `Config Type`: `Development Computer` (개발 환경에 최적화된 설정)를 선택합니다. 이는 MySQL이 개발 PC의 자원을 효율적으로 사용하도록 기본 설정을 조정합니다.
    *   `Port`: 기본값 `3306`을 유지합니다. 이 포트는 MySQL 서버가 클라이언트 연결을 수신하는 데 사용되는 표준 포트입니다. 다른 서비스와 충돌하지 않는 한 변경할 필요가 없습니다.
    *   `Open Windows Firewall port for network access`: 체크하여 방화벽 예외를 추가합니다. (Linux 환경에서는 `ufw allow 3306`과 같은 명령어로 방화벽 포트를 열 수 있습니다.)
*   **`my.ini` (Windows) 또는 `my.cnf` (Linux) 파일: MySQL 서버의 핵심 설정 파일**
    MySQL 설정 파일은 서버의 동작 방식을 제어하는 중요한 파일입니다. 설치 후 필요에 따라 이 파일을 수정하여 서버 설정을 변경할 수 있습니다. 이 파일은 일반적으로 MySQL 설치 디렉토리 내에 위치합니다.
    *   **주요 설정값 (데이터 분석가를 위한 개발 환경 권장 설정):**
        *   `character_set_server = utf8mb4`: **한글 및 이모지 등 다양한 유니코드 문자를 문제없이 처리하기 위한 필수 설정입니다.** 이 설정이 `latin1` 등 다른 값으로 되어 있으면 한글 데이터가 깨지거나 저장되지 않는 문제가 발생할 수 있습니다. 데이터 분석 시 다양한 언어의 데이터를 다룰 가능성이 높으므로 반드시 `utf8mb4`로 설정해야 합니다.
        *   `collation_server = utf8mb4_unicode_ci`: `utf8mb4` 문자셋에 대한 정렬 및 비교 규칙을 정의합니다. `_unicode_ci`는 유니코드 기반으로 대소문자를 구분하지 않는(case-insensitive) 비교를 의미합니다.
        *   `max_connections`: 동시에 접속할 수 있는 최대 클라이언트 수를 지정합니다. 개발 환경에서는 기본값으로도 충분하지만, 동시 접속 테스트가 필요할 경우 이 값을 늘릴 수 있습니다. (운영 환경에서는 서버 자원과 애플리케이션 특성을 고려하여 신중하게 설정해야 합니다.)
        *   `innodb_buffer_pool_size`: InnoDB 스토리지 엔진이 데이터와 인덱스를 캐싱하는 데 사용하는 메모리 크기입니다. **이 값은 MySQL 성능에 가장 큰 영향을 미치는 설정 중 하나입니다.** 로컬 개발 환경에서는 시스템 메모리의 50-70% 정도로 설정하면 디스크 I/O를 줄여 쿼리 성능을 향상시킬 수 있습니다. (예: 8GB RAM 시스템에서 4GB ~ 5.6GB 할당)
        *   `datadir`: MySQL 데이터 파일이 저장되는 경로입니다. 기본 경로를 유지하거나, 충분한 공간이 있는 다른 드라이브로 변경할 수 있습니다.
3.  **Authentication Method (인증 방식):**
    *   `Use Strong Password Encryption for Authentication (RECOMMENDED)`: 강력한 비밀번호 암호화를 사용합니다. **보안상 권장되는 옵션입니다.**
    *   `Use Legacy Authentication Method (Retain MySQL 5.x Compatibility)`: 이전 버전과의 호환성을 위해 사용하지만, 보안상 취약할 수 있습니다. (특별한 이유가 없다면 선택하지 않습니다.)
    `RECOMMENDED` 옵션을 선택하고 `Next`를 클릭합니다.
4.  **Accounts and Roles (계정 및 역할):**
    *   `MySQL Root Password`: `root` 계정의 비밀번호를 설정합니다. **이 비밀번호는 MySQL 서버에 대한 모든 권한을 가지므로, 매우 중요하며 반드시 기억해야 합니다.** 복잡하고 예측 불가능한 비밀번호를 설정하는 것이 좋습니다.
    *   `Add User`: 필요한 경우 추가 사용자 계정을 생성할 수 있습니다. **실무에서는 `root` 계정 대신 특정 권한을 가진 사용자 계정을 생성하여 사용하는 것이 보안상 강력히 권장됩니다.** (최소 권한의 원칙)
5.  **Windows Service (Windows 서비스):**
    *   `Configure MySQL Server as a Windows Service`: MySQL 서버를 Windows 서비스로 등록하여 시스템 시작 시 자동으로 실행되도록 합니다.
    *   `Start the MySQL Server at System Startup`: 체크하여 시스템 시작 시 자동 실행되도록 설정합니다.
    *   `Run Windows Service as`: `Standard System Account`를 선택합니다. (특별한 권한 설정이 필요하지 않다면 기본값 유지)
6.  **Apply Configuration (구성 적용):** `Execute`를 클릭하여 설정 변경 사항을 적용합니다. 모든 단계가 완료되면 `Finish`를 클릭하여 설치를 마칩니다.

**실무 팁: 설치 후 `my.ini` / `my.cnf` 파일 수정**
설치 과정에서 설정한 내용 외에 추가적인 최적화나 문제 해결을 위해 `my.ini` (Windows) 또는 `my.cnf` (Linux) 파일을 직접 수정해야 할 때가 있습니다. 이 파일은 일반적으로 MySQL 설치 경로의 `ProgramData` (숨김 폴더) 또는 `/etc/mysql/mysql.conf.d/` 등에 위치합니다.
*   **파일 위치 확인:** MySQL Workbench의 `Options File` 메뉴나 `SHOW VARIABLES LIKE 'datadir';` 명령으로 데이터 디렉토리를 확인한 후, 해당 디렉토리나 상위 디렉토리에서 `my.ini` 또는 `my.cnf` 파일을 찾을 수 있습니다.
*   **수정 후 재시작:** 설정 파일을 수정한 후에는 반드시 MySQL 서버를 재시작해야 변경 사항이 적용됩니다. (Windows 서비스 관리자 또는 `sudo systemctl restart mysql`)
*   **백업:** 설정 파일을 수정하기 전에는 항상 원본 파일을 백업해두는 습관을 들이세요.

### 1.2.1. 저장 엔진 (Storage Engine)
MySQL은 다양한 저장 엔진을 지원하며, 각 엔진은 데이터 저장 및 처리 방식에 차이가 있습니다.
*   **`InnoDB` (기본값):** 트랜잭션(ACID), 외래 키, 행 수준 잠금(Row-level locking)을 지원하여 데이터 무결성과 동시성 제어에 강점이 있습니다. 대부분의 애플리케이션과 데이터 분석 환경에서 권장됩니다.
*   **`MyISAM`:** 트랜잭션을 지원하지 않지만, 읽기(Read) 작업에 특화되어 있습니다. (과거에 많이 사용되었으나, 현재는 `InnoDB`가 대부분의 경우 더 우수합니다.)

### 1.2.2. MySQL 아키텍처 (클라이언트-서버 모델)
MySQL 서버는 클라이언트-서버 모델로 동작합니다. 클라이언트(MySQL CLI, Workbench, DBeaver, 파이썬 애플리케이션 등)는 네트워크를 통해 MySQL 서버에 접속하여 쿼리를 전송하고, 서버는 이를 처리하여 결과를 클라이언트에 반환합니다.
*   **클라이언트:** 쿼리를 생성하고 서버에 전송하며, 서버로부터 받은 결과를 사용자에게 표시합니다.
*   **서버:** 클라이언트의 요청을 받아 SQL 쿼리를 파싱하고, 최적화하며, 실행 계획을 수립합니다. 실제 데이터는 **스토리지 엔진**을 통해 디스크에 저장되거나 읽혀집니다. 서버는 쿼리 실행 후 결과를 클라이언트에 전송합니다.
이러한 분리된 구조 덕분에 여러 클라이언트가 동시에 데이터베이스에 접근할 수 있으며, 서버는 데이터의 일관성과 무결성을 중앙에서 관리할 수 있습니다.

## 2. 개발 환경 연동

MySQL 서버가 설치되었다면, 이제 이 서버에 접속하여 데이터를 관리하고 쿼리를 실행할 수 있는 개발 환경을 설정해야 합니다.

### 2.1. 명령 프롬프트(CLI) 연동을 위한 환경 변수 설정 (데이터 분석가의 필수 도구)

명령 프롬프트(CMD) 또는 터미널에서 `mysql` 명령어를 바로 실행하려면 MySQL 실행 파일의 경로를 시스템 환경 변수 `PATH`에 추가해야 합니다. 이는 데이터 분석가가 CLI 환경에서 MySQL을 효율적으로 사용하기 위한 필수 설정입니다.

1.  **MySQL 설치 경로 확인:** 일반적으로 `C:\Program Files\MySQL\MySQL Server X.X\bin` (X.X는 버전 번호)입니다. 이 경로에 `mysql.exe` 실행 파일이 있습니다.
2.  **환경 변수 편집기 열기:**
    *   Windows 검색창에 "환경 변수"를 입력하고 "시스템 환경 변수 편집"을 선택합니다.
    *   "시스템 속성" 창에서 "환경 변수(N)..." 버튼을 클릭합니다.
3.  **Path 변수 편집:**
    *   "환경 변수" 창의 "시스템 변수" 섹션에서 `Path` 변수를 찾아 선택하고 "편집(I)..." 버튼을 클릭합니다.
    *   "환경 변수 편집" 창에서 "새로 만들기(N)"를 클릭하고, MySQL `bin` 폴더의 경로(예: `C:\Program Files\MySQL\MySQL Server 8.0\bin`)를 추가합니다.
    *   "확인"을 클릭하여 모든 창을 닫습니다.
4.  **확인:** **새 명령 프롬프트 또는 터미널 창을 열고** `mysql --version`을 입력하여 MySQL 버전 정보가 올바르게 표시되는지 확인합니다.

**실무 팁:**
*   **터미널 재시작 필수:** 환경 변수를 변경한 후에는 기존에 열려 있던 명령 프롬프트나 터미널 창에서는 변경 사항이 적용되지 않습니다. 반드시 **새로운 터미널 창을 열어서** 확인해야 합니다.
*   **경로 오류 확인:** 만약 `mysql` 명령어를 찾을 수 없다는 오류가 발생하면, `PATH` 변수에 추가한 경로가 정확한지, 오타는 없는지 다시 확인해야 합니다.
*   **관리자 권한:** 경우에 따라 환경 변수 변경을 위해 관리자 권한이 필요할 수 있습니다.

### 2.1.1. 클라이언트 문자 셋 설정 (한글 깨짐 방지)

데이터베이스와 클라이언트(MySQL CLI, GUI 도구, 파이썬 애플리케이션 등) 간의 문자 인코딩이 일치하지 않으면 **한글 깨짐 현상**이나 데이터 저장 오류 등의 문제가 발생할 수 있습니다. 특히 한국어 데이터를 다루는 데이터 분석가에게는 이 설정이 매우 중요합니다.

*   **임시 설정 (MySQL CLI 접속 후):**
    MySQL CLI에 접속한 후 다음 명령어를 실행하여 현재 세션의 문자 셋을 `utf8mb4`로 설정할 수 있습니다.
    ```sql
    SET NAMES utf8mb4;
    ```
    이 명령어는 `character_set_client`, `character_set_connection`, `character_set_results` 세 가지 시스템 변수를 한 번에 `utf8mb4`로 설정합니다.

*   **영구 설정 (`my.cnf` 또는 `my.ini` 파일):**
    매번 `SET NAMES` 명령을 실행하는 번거로움을 피하려면, MySQL 클라이언트 설정 파일(`my.cnf` 또는 `my.ini`)에 기본 문자 셋을 영구적으로 지정하는 것이 좋습니다. 이 파일은 일반적으로 `[mysql]` 또는 `[client]` 섹션에 설정합니다.
    ```ini
    # my.cnf 또는 my.ini 파일 내용 예시
    [client]
    default-character-set=utf8mb4

    [mysql]
    default-character-set=utf8mb4
    ```
    설정 파일을 수정한 후에는 MySQL CLI를 재시작해야 변경 사항이 적용됩니다.

**실무 팁:**
*   **서버, 데이터베이스, 테이블, 컬럼, 클라이언트 모두 `utf8mb4`로 통일:** 가장 이상적인 환경은 MySQL 서버 자체의 `character_set_server`, 데이터베이스 생성 시의 `CHARACTER SET`, 테이블 및 컬럼의 `CHARACTER SET`, 그리고 클라이언트의 `default-character-set`까지 모두 `utf8mb4`로 통일하는 것입니다. 이렇게 하면 한글 깨짐 문제를 대부분 방지할 수 있습니다.
*   **`utf8` vs `utf8mb4`:** `utf8`은 MySQL에서 3바이트까지만 지원하므로 이모지(Emoji)와 같은 4바이트 문자를 저장할 수 없습니다. `utf8mb4`는 4바이트 문자를 포함한 모든 유니코드 문자를 지원하므로, **반드시 `utf8mb4`를 사용해야 합니다.**

### 2.2. GUI 도구 연결 (DBeaver, MySQL Workbench) (데이터 탐색 및 시각화의 필수 도구)

CLI 환경은 강력하지만, GUI 도구는 데이터베이스 구조를 시각적으로 탐색하고, 쿼리 결과를 표 형태로 확인하며, 데이터베이스 관리를 더 편리하게 할 수 있도록 돕습니다. 데이터 분석가에게는 데이터 탐색(EDA)과 시각화, 복잡한 쿼리 작성 및 디버깅에 필수적인 도구입니다.

*   **MySQL Workbench:**
    *   MySQL 공식 GUI 도구로, MySQL 서버와 완벽하게 통합되어 있습니다.
    *   데이터베이스 설계(ERD), 개발(SQL Editor), 관리(Server Status, User Management) 기능을 모두 제공합니다.
    *   설치 시 `Developer Default` 옵션을 선택했다면 이미 설치되어 있습니다.
    *   **장점:** MySQL에 특화된 기능과 최적화된 성능을 제공하며, MySQL 생태계에 익숙해지는 데 도움이 됩니다.
*   **DBeaver:**
    *   다양한 데이터베이스(MySQL, PostgreSQL, Oracle, SQL Server, SQLite 등)를 지원하는 **범용 데이터베이스 클라이언트**입니다.
    *   직관적인 인터페이스와 강력한 기능을 제공하여 데이터 분석가에게 매우 유용합니다. 특히 여러 종류의 데이터베이스를 동시에 다루는 환경에서 빛을 발합니다.
    *   [DBeaver 공식 웹사이트](https://dbeaver.io/download/)에서 다운로드하여 설치할 수 있습니다.
    *   **장점:** 뛰어난 범용성, 풍부한 플러그인 지원, 강력한 데이터 내보내기/가져오기 기능, ERD 자동 생성 기능.

### 2.2.1. [실무 노트] CLI vs GUI: 언제 무엇을 써야 할까?
> 실무에서 CLI와 GUI는 경쟁 관계가 아닌 **상호 보완 관계**입니다. 데이터 분석가는 두 도구의 장점을 모두 활용하여 작업 효율을 극대화해야 합니다.
>
> | 구분 | **CLI (Command Line Interface)** | **GUI (Graphical User Interface)** |
> | :--- | :--- | :--- |
> | **강점** | **자동화, 반복 작업, 서버 환경** | **탐색, 시각화, 디버깅** |
> | **주요 용도** | - 대용량 데이터 로딩/백업 스크립트 실행<br>- 정기적으로 실행되는 ETL 배치 작업<br>- 서버에서 긴급하게 로그를 확인할 때 | - 테이블 구조 및 관계 파악 (ERD)<br>- **탐색적 데이터 분석 (EDA)**<br>- 복잡한 쿼리 작성 및 디버깅<br>- 분석 결과를 동료에게 공유 (CSV/Excel Export) |
> | **핵심 워크플로우** | **GUI로 데이터를 탐색하고 분석 쿼리를 개발한 뒤, 완성된 쿼리를 CLI 스크립트로 만들어 자동화**하는 흐름을 따르는 것이 가장 효율적입니다. |

### 2.2.2. MySQL CLI `pager` 기능 활용
MySQL CLI에서 `SELECT` 쿼리 결과가 너무 길어 화면을 벗어날 때 `pager` 명령어를 사용하면 `less`와 같은 외부 프로그램을 통해 결과를 페이지 단위로 볼 수 있어 편리합니다.
```sql
pager less -S
SELECT * FROM large_table;
```
`-S` 옵션은 긴 줄을 자르지 않고 한 줄로 표시하여 가로 스크롤을 가능하게 합니다.

**GUI 도구 연결 방법 (일반적인 절차):**

1.  GUI 도구를 실행합니다.
2.  새 데이터베이스 연결을 생성합니다.
3.  `Database Type`에서 `MySQL`을 선택합니다.
4.  `Server Hostname`: `127.0.0.1` 또는 `localhost` (로컬 PC에 설치한 경우)
5.  `Port`: `3306` (기본값)
6.  `Username`: `root` (또는 설치 시 생성한 사용자 계정)
7.  `Password`: `root` 계정 비밀번호 (또는 사용자 계정 비밀번호)
8.  `Test Connection`을 클릭하여 연결이 성공하는지 확인합니다.
9.  연결을 저장하고 데이터베이스를 탐색합니다.

**실무 팁: 연결 문제 해결 및 활용**
*   **방화벽 확인:** 연결 테스트에 실패한다면, Windows 방화벽이나 서버의 방화벽(Linux의 `ufw`, `firewalld` 등)에서 3306 포트가 열려 있는지 확인해야 합니다.
*   **사용자 권한:** 접속하려는 사용자 계정에 해당 데이터베이스에 대한 접근 권한이 있는지 확인합니다. (특히 `root`가 아닌 다른 계정으로 접속 시)
*   **데이터 탐색:** GUI 도구의 스키마 탐색기(Schema Explorer)를 활용하여 테이블 목록, 컬럼 정보, 인덱스, 제약조건 등을 시각적으로 확인하고 데이터 구조를 빠르게 파악할 수 있습니다.
*   **쿼리 작성 및 실행:** SQL Editor에서 쿼리를 작성하고 실행하며, 쿼리 결과를 표 형태로 확인하고 필요에 따라 CSV, Excel 등으로 내보낼 수 있습니다.
*   **SQL 이해의 중요성:** GUI 도구가 쿼리 작성을 편리하게 해주지만, 내부적으로 어떤 SQL이 실행되는지 이해하는 것은 여전히 중요합니다. 복잡한 분석이나 성능 튜닝을 위해서는 SQL에 대한 깊은 지식이 필수적입니다.

## 3. 데이터베이스 기본 관리 (CLI 기준)

GUI 도구도 편리하지만, CLI 환경에서의 기본 관리 명령어는 데이터베이스의 동작 원리를 이해하고 문제 발생 시 빠르게 대처하는 데 필수적입니다.

### 3.1. MySQL 서버 접속 및 상태 확인 (데이터베이스 상태 진단)

MySQL 서버에 접속하여 쿼리를 실행하고 서버의 현재 상태를 확인할 수 있습니다. CLI 환경에서의 이러한 기본 관리 명령어는 데이터베이스의 동작 원리를 이해하고 문제 발생 시 빠르게 대처하는 데 필수적입니다.

*   **MySQL 서버 접속:**
    ```bash
    mysql -u root -p
    ```
    `-u`는 사용자 이름(user), `-p`는 비밀번호(password)를 의미합니다. 명령어를 입력하면 비밀번호를 입력하라는 프롬프트가 나타납니다. **보안을 위해 비밀번호를 직접 명령어 뒤에 붙이지 않는 것이 좋습니다.**

*   **MySQL 서버 상태 확인 (`STATUS;`):**
    접속 후 `STATUS;` 명령어를 입력하여 서버의 현재 상태에 대한 요약 정보를 확인할 수 있습니다. 이는 데이터베이스의 기본적인 건강 상태를 빠르게 파악하는 데 유용합니다.
    ```sql
    STATUS;
    ```
    **주요 출력 항목:**
    *   `Uptime`: 서버가 가동된 시간.
    *   `Threads`: 현재 활성화된 클라이언트 연결 수.
    *   `Questions`: 서버 시작 이후 실행된 쿼리 수.
    *   `Slow queries`: `long_query_time` 설정보다 오래 걸린 쿼리 수. (성능 문제 진단에 중요)
    *   `Open tables`: 현재 열려 있는 테이블 수.
    *   `Connections`: 서버 시작 이후 총 연결 시도 횟수.

*   **상세 상태 및 설정 변수 확인 (`SHOW VARIABLES`, `SHOW STATUS`):**
    더 상세한 서버 설정(`VARIABLES`)이나 실시간 상태 지표(`STATUS`)를 확인하려면 `SHOW VARIABLES LIKE '변수명';` 또는 `SHOW STATUS LIKE '지표명';` 명령어를 사용합니다.
    ```sql
    -- MySQL 서버가 사용하는 포트 확인
    SHOW VARIABLES LIKE 'port';

    -- 현재 활성화된 연결 수 확인
    SHOW STATUS LIKE 'Threads_connected';

    -- InnoDB 버퍼 풀 사용량 확인 (성능 튜닝에 중요)
    SHOW STATUS LIKE 'Innodb_buffer_pool_reads';
    SHOW STATUS LIKE 'Innodb_buffer_pool_read_requests';
    ```

*   **접속 종료:**
    ```sql
    EXIT;
    ```
    또는
    ```sql
    QUIT;
    ```

**실무 팁:**
*   **`SHOW PROCESSLIST;` 활용:** 현재 실행 중인 쿼리 목록을 확인하여 느린 쿼리나 잠금(Lock) 상태의 쿼리를 식별할 수 있습니다. `SHOW FULL PROCESSLIST;`는 전체 쿼리 텍스트를 보여줍니다.
*   **정기적인 모니터링:** `STATUS;`나 `SHOW` 명령어를 통해 주기적으로 서버 상태를 확인하는 습관을 들이는 것이 좋습니다. 이는 잠재적인 성능 문제를 조기에 발견하는 데 도움이 됩니다.

### 3.2. 데이터베이스 생성 및 SQL 스크립트 복원 (데이터 분석 프로젝트의 시작)

데이터 분석 프로젝트를 시작하기 전에 데이터를 저장할 공간인 데이터베이스를 생성하고, 필요한 경우 기존 SQL 스크립트 파일을 통해 샘플 데이터나 테이블 구조를 복원할 수 있습니다.

*   **데이터베이스 목록 확인:**
    ```sql
    SHOW DATABASES;
    ```
    이 명령어를 통해 현재 MySQL 서버에 어떤 데이터베이스들이 존재하는지 확인할 수 있습니다.

*   **새 데이터베이스 생성:**
    ```sql
    CREATE DATABASE company_db;
    ```
    데이터베이스 이름은 소문자와 언더스코어를 사용하는 것이 일반적입니다. (예: `my_project_db`, `sales_data_warehouse`)
    **실무 팁:** 데이터베이스 이름은 해당 데이터베이스의 목적을 명확히 나타내도록 짓는 것이 좋습니다. 또한, 한글이나 특수문자보다는 영문 소문자와 언더스코어(`_`) 조합을 사용하는 것이 호환성 측면에서 안전합니다.

*   **데이터베이스 선택:**
    쿼리를 실행할 데이터베이스를 선택합니다. 이 명령어를 실행한 후부터는 명시적으로 다른 데이터베이스를 지정하지 않는 한, 모든 DDL/DML 작업은 이 데이터베이스 내에서 이루어집니다.
    ```sql
    USE my_project_db;
    ```
    현재 선택된 데이터베이스를 확인하려면 `SELECT DATABASE();` 명령을 사용합니다.

*   **SQL 스크립트 복원 (외부 파일 로드):**
    미리 준비된 `.sql` 파일(예: 샘플 데이터, 테이블 구조)을 데이터베이스에 로드할 때 사용합니다. 이는 데이터베이스를 초기화하거나, 다른 시스템에서 가져온 데이터를 로드할 때 유용합니다.
    *   **MySQL CLI에서 접속한 상태에서 `SOURCE` 명령어 사용:**
        ```bash
        SOURCE C:/path/to/your/sample_data.sql;
        ```
        *   **장점:** MySQL CLI에 접속한 상태에서 바로 실행할 수 있습니다.
        *   **주의:** 파일 경로를 정확히 지정해야 하며, Windows에서는 백슬래시(``) 대신 슬래시(`/`)를 사용하거나 이중 백슬래시(``)를 사용해야 합니다.
    *   **명령 프롬프트(터미널)에서 리다이렉션(` < `) 사용:**
        MySQL CLI에 접속하기 전에 명령 프롬프트에서 바로 SQL 파일을 실행할 수도 있습니다. 이 방법은 특히 대용량 SQL 파일을 로드할 때 유용합니다.
        ```bash
        mysql -u root -p my_project_db < C:/path/to/your/sample_data.sql
        ```
        *   **장점:** MySQL 클라이언트가 직접 파일을 읽어 서버로 전송하므로, 대용량 파일 로드에 더 효율적일 수 있습니다.
        *   **주의:** `my_project_db`는 데이터를 로드할 대상 데이터베이스 이름입니다. 이 데이터베이스는 미리 생성되어 있어야 합니다.

**실무 팁: 대용량 SQL 파일 복원 시 고려사항**
*   **`max_allowed_packet`:** 대용량 SQL 파일을 복원할 때 `Packet for query is too large` 오류가 발생할 수 있습니다. 이는 MySQL 서버의 `max_allowed_packet` 설정값이 너무 작기 때문입니다. `my.ini` 또는 `my.cnf` 파일에서 이 값을 충분히 크게 늘려야 합니다. (예: `max_allowed_packet = 256M`)
*   **`innodb_buffer_pool_size`:** 대량의 데이터를 로드할 때는 `innodb_buffer_pool_size`를 충분히 확보하여 디스크 I/O를 줄이는 것이 좋습니다.
*   **트랜잭션:** 대용량 데이터 로드 시에는 단일 트랜잭션으로 처리하기보다, 여러 개의 작은 트랜잭션으로 나누어 커밋하는 것이 메모리 사용량과 복구 시간을 줄이는 데 도움이 될 수 있습니다. (SQL 파일에 `COMMIT;`이 포함되어 있지 않다면 `autocommit` 설정을 확인해야 합니다.)

### 3.2.1. 데이터베이스 생성 시 인코딩 및 콜레이션 설정 (실무적 의미)
데이터베이스를 생성할 때 문자 인코딩(Character Set)과 콜레이션(Collation)을 명시적으로 지정하는 것은 매우 중요합니다.
```sql
CREATE DATABASE my_project_db
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```
*   **`CHARACTER SET utf8mb4`**: 데이터베이스가 한글, 일본어, 중국어, 그리고 이모지(Emoji)와 같은 4바이트 유니코드 문자까지 모두 올바르게 저장하고 처리할 수 있도록 설정합니다. `utf8`은 3바이트 문자까지만 지원하므로, `utf8mb4`를 사용하는 것이 현대적인 웹 환경과 데이터 분석에 필수적입니다.
*   **`COLLATE utf8mb4_unicode_ci`**: 문자열을 정렬하고 비교하는 규칙을 정의합니다. `_unicode_ci`는 유니코드 표준에 따라 정렬하며, 대소문자를 구분하지 않는(case-insensitive) 비교를 의미합니다.

### 3.3. 사용자 생성 및 권한 부여 (DCL 기초: 보안의 시작)

실무에서는 `root` 계정(모든 권한을 가진 최고 관리자 계정)을 직접 사용하여 데이터베이스에 접근하는 것은 **매우 위험합니다.** `root` 계정은 시스템 관리 목적으로만 사용하고, 실제 애플리케이션이나 데이터 분석 작업에는 **최소한의 권한을 가진 별도의 사용자 계정을 생성하여 사용하는 것이 보안상 강력히 권장됩니다.** DCL(Data Control Language)은 데이터베이스 접근 권한을 제어하는 명령어입니다.

*   **새 사용자 생성:**
    ```sql
    CREATE USER 'new_user'@'localhost' IDENTIFIED BY 'user_password';
    ```
    *   `'new_user'`: 생성할 사용자 이름입니다.
    *   `'localhost'`: 사용자가 접속을 허용할 호스트를 지정합니다. `'localhost'`는 로컬 PC에서만 접속을 허용하며, `'%'`는 모든 호스트에서 접속을 허용합니다. (운영 환경에서는 특정 IP 주소나 서브넷을 지정하는 것이 보안상 안전합니다.)
    *   `'user_password'`: 사용자 계정의 비밀번호입니다. 강력한 비밀번호를 사용해야 합니다.

*   **권한 부여 (`GRANT`):**
    `GRANT` 문을 사용하여 특정 데이터베이스, 테이블, 또는 컬럼에 대해 사용자에게 필요한 권한을 부여합니다. 필요한 권한만 정확히 부여하는 것이 **최소 권한의 원칙(Principle of Least Privilege)**을 지키는 것입니다.
    ```sql
    -- 예시 1: my_project_db 데이터베이스의 모든 테이블에 대해 new_user에게 모든 권한 부여 (개발/테스트 환경에서만 사용)
    GRANT ALL PRIVILEGES ON my_project_db.* TO 'new_user'@'localhost';

    -- 예시 2: my_project_db 데이터베이스의 employees 테이블에 대해 SELECT, INSERT, UPDATE, DELETE 권한 부여
    GRANT SELECT, INSERT, UPDATE, DELETE ON my_project_db.employees TO 'new_user'@'localhost';

    -- 예시 3: my_project_db 데이터베이스의 모든 테이블에 대해 SELECT 권한만 부여 (데이터 분석가에게 가장 일반적인 권한)
    GRANT SELECT ON my_project_db.* TO 'analyst_user'@'localhost';

    -- 예시 4: 특정 컬럼에 대한 권한 부여 (더 세밀한 제어)
    -- GRANT UPDATE(salary) ON my_project_db.employees TO 'hr_user'@'localhost';
    ```

*   **권한 적용 (`FLUSH PRIVILEGES`):**
    권한 변경 사항을 즉시 적용합니다. MySQL 8.0부터는 `GRANT`나 `REVOKE` 명령어가 자동으로 권한 캐시를 갱신하므로, 대부분의 경우 `FLUSH PRIVILEGES`를 명시적으로 호출할 필요가 없습니다. 하지만 이전 버전과의 호환성이나 특정 상황에서는 여전히 유용할 수 있습니다.
    ```sql
    FLUSH PRIVILEGES;
    ```

*   **권한 회수 (`REVOKE`):**
    부여했던 권한을 회수할 때 사용합니다.
    ```sql
    REVOKE ALL PRIVILEGES ON my_project_db.* FROM 'new_user'@'localhost';
    ```

**실무 팁: 사용자 계정 관리의 중요성**
*   **계정 분리:** 개발, 테스트, 운영 환경별로 계정을 분리하고, 각 계정에는 필요한 최소한의 권한만 부여합니다.
*   **비밀번호 정책:** 강력한 비밀번호 정책을 적용하고, 주기적으로 비밀번호를 변경하도록 강제합니다.
*   **사용자 감사:** 데이터베이스 접근 로그를 주기적으로 감사하여 비정상적인 접근이나 활동을 탐지합니다.
*   **권한 관리 도구:** 대규모 환경에서는 권한 관리를 위한 전문 도구나 스크립트를 활용하여 휴먼 에러를 줄이고 효율성을 높입니다.

### 3.3.1. `FLUSH PRIVILEGES`의 대안 (MySQL 8.0+)
MySQL 8.0 이상에서는 `GRANT` 또는 `REVOKE` 명령어가 자동으로 권한 캐시를 갱신하므로, 일반적으로 `FLUSH PRIVILEGES`를 명시적으로 호출할 필요가 없습니다. 만약 특정 이유로 권한 캐시를 수동으로 갱신해야 한다면, `FLUSH PRIVILEGES` 대신 `SET GLOBAL read_only = ON;` 후 `SET GLOBAL read_only = OFF;`와 같이 서버를 잠시 읽기 전용 모드로 전환하는 방법을 고려할 수 있습니다. 이는 서버 전체에 미치는 영향을 최소화하면서 권한을 갱신하는 방법 중 하나입니다. (하지만 이 역시 운영 중인 시스템에서는 신중하게 사용해야 합니다.)

### 3.3.2. [실무 노트] 최소 권한의 원칙: 데이터 분석가의 기본 소양
> **"최소 권한의 원칙(Principle of Least Privilege)"**은 보안의 가장 기본 원칙이자, 동료와의 신뢰를 지키는 핵심적인 약속입니다. 데이터 분석가는 운영 DB에 접근하는 경우가 많으므로, 실수로 데이터를 변경하거나 삭제하는 사고를 방지하기 위해 반드시 이 원칙을 지켜야 합니다.
>
> *   **분석가의 권한:** 일반적으로 데이터 조회(`SELECT`) 권한만 가집니다.
> *   **`GRANT ALL PRIVILEGES`는 절대 금물:** 개발 환경이 아닌 이상 이 명령어는 사용하지 않습니다. 필요한 권한(`SELECT`, `INSERT` 등)만 명시적으로 부여하는 것이 안전합니다.
> *   **샌드박스 환경:** 데이터 변경이 필요한 분석 작업(예: 데이터 클렌징, 피처 엔지니어링)은 운영 DB를 복제한 별도의 **분석용 샌드박스(Sandbox) 데이터베이스**에서 수행하는 것이 일반적입니다. 이를 통해 운영 환경에 영향을 주지 않고 자유롭게 데이터를 탐색하고 가공할 수 있습니다.
> *   **권한 요청:** 만약 `SELECT` 외의 권한이 필요하다면, **정확히 어떤 작업을 위해(WHY), 어떤 테이블에(WHAT), 어떤 권한이(HOW) 필요한지** 명확히 정리하여 데이터 엔지니어 또는 DBA에게 요청하는 것이 올바른 협업 방식입니다.

## 4. SQL과 관계형 데이터베이스(RDB)의 기본

데이터 분석가에게 SQL은 데이터와 소통하는 언어이며, 관계형 데이터베이스는 그 데이터가 저장되는 구조입니다. 이 둘의 기본 개념을 이해하는 것은 매우 중요합니다.

### 4.1. SQL이란? (Structured Query Language)

> **현업 데이터 분석가의 관점 한 줄 요약:**
> SQL은 데이터 분석가의 '모국어'입니다. 데이터베이스와 직접 소통하고, 원하는 데이터를 추출하며, 복잡한 비즈니스 질문에 답하기 위한 가장 강력하고 보편적인 도구입니다. 단순히 문법을 아는 것을 넘어, SQL을 통해 데이터의 구조를 이해하고, 효율적인 쿼리를 작성하는 능력은 데이터 분석가의 핵심 경쟁력입니다.

SQL은 관계형 데이터베이스 시스템에서 데이터를 관리하고 처리하기 위해 설계된 표준 언어입니다.

#### 4.1.1. SQL의 역사와 표준

*   **역사:** 1970년대 IBM에서 개발된 SEQUEL(Structured English Query Language)에서 시작하여, 1986년 ANSI(미국 표준 협회)에 의해 표준화되었습니다. 이후 ISO(국제 표준화 기구)에서도 표준으로 채택되어 현재까지 발전하고 있습니다.
*   **표준:** SQL은 표준이 존재하지만, 각 데이터베이스 벤더(MySQL, PostgreSQL, Oracle, SQL Server 등)는 표준 SQL에 자신들만의 확장 기능을 추가하여 사용합니다. 따라서 특정 DBMS에서만 동작하는 문법이 있을 수 있습니다.

#### 4.1.1.1. [실무 노트] SQL 방언(Dialect)과 호환성 문제 대처법
> SQL은 표준이 있지만, 각 DBMS(MySQL, PostgreSQL, Oracle 등)는 자신만의 고유한 함수와 문법(방언)을 가지고 있습니다. 데이터 분석가는 여러 DBMS를 다룰 가능성이 높으므로, 이 차이를 이해하고 **이식성 높은(portable) 코드**를 작성하는 능력이 중요합니다.
>
> **[주요 방언 차이 및 해결 전략]**
>
> | 기능 | MySQL | PostgreSQL | SQL Server | **권장 해결 전략** |
> | :--- | :--- | :--- | :--- | :--- |
> | **TOP N 로우** | `LIMIT N` | `LIMIT N` | `TOP N` | ANSI 표준인 **`FETCH FIRST N ROWS ONLY`** 사용을 고려하거나, 각 DBMS에 맞는 문법을 조건부로 사용합니다. |
> | **NULL 처리** | `IFNULL(A, B)` | `COALESCE(A, B)` | `ISNULL(A, B)` | 대부분의 DBMS가 지원하는 표준 함수 **`COALESCE(A, B, C, ...)`** 사용을 습관화하는 것이 좋습니다. |
> | **문자열 합치기** | `CONCAT()` | `||` | `+` | 표준 함수인 **`CONCAT()`**을 우선적으로 사용합니다. |
> | **조건부 로직** | `IF()` | `CASE WHEN` | `CASE WHEN` | 모든 DBMS에서 지원하는 표준 **`CASE WHEN ... END`** 구문을 사용합니다. |
>
> **핵심 전략:**
> 1.  **표준 SQL(ANSI SQL)을 최우선으로 사용합니다.** 이는 코드의 재사용성과 이식성을 높이는 가장 확실한 방법입니다.
> 2.  특정 DBMS의 강력한 분석 함수(예: PostgreSQL의 `jsonb` 함수)를 사용해야 할 경우, 해당 코드가 **특정 DBMS에 종속적임을 주석으로 명확히 명시**하여 다른 동료나 미래의 자신이 혼동하지 않도록 합니다.
> 3.  파이썬과 함께 작업할 경우, **SQLAlchemy**와 같은 라이브러리는 이러한 방언 차이를 추상화하여 동일한 코드로 여러 DBMS와 상호작용할 수 있게 도와줍니다.

#### 4.1.2. SQL의 역할과 중요성 (데이터 분석가의 핵심 역량)

SQL은 단순한 데이터 조회 언어를 넘어, 데이터베이스 시스템을 관리하고 데이터를 분석하는 데 필요한 다양한 역할을 수행합니다. 데이터 분석가에게 SQL은 데이터에 직접 접근하고, 원하는 형태로 가공하며, 비즈니스 인사이트를 도출하는 핵심 도구입니다.

*   **데이터 정의 (DDL - Data Definition Language):**
    *   **역할:** 테이블, 뷰, 인덱스, 데이터베이스 등 데이터베이스 객체의 구조를 정의, 변경, 삭제합니다. 데이터가 저장될 '틀'을 만드는 작업입니다.
    *   **중요성:** 데이터 분석가는 직접 테이블을 생성할 일은 많지 않지만, 기존 테이블의 스키마(구조)를 이해하고, 필요에 따라 임시 테이블을 생성하여 분석에 활용하는 데 필수적인 지식입니다.

*   **데이터 조작 (DML - Data Manipulation Language):**
    *   **역할:** 데이터베이스 내의 실제 데이터를 조회(`SELECT`), 삽입(`INSERT`), 수정(`UPDATE`), 삭제(`DELETE`)합니다.
    *   **중요성:** 데이터 분석가의 업무 중 가장 많은 부분을 차지합니다. 원하는 데이터를 추출하고, 전처리하며, 분석에 필요한 형태로 가공하는 모든 과정에 DML, 특히 `SELECT` 문이 사용됩니다.

*   **데이터 제어 (DCL - Data Control Language):**
    *   **역할:** 데이터베이스에 대한 접근 권한(`GRANT`, `REVOKE`) 및 보안을 제어합니다.
    *   **중요성:** 데이터 분석가는 운영 데이터베이스에 접근할 때 최소 권한의 원칙을 이해하고, 필요한 권한을 요청하며, 데이터 보안의 중요성을 인지해야 합니다.

*   **트랜잭션 제어 (TCL - Transaction Control Language):**
    *   **역할:** 데이터의 일관성과 무결성을 유지하기 위해 트랜잭션(`COMMIT`, `ROLLBACK`, `SAVEPOINT`)을 제어합니다.
    *   **중요성:** 데이터 변경 작업 시 데이터의 신뢰성을 보장하는 데 필수적입니다. 특히 분석을 위해 데이터를 가공하거나 임시 테이블에 저장할 때 데이터 일관성을 유지하는 데 중요한 역할을 합니다.

*   **데이터 분석:**
    *   **역할:** 복잡한 쿼리를 통해 데이터를 집계하고 분석하여 비즈니스 인사이트를 도출합니다.
    *   **중요성:** SQL은 대규모 데이터를 효율적으로 처리하고, 다양한 분석 함수와 그룹화 기능을 통해 비즈니스 질문에 대한 답을 찾는 데 가장 강력한 도구입니다. 데이터 기반 의사결정의 핵심 기반이 됩니다.

#### 4.1.3. SQL 주석 (Comments): 코드 가독성 및 협업

SQL 주석은 쿼리 코드 내에 설명을 추가하여 코드의 가독성을 높이고, 다른 사람과의 협업을 용이하게 합니다. 데이터베이스 시스템은 주석을 무시하고 쿼리를 실행합니다.

*   **한 줄 주석 (`--`):**
    `--` 뒤에 오는 내용은 해당 줄의 끝까지 주석으로 처리됩니다.
    ```sql
    SELECT employee_id, first_name -- 직원 ID와 이름 조회
    FROM employees;
    ```

*   **여러 줄 주석 (`/* ... */`):**
    `/*`와 `*/` 사이에 오는 모든 내용은 여러 줄에 걸쳐 주석으로 처리됩니다.
    ```sql
    /*
    이 쿼리는 employees 테이블에서
    급여가 50000 이상인 직원을 조회합니다.
    작성자: Alpine_Dolce
    */
    SELECT employee_id, first_name, salary
    FROM employees
    WHERE salary >= 50000;
    ```

**실무적 활용:**
*   **쿼리 설명:** 복잡한 쿼리 로직이나 특정 조건에 대한 설명을 추가하여 나중에 쿼리를 다시 보거나 다른 사람이 이해할 때 도움을 줍니다.
*   **변경 이력:** 쿼리 수정 시 변경된 내용, 날짜, 작성자 등을 기록하여 버전 관리에 준하는 효과를 얻을 수 있습니다.
*   **디버깅:** 특정 SQL 구문을 임시로 비활성화할 때 주석 처리하여 디버깅에 활용할 수 있습니다.
*   **협업:** 팀원 간 쿼리를 공유할 때 주석을 통해 의도를 명확히 전달하고 소통 오류를 줄일 수 있습니다.

#### 4.1.4. SQL 표준과 비표준 (ANSI SQL vs. Vendor-Specific SQL)

##### 4.1.4.1. SQL 코딩 컨벤션의 중요성 (실무적 관점)
실무는 혼자 일하는 공간이 아닌, 여러 동료와 함께 코드를 공유하고 유지보수하는 협업의 장입니다. 따라서 일관된 **코딩 컨벤션(Coding Convention)**을 따르는 것은 매우 중요합니다. 깔끔하고 예측 가능한 코드는 가독성을 높여 실수를 줄이고, 동료가 코드를 쉽게 이해하고 수정할 수 있도록 돕습니다.
*   **일반적인 SQL 코딩 컨벤션 예시:**
    *   **키워드는 대문자로 작성:** `SELECT`, `FROM`, `WHERE`, `GROUP BY` 등 SQL 예약어는 대문자로 작성하여 코드의 구조를 명확히 합니다.
    *   **테이블, 컬럼명은 소문자로 작성:** `employees`, `department_name` 등은 소문자로 작성하여 키워드와 구분합니다.
    *   **적절한 들여쓰기:** `JOIN`, 서브쿼리 등은 논리적인 구조에 맞게 들여쓰기하여 가독성을 높입니다.
    *   **의미 있는 별칭(Alias) 사용:** `e`, `d` 와 같이 너무 짧은 별칭보다는 `emp`, `dept` 처럼 의미를 유추할 수 있는 별칭을 사용하는 것이 좋습니다.
*   팀에 합류하면 가장 먼저 팀의 코딩 컨벤션을 확인하고 따르는 것이 원활한 협업의 첫걸음입니다.

SQL은 ANSI(미국 표준 협회)와 ISO(국제 표준화 기구)에 의해 표준화된 언어이지만, 실제로는 각 데이터베이스 관리 시스템(DBMS) 벤더(MySQL, PostgreSQL, Oracle, SQL Server 등)가 표준 SQL에 자신들만의 고유한 기능과 문법(방언, Dialect)을 추가하여 사용합니다. 데이터 분석가는 이러한 표준과 비표준의 차이를 이해하는 것이 중요합니다.

*   **ANSI SQL (표준 SQL):**
    *   대부분의 DBMS에서 공통적으로 지원하는 문법과 기능을 정의합니다.
    *   `SELECT`, `FROM`, `WHERE`, `GROUP BY`, `ORDER BY`, `INNER JOIN`, `LEFT JOIN`, `CREATE TABLE`, `INSERT`, `UPDATE`, `DELETE`, `COMMIT`, `ROLLBACK` 등 기본적인 DDL, DML, TCL 명령어는 표준 SQL에 속합니다.
    *   **장점:** 코드의 이식성이 높아 다른 DBMS로 전환하거나 여러 DBMS를 동시에 다룰 때 유리합니다.
    *   **단점:** 특정 DBMS의 강력한 최적화 기능이나 고유한 분석 함수를 활용하지 못할 수 있습니다.

*   **Vendor-Specific SQL (비표준 SQL 또는 방언):**
    *   각 DBMS 벤더가 자사 제품의 성능, 기능, 특정 사용 사례에 최적화하기 위해 추가한 고유한 문법과 기능입니다.
    *   **예시:**
        *   **MySQL:** `LIMIT` (로우 제한), `INSERT ... ON DUPLICATE KEY UPDATE`, `GROUP_CONCAT()`, `IF()` 함수, `LOAD DATA INFILE` 등
        *   **PostgreSQL:** `LATERAL JOIN`, `JSONB` 데이터 타입 및 관련 함수, `GENERATE_SERIES()`, `DISTINCT ON` 등
        *   **Oracle:** `ROWNUM` (로우 제한), `CONNECT BY` (계층 쿼리), `DECODE()` 함수, `Materialized View` 등
        *   **SQL Server:** `TOP` (로우 제한), `PIVOT`/`UNPIVOT`, `APPLY` 연산자 등
    *   **장점:** 특정 DBMS의 강력한 기능을 활용하여 성능을 극대화하거나 복잡한 문제를 효율적으로 해결할 수 있습니다.
    *   **단점:** 코드의 이식성이 낮아 다른 DBMS로 전환 시 코드 수정이 필요하며, 학습 비용이 증가할 수 있습니다.

**데이터 분석 실무에서의 고려사항:**
*   **이식성 vs. 성능/기능:** 분석 프로젝트의 요구사항에 따라 표준 SQL을 고수할지, 아니면 특정 DBMS의 비표준 기능을 적극적으로 활용할지 결정해야 합니다. 초기 단계에서는 표준 SQL을 우선하되, 성능 병목이나 특정 기능이 필요할 때 비표준 기능을 도입하는 것이 일반적입니다.
*   **문서화:** 비표준 SQL을 사용할 경우, 해당 부분이 어떤 DBMS의 어떤 기능인지 명확히 문서화하여 다른 팀원이나 미래의 자신을 위해 기록을 남기는 것이 중요합니다.
*   **추상화 계층:** 파이썬의 SQLAlchemy와 같은 라이브러리는 DBMS별 방언 차이를 추상화하여 개발자가 동일한 코드로 여러 DBMS와 상호작용할 수 있도록 돕습니다. 이는 특히 애플리케이션 개발 시 유용합니다.

##### 4.1.4.2. 데이터 분석가를 위한 RDBMS 선택 고려사항
데이터 분석 프로젝트에서는 목적에 따라 적합한 RDBMS를 선택하는 것이 중요합니다.
*   **MySQL:** 웹 서비스 백엔드에 널리 사용되며, 설치 및 관리가 비교적 쉽습니다. 대규모 트랜잭션 처리보다는 읽기(Read) 성능에 강점이 있습니다.
*   **PostgreSQL:** 객체-관계형 데이터베이스로, SQL 표준을 잘 준수하며 확장성이 뛰어납니다. 복잡한 분석 쿼리, 지리 정보 시스템(GIS), JSONB와 같은 반정형 데이터 처리에 강점이 있어 데이터 분석 및 과학 분야에서 인기가 높습니다.
*   **SQL Server (Microsoft):** Windows 환경에 최적화되어 있으며, BI(Business Intelligence) 도구와의 연동이 강력합니다.
*   **Oracle:** 대규모 엔터프라이즈 환경에서 가장 널리 사용되는 상용 DBMS로, 강력한 안정성과 성능을 자랑합니다.
*   **SQLite:** 서버 없이 파일 기반으로 동작하는 경량 데이터베이스입니다. 별도의 설치나 설정이 필요 없어 파이썬 애플리케이션에 내장하거나 소규모 데이터 분석, 프로토타이핑에 매우 유용합니다.
데이터 분석가는 주로 데이터 추출 및 분석에 집중하므로, 분석 함수 지원, JSON 데이터 처리 능력, 그리고 커뮤니티 지원 등을 고려하여 DBMS를 선택할 수 있습니다.

### 4.2. SQL 명령어의 4가지 분류 (SQL의 언어 구조 이해)

SQL 명령어는 기능과 목적에 따라 크게 4가지로 분류할 수 있습니다. 이 분류를 이해하는 것은 SQL 쿼리의 구조를 파악하고, 데이터베이스 시스템의 동작 원리를 이해하는 데 도움이 됩니다.

#### 4.2.1. DDL (Data Definition Language): 데이터 정의어

데이터베이스 객체(테이블, 뷰, 인덱스 등)의 구조를 정의, 변경, 삭제하는 명령어입니다. 데이터 자체보다는 데이터가 저장될 "틀"을 다룹니다.

*   `CREATE`: 데이터베이스, 테이블, 뷰, 인덱스 등을 생성합니다.
*   `ALTER`: 기존 데이터베이스 객체의 구조를 변경합니다. (예: 테이블에 컬럼 추가/삭제, 제약조건 변경)
*   `DROP`: 데이터베이스, 테이블, 뷰, 인덱스 등을 완전히 삭제합니다.
*   `TRUNCATE`: 테이블의 모든 데이터를 삭제하고, 테이블 구조는 남겨둡니다. (DDL로 분류되기도 하며, `DELETE`와 달리 롤백 불가)

**데이터 분석가에게 DDL의 의미:** 직접 DDL을 사용할 일은 많지 않지만, 데이터베이스의 스키마를 이해하고, 분석에 필요한 임시 테이블을 생성하거나 기존 테이블의 구조를 파악하는 데 필수적인 개념입니다.

#### 4.2.2. DML (Data Manipulation Language): 데이터 조작어

데이터베이스 내의 실제 데이터를 조회, 삽입, 수정, 삭제하는 명령어입니다. 데이터 분석가의 업무에서 가장 빈번하게 사용되는 명령어 그룹입니다.

*   `SELECT`: 데이터베이스에서 데이터를 조회합니다. (데이터 분석의 핵심)
*   `INSERT`: 테이블에 새로운 데이터를 삽입합니다.
*   `UPDATE`: 테이블의 기존 데이터를 수정합니다.
*   `DELETE`: 테이블의 데이터를 삭제합니다.

**데이터 분석가에게 DML의 의미:** `SELECT`는 데이터 분석의 시작이자 끝입니다. `INSERT`, `UPDATE`, `DELETE`는 주로 데이터 전처리, 클렌징, 또는 분석 결과를 데이터베이스에 저장할 때 사용됩니다.

#### 4.2.3. DCL (Data Control Language): 데이터 제어어

데이터베이스에 대한 접근 권한 및 보안을 제어하는 명령어입니다. 데이터의 보안과 무결성을 관리하는 데 사용됩니다.

*   `GRANT`: 사용자에게 특정 권한을 부여합니다.
*   `REVOKE`: 사용자에게 부여된 권한을 회수합니다.

**데이터 분석가에게 DCL의 의미:** 운영 데이터베이스에 접근할 때 필요한 권한을 이해하고, 최소 권한의 원칙을 준수하며, 데이터 보안의 중요성을 인지하는 데 필요합니다.

#### 4.2.4. TCL (Transaction Control Language): 트랜잭션 제어어

데이터의 일관성과 무결성을 유지하기 위해 트랜잭션을 제어하는 명령어입니다. 트랜잭션은 데이터베이스의 논리적인 작업 단위입니다. **데이터 분석가가 DML 작업을 수행할 때 데이터의 무결성을 보장하기 위해 반드시 이해하고 활용해야 하는 매우 중요한 개념입니다.**

*   `COMMIT`: 트랜잭션 내의 모든 변경 사항을 영구적으로 데이터베이스에 반영합니다.
*   `ROLLBACK`: 트랜잭션 내의 모든 변경 사항을 취소하고 이전 상태로 되돌립니다.
*   `SAVEPOINT`: 트랜잭션 내에서 롤백할 지점을 지정합니다.

**데이터 분석가에게 TCL의 의미:** 데이터 변경 작업 시 데이터의 신뢰성을 확보하고, 오류 발생 시 데이터를 안전하게 복구하는 데 필수적입니다. 특히 여러 단계의 데이터 조작이 필요한 배치 작업에서 중요하게 활용됩니다.

### 4.3. 관계형 데이터베이스의 구조 (데이터의 논리적 설계)

> **현업 데이터 분석가의 관점 한 줄 요약:**
> 관계형 데이터베이스는 데이터를 효율적이고 일관되게 관리하기 위한 강력한 프레임워크입니다. 테이블, 컬럼, 로우, 그리고 키의 개념을 명확히 이해하는 것은 복잡한 데이터를 효과적으로 쿼리하고, 데이터 모델을 분석하며, 비즈니스 로직을 데이터 구조와 연결 짓는 데 필수적인 기초 지식입니다.

관계형 데이터베이스(RDB)는 데이터를 테이블(Table)이라는 2차원 구조로 저장하고, 이 테이블들 간의 관계를 통해 데이터를 관리합니다.

#### 4.3.1. 테이블(Table), 컬럼(Column), 로우(Row) (데이터의 기본 구성 요소)

관계형 데이터베이스의 데이터는 테이블이라는 구조 내에 저장됩니다. 테이블은 스프레드시트와 유사하게 행과 열로 구성됩니다.

*   **테이블 (Table):**
    *   **개념:** 데이터를 저장하는 기본 단위이자, 특정 주제에 대한 데이터를 구조화하여 저장하는 2차원 구조입니다. (예: `employees` 테이블, `products` 테이블)
    *   **역할:** 데이터의 논리적인 집합을 나타내며, 데이터베이스 설계의 핵심 요소입니다.

*   **컬럼 (Column):**
    *   **개념:** 테이블의 각 열을 의미하며, 특정 속성(Attribute)을 나타냅니다. 각 컬럼은 고유한 이름과 데이터 타입(예: 숫자, 문자열, 날짜)을 가집니다.
    *   **역할:** 데이터의 종류와 형식을 정의하며, 데이터의 무결성을 보장하는 제약조건이 적용될 수 있습니다. (예: `employee_id`, `first_name`, `salary`)
    *   **데이터 분석가에게:** 컬럼의 이름과 데이터 타입을 정확히 이해하는 것은 쿼리 작성의 첫걸음입니다. 어떤 컬럼에 어떤 데이터가 들어있는지 알아야 올바른 분석을 수행할 수 있습니다.

*   **로우 (Row):**
    *   **개념:** 테이블의 각 행을 의미하며, 하나의 레코드(Record) 또는 튜플(Tuple)이라고도 합니다. 각 로우는 특정 개체(Entity)에 대한 모든 속성 값의 집합입니다.
    *   **역할:** 실제 데이터의 개별 인스턴스를 나타냅니다. (예: 특정 직원 한 명의 모든 정보)
    *   **데이터 분석가에게:** `SELECT` 쿼리의 결과는 기본적으로 로우들의 집합으로 반환됩니다. 각 로우가 의미하는 바를 정확히 파악하는 것이 중요합니다.

#### 4.3.1.1. 인덱스 (Index)
*   **인덱스 (Index):** 테이블의 특정 컬럼에 대한 검색 속도를 향상시키는 데이터 구조입니다. 책의 찾아보기(색인)와 유사하며, `WHERE` 절이나 `JOIN` 조건에서 자주 사용되는 컬럼에 인덱스를 생성하면 쿼리 성능을 획기적으로 향상시킬 수 있습니다. (자세한 내용은 [08_성능튜닝과_인덱스.md](./08_성능튜닝과_인덱스.md)를 참조하세요.)

#### 4.3.2. 키(Key)의 종류와 역할 (Primary Key, Foreign Key) (데이터 관계의 핵심)

키(Key)는 관계형 데이터베이스에서 테이블 간의 관계를 설정하고 데이터의 무결성(Integrity)을 보장하는 데 사용되는 중요한 개념입니다. 키를 통해 데이터의 중복을 방지하고, 데이터 간의 논리적인 연결을 만듭니다.

*   **기본 키 (Primary Key, PK):**
    *   **개념:** 테이블의 각 로우를 고유하게 식별할 수 있는 하나 이상의 컬럼 조합입니다. 주민등록번호처럼 각 로우를 유일하게 구분하는 역할을 합니다.
    *   **특징:**
        *   `NULL` 값을 가질 수 없습니다 (`NOT NULL`).
        *   중복된 값을 가질 수 없습니다 (`UNIQUE`).
        *   테이블당 하나의 기본 키만 존재할 수 있습니다.
    *   **역할:** 데이터의 고유성을 보장하고, 다른 테이블과의 관계를 설정하는 데 사용되는 핵심 식별자입니다.
    *   **데이터 분석가에게:** 기본 키는 `JOIN` 연산의 핵심입니다. 어떤 컬럼이 기본 키인지 파악하면 테이블 간의 관계를 쉽게 이해하고, 정확한 `JOIN` 쿼리를 작성할 수 있습니다.

*   **외래 키 (Foreign Key, FK):**
    *   **개념:** 다른 테이블의 기본 키를 참조하는 컬럼입니다. 두 테이블 간의 논리적인 연결을 만듭니다.
    *   **역할:** **참조 무결성(Referential Integrity)**을 보장합니다. 즉, 외래 키 값은 참조하는 테이블의 기본 키 값으로 반드시 존재하거나 `NULL`이어야 합니다. 이를 통해 데이터의 일관성을 유지하고, 유효하지 않은 데이터가 삽입되는 것을 방지합니다.
    *   **예시:** `employees` 테이블의 `department_id` 컬럼이 `departments` 테이블의 `department_id` (기본 키)를 외래 키로 참조합니다. 이는 모든 직원이 유효한 부서에 속하도록 강제합니다.
    *   **데이터 분석가에게:** 외래 키는 테이블 간의 관계를 파악하고 `JOIN` 쿼리를 작성하는 데 필수적인 정보입니다. 외래 키를 통해 여러 테이블에 흩어진 데이터를 효과적으로 통합하여 분석할 수 있습니다.

**참조 무결성의 중요성 (실무적 관점):**
참조 무결성은 데이터베이스의 신뢰성을 보장하는 핵심 요소입니다. 만약 외래 키 제약조건이 없다면, 존재하지 않는 부서 ID를 가진 직원이 `employees` 테이블에 삽입될 수 있고, 이는 데이터의 불일치와 분석 결과의 왜곡으로 이어질 수 있습니다. 외래 키는 이러한 데이터 부정합을 방지하여 데이터의 품질을 높입니다.

#### 4.3.3. 스키마(Schema)와 데이터베이스 (데이터 구조의 논리적 분류)

데이터베이스 시스템에서 '데이터베이스'와 '스키마'는 종종 혼용되어 사용되지만, 엄밀히 말하면 다른 개념입니다. 하지만 MySQL에서는 이 둘을 거의 동일한 개념으로 취급합니다.

*   **데이터베이스 (Database):**
    *   **개념:** 관련된 데이터와 그 데이터를 관리하는 시스템(DBMS)의 집합입니다. 물리적인 저장 공간과 논리적인 데이터 집합을 모두 포함하는 상위 개념입니다.
    *   **역할:** 여러 스키마를 포함할 수 있으며, 데이터의 독립적인 관리 단위를 제공합니다.

*   **스키마 (Schema):**
    *   **개념:** 데이터베이스 내에서 데이터의 구조와 제약조건을 정의한 논리적인 단위입니다. 테이블, 뷰, 인덱스, 저장 프로시저 등 데이터베이스 객체들의 집합을 의미합니다.
    *   **MySQL에서의 특이점:** MySQL에서는 `CREATE DATABASE`는 `CREATE SCHEMA`와 동일하게 동작합니다. 즉, MySQL에서는 데이터베이스와 스키마가 거의 동일한 개념으로 사용됩니다. 다른 DBMS(예: PostgreSQL, Oracle)에서는 하나의 데이터베이스 안에 여러 스키마를 가질 수 있어, 스키마가 데이터베이스 객체들을 논리적으로 그룹화하는 역할을 합니다.
    *   **데이터 분석가에게:** 데이터 분석가는 특정 데이터베이스 내의 어떤 스키마(또는 MySQL에서는 데이터베이스)에 접근해야 하는지 정확히 알아야 합니다. 스키마를 이해하는 것은 데이터의 논리적인 분류와 구조를 파악하는 데 필수적입니다.
