## 1. 데이터 타입: 데이터의 형태 정의하기

데이터 타입은 데이터베이스 컬럼에 저장될 값의 종류와 형식을 정의합니다. 올바른 데이터 타입 선택은 데이터의 무결성, 저장 공간 효율성, 쿼리 성능에 큰 영향을 미칩니다.

### 1.1. 숫자형 타입 (INT, DECIMAL, FLOAT 등)

숫자 데이터를 저장하는 데 사용됩니다. 정수, 고정 소수점, 부동 소수점 등 다양한 종류가 있습니다.

| 타입 | 설명 | 범위 (MySQL 기준) | 사용 예시 |
| :--- | :--- | :--- | :--- |
| `TINYINT` | 매우 작은 정수 | -128 ~ 127 (signed), 0 ~ 255 (unsigned) | 나이, 상태 코드 |
| `SMALLINT` | 작은 정수 | -32768 ~ 32767 (signed) | 상품 재고 |
| `MEDIUMINT` | 중간 크기 정수 | -8388608 ~ 8388607 (signed) | |
| `INT` | 일반적인 정수 | -2147483648 ~ 2147483647 (signed) | 사용자 ID, 주문 수량 |
| `BIGINT` | 큰 정수 | -9223372036854775808 ~ 9223372036854775807 (signed) | 매우 큰 ID, 총 판매액 |
| `DECIMAL(M, D)` | 고정 소수점 숫자. `M`은 총 자릿수, `D`는 소수점 이하 자릿수. **정확한 금융 계산에 적합.** | `M`은 1~65, `D`는 0~30 | 가격, 통화, 정밀한 측정값 |
| `FLOAT(p)` | 단정밀도 부동 소수점 숫자. 근사치 저장. **부동 소수점 오차 발생 가능성 있음.** | 약 -3.402823466E+38 ~ 3.402823466E+38 | 과학 계산, 근사치가 허용되는 측정값 |
| `DOUBLE` | 배정밀도 부동 소수점 숫자. 근사치 저장. **부동 소수점 오차 발생 가능성 있음.** | 약 -1.7976931348623157E+308 ~ 1.7976931348623157E+308 | 더 높은 정밀도가 필요한 과학 계산 |

**`UNSIGNED` 속성:** 숫자형 타입 뒤에 `UNSIGNED`를 붙이면 음수 값을 저장할 수 없게 되어 양수 범위가 두 배로 늘어납니다. (예: `INT UNSIGNED`는 0 ~ 4294967295)

**`DECIMAL` vs `FLOAT`/`DOUBLE`:** 금융 데이터나 정확한 계산이 필요한 경우에는 `DECIMAL`을 사용해야 합니다. `FLOAT`나 `DOUBLE`은 부동 소수점 오차를 가질 수 있습니다.

### 1.2. 문자형 타입 (VARCHAR, CHAR, TEXT 등)

문자열 데이터를 저장하는 데 사용됩니다.

| 타입 | 설명 | 최대 길이 (MySQL 기준) | 사용 예시 |
| :--- | :--- | :--- | :--- |
| `CHAR(L)` | 고정 길이 문자열. `L`은 1~255. 항상 `L`만큼의 공간을 차지. | 255 | 성별, 우편번호 (길이가 고정된 경우) |
| `VARCHAR(L)` | 가변 길이 문자열. `L`은 1~65535. 실제 저장된 길이에 따라 공간 차지. | 65535 | 이름, 주소, 제목 |
| `TINYTEXT` | 매우 작은 텍스트 | 255 바이트 | 짧은 메모 |
| `TEXT` | 작은 텍스트 | 65535 바이트 | 긴 설명, 본문 |
| `MEDIUMTEXT` | 중간 크기 텍스트 | 16MB | 블로그 게시물 |
| `LONGTEXT` | 매우 큰 텍스트 | 4GB | 매우 긴 문서, 로그 |

**`TEXT` 계열 타입 (TEXT, MEDIUMTEXT, LONGTEXT) 사용 시 고려사항:**
`TEXT` 계열 타입은 대량의 문자열 데이터를 저장하는 데 유용하지만, 일반적인 `VARCHAR`와 달리 인덱싱에 제약이 있거나 인덱스 효율이 떨어질 수 있습니다. 특히 전체 텍스트 검색(Full-text search)이 필요한 경우에는 `FULLTEXT` 인덱스를 별도로 고려해야 합니다. `WHERE` 절에서 `LIKE '%keyword%'`와 같이 패턴 매칭을 할 경우 인덱스를 활용하기 어려워 성능 저하의 원인이 될 수 있습니다.

| `ENUM('val1', 'val2', ...)` | 미리 정의된 값 목록 중 하나만 저장 가능. | 65535개 값 | 요일, 상태 (승인, 대기, 거절) |
| `SET('val1', 'val2', ...)` | 미리 정의된 값 목록 중 여러 개를 선택하여 저장 가능. | 64개 값 | 취미 (독서, 운동, 영화) |

**`CHAR` vs `VARCHAR`:**
*   `CHAR`: 길이가 고정적이거나, 최대 길이까지 거의 항상 채워지는 데이터에 적합합니다. (예: 주민등록번호, 전화번호) 저장 공간 효율은 떨어지지만, 접근 속도가 빠를 수 있습니다.
*   `VARCHAR`: 길이가 가변적인 데이터에 적합합니다. (예: 이름, 주소) 저장 공간 효율이 좋지만, 접근 속도가 약간 느릴 수 있습니다.

*   **`ENUM` vs `FOREIGN KEY` (작은 고정 목록 관리):**
    *   **`ENUM`:** 미리 정의된 값 목록이 매우 작고, 변경될 가능성이 거의 없으며, 참조 무결성(Referential Integrity)이 엄격하게 요구되지 않을 때 사용합니다. (예: 성별, 요일) 저장 공간 효율이 좋고 쿼리가 간단합니다.
    *   **`FOREIGN KEY`:** 값 목록이 변경될 가능성이 있거나, 목록의 수가 많거나, 참조 무결성이 매우 중요할 때 별도의 참조(Lookup) 테이블을 만들고 `FOREIGN KEY`로 연결하는 것이 좋습니다. (예: 국가 코드, 상품 카테고리) 데이터 일관성과 유연성이 높습니다.

### 1.3. 날짜/시간 타입 (DATE, DATETIME, TIMESTAMP 등)

날짜와 시간 정보를 저장하는 데 사용됩니다.

| 타입 | 설명 | 범위 (MySQL 기준) | 사용 예시 |
| :--- | :--- | :--- | :--- |
| `DATE` | 날짜 (년, 월, 일) | '1000-01-01' ~ '9999-12-31' | 생년월일, 주문일 |
| `TIME` | 시간 (시, 분, 초) | '-838:59:59' ~ '838:59:59' | 근무 시작 시간 |
| `YEAR` | 연도 | 1901 ~ 2155 | 출판 연도 |
| `DATETIME` | 날짜와 시간 (년, 월, 일, 시, 분, 초) | '1000-01-01 00:00:00' ~ '9999-12-31 23:59:59' | 생성일시, 이벤트 시작 시간 |
| `TIMESTAMP` | 날짜와 시간 (UTC 기준). 타임존 변환이 자동으로 이루어짐. | '1970-01-01 00:00:01' UTC ~ '2038-01-19 03:14:07' UTC | 마지막 수정일시, 로그 기록 시간 |

**`DATETIME` vs `TIMESTAMP`:**
*   `DATETIME`: 서버의 타임존 설정에 영향을 받지 않고, 입력된 값을 그대로 저장합니다. 주로 특정 시점의 고정된 날짜/시간을 기록할 때 사용합니다.
*   `TIMESTAMP`: UTC(협정 세계시) 기준으로 저장되며, 조회 시 서버의 타임존에 맞춰 변환됩니다. 전 세계 사용자를 대상으로 하는 서비스나 타임존 변환이 필요한 경우에 적합합니다.

### 1.4. 기타 타입 (BOOLEAN, ENUM, JSON 등)

특수한 목적을 위한 데이터 타입입니다.

| 타입 | 설명 | 사용 예시 |
| :--- | :--- |
| `BOOLEAN` | 참/거짓 (MySQL에서는 `TINYINT(1)`로 처리) | 활성화 여부, 로그인 상태 |
| `BLOB` | 바이너리 대형 객체 (이미지, 오디오, 비디오 등) | 파일 데이터 |
| `JSON` | JSON 형식의 데이터를 저장. MySQL 5.7 이상에서 지원. | 유연한 스키마의 설정값, 사용자 프로필 |

## 2. DDL 실습: 첫 데이터베이스와 테이블 만들기

DDL(Data Definition Language)은 데이터베이스 객체의 구조를 정의하고 관리하는 SQL 명령어입니다. `CREATE`, `ALTER`, `DROP` 등이 있습니다.

### 2.1. 데이터베이스 생성 및 선택 (`CREATE DATABASE`, `USE`)

데이터를 저장하기 위한 공간인 데이터베이스를 생성하고, 해당 데이터베이스를 사용하도록 선택합니다.

```sql
-- 데이터베이스 목록 확인
SHOW DATABASES;

-- 새 데이터베이스 생성
CREATE DATABASE company_db;

-- 데이터베이스 선택 (이후의 모든 DDL/DML 작업은 이 데이터베이스 내에서 이루어짐)
USE company_db;

-- 선택된 데이터베이스 확인
SELECT DATABASE();
```

### 2.2. 테이블 생성 (`CREATE TABLE`)

`CREATE TABLE` 문을 사용하여 데이터가 저장될 테이블의 구조를 정의합니다. 컬럼 이름, 데이터 타입, 제약조건 등을 명시합니다.

```sql
CREATE TABLE 테이블명 (
    컬럼명1 데이터타입 [제약조건],
    컬럼명2 데이터타입 [제약조건],
    ...
    [테이블 레벨 제약조건]
);
```

#### 2.2.1. 직원 테이블 (`employees`) 설계 및 생성

직원 정보를 저장하는 테이블입니다.

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY AUTO_INCREMENT, -- 직원 ID (기본 키, 자동 증가)
    first_name VARCHAR(50) NOT NULL,             -- 이름 (필수)
    last_name VARCHAR(50) NOT NULL,              -- 성 (필수)
    email VARCHAR(100) UNIQUE,                   -- 이메일 (고유)
    phone_number VARCHAR(20),
    hire_date DATE NOT NULL,                     -- 고용일 (필수)
    job_id VARCHAR(10) NOT NULL,                 -- 직무 ID (필수)
    salary DECIMAL(10, 2) NOT NULL,              -- 급여 (필수, 소수점 2자리까지)
    department_id INT,                           -- 부서 ID (외래 키)
    INDEX idx_last_name (last_name)              -- 성에 대한 인덱스 (조회 성능 향상, 자세한 내용은 [6.2. 인덱스 최적화 전략](#62-인덱스-최적화-전략)을 참조하세요.)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- AUTO_INCREMENT 시작 값 지정 예시 (테이블 생성 후 또는 ALTER TABLE로 지정 가능)
-- ALTER TABLE employees AUTO_INCREMENT = 1001;
```

#### 2.2.2. 부서 테이블 (`departments`) 설계 및 생성

부서 정보를 저장하는 테이블입니다.

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY AUTO_INCREMENT, -- 부서 ID (기본 키, 자동 증가)
    department_name VARCHAR(100) UNIQUE NOT NULL, -- 부서명 (고유, 필수)
    location VARCHAR(100)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

#### 2.2.3. 프로젝트 테이블 (`projects`) 설계 및 생성

프로젝트 정보를 저장하는 테이블입니다.

```sql
CREATE TABLE projects (
    project_id INT PRIMARY KEY AUTO_INCREMENT,    -- 프로젝트 ID (기본 키, 자동 증가)
    project_name VARCHAR(100) UNIQUE NOT NULL,    -- 프로젝트명 (고유, 필수)
    start_date DATE NOT NULL,                     -- 시작일 (필수)
    end_date DATE,
    budget DECIMAL(15, 2)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 2.3. 테이블 구조 확인 (`DESCRIBE`, `SHOW TABLES`)

생성된 테이블의 구조를 확인하거나, 현재 데이터베이스의 테이블 목록을 조회합니다.

```sql
-- 현재 데이터베이스의 모든 테이블 목록 확인
SHOW TABLES;

-- 특정 테이블의 구조 확인 (컬럼, 타입, 제약조건 등)
DESCRIBE employees; -- 또는 DESC employees;
```

### 2.4. 테이블 수정 (`ALTER TABLE`)

`ALTER TABLE` 문을 사용하여 기존 테이블의 구조를 변경합니다. 컬럼 추가, 삭제, 수정, 제약조건 추가/삭제 등이 가능합니다.

```sql
-- employees 테이블에 department_id 컬럼에 외래 키 제약조건 추가
ALTER TABLE employees
ADD CONSTRAINT fk_department
FOREIGN KEY (department_id) REFERENCES departments(department_id);

-- employees 테이블에 phone_number 컬럼의 데이터 타입 변경
ALTER TABLE employees
MODIFY COLUMN phone_number VARCHAR(30);

-- employees 테이블에 gender 컬럼 추가
ALTER TABLE employees
ADD COLUMN gender ENUM('M', 'F', 'Other') AFTER last_name;

-- employees 테이블에서 phone_number 컬럼 삭제
ALTER TABLE employees
DROP COLUMN phone_number;
```

#### 2.4.1. 컬럼 추가/삭제/수정

*   **컬럼 추가:** `ADD COLUMN`
*   **컬럼 삭제:** `DROP COLUMN`
*   **컬럼 수정:** `MODIFY COLUMN` (데이터 타입, 제약조건 변경) 또는 `CHANGE COLUMN` (컬럼 이름까지 변경)

#### 2.4.2. 제약조건 추가/삭제

*   **제약조건 추가:** `ADD CONSTRAINT`
*   **제약조건 삭제:** `DROP CONSTRAINT` (MySQL에서는 `DROP FOREIGN KEY` 등)

#### 2.4.3. `AUTO_INCREMENT` 값 재설정

`AUTO_INCREMENT` 컬럼의 다음 시작 값을 수동으로 재설정할 수 있습니다. 주로 `TRUNCATE TABLE` 후 `AUTO_INCREMENT` 값을 1부터 다시 시작하고 싶을 때 사용합니다.

```sql
-- employees 테이블의 AUTO_INCREMENT 값을 1001부터 시작하도록 재설정
ALTER TABLE employees AUTO_INCREMENT = 1001;
```

### 2.5. 테이블 삭제 (`DROP TABLE`)

`DROP TABLE` 문을 사용하여 데이터베이스에서 테이블을 완전히 삭제합니다. 테이블의 구조와 데이터가 모두 제거됩니다.

```sql
-- employees 테이블 삭제
DROP TABLE employees;

-- 만약 테이블이 존재하면 삭제 (에러 방지)
DROP TABLE IF EXISTS projects;
```

### 2.6. 임시 테이블 (Temporary Table) 활용

임시 테이블은 현재 세션에서만 존재하고, 세션이 종료되면 자동으로 삭제되는 특별한 테이블입니다. 데이터 분석가가 복잡한 쿼리의 중간 결과를 저장하거나, 여러 단계의 데이터 처리 과정을 분리하여 관리할 때 매우 유용합니다.

*   **생성:** `CREATE TEMPORARY TABLE` 문을 사용하여 생성합니다. 일반 테이블과 동일하게 컬럼과 제약조건을 정의할 수 있습니다.
    ```sql
    CREATE TEMPORARY TABLE temp_high_salary_employees (
        employee_id INT PRIMARY KEY,
        full_name VARCHAR(100),
        salary DECIMAL(10, 2)
    );

    -- SELECT 결과를 기반으로 임시 테이블 생성
    CREATE TEMPORARY TABLE temp_department_avg_salary AS
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id;
    ```

*   **사용:** 일반 테이블처럼 `INSERT`, `SELECT`, `UPDATE`, `DELETE` 등의 DML 작업을 수행할 수 있습니다.
    ```sql
    -- 임시 테이블에 데이터 삽입
    INSERT INTO temp_high_salary_employees (employee_id, full_name, salary)
    SELECT employee_id, CONCAT(first_name, ' ', last_name), salary
    FROM employees
    WHERE salary >= 70000;

    -- 임시 테이블 조회
    SELECT * FROM temp_high_salary_employees;
    ```

*   **삭제:** 세션이 종료되면 자동으로 삭제되지만, 명시적으로 `DROP TEMPORARY TABLE`을 사용하여 삭제할 수도 있습니다.
    ```sql
    DROP TEMPORARY TABLE temp_high_salary_employees;
    ```

**실무적 활용:**
*   **복잡한 쿼리 분해:** 여러 단계로 이루어진 복잡한 분석 쿼리를 임시 테이블을 사용하여 논리적으로 분리하고, 각 단계의 결과를 확인하며 개발할 수 있습니다. 이는 쿼리 디버깅과 가독성 향상에 도움이 됩니다.
*   **중간 결과 저장:** 대규모 데이터셋에서 반복적으로 사용되는 중간 계산 결과를 임시 테이블에 저장하여 쿼리 성능을 향상시킬 수 있습니다. (단, 인덱스 생성 등 최적화 고려)
*   **데이터 전처리:** 원본 데이터를 변경하지 않고, 임시 테이블에서 데이터를 정제하거나 변환하는 작업을 수행할 수 있습니다.
*   **동시성:** 각 세션마다 독립적인 임시 테이블이 생성되므로, 다른 사용자의 작업에 영향을 주지 않습니다.

## 3. 데이터 무결성: 제약조건(Constraints) 활용

데이터 무결성(Data Integrity)은 데이터베이스에 저장된 데이터의 정확성, 일관성, 유효성을 유지하는 것을 의미합니다. 제약조건(Constraints)은 데이터 무결성을 보장하기 위해 테이블의 컬럼에 적용되는 규칙입니다.

### 3.1. 제약조건의 종류와 역할

| 제약조건 | 설명 | 역할 |
| :--- | :--- | :--- |
| `PRIMARY KEY` | 테이블의 각 로우를 고유하게 식별하는 컬럼(들). `NOT NULL`과 `UNIQUE` 속성을 가짐. | 로우의 고유성 보장, 다른 테이블과의 관계 설정 |
| `FOREIGN KEY` | 다른 테이블의 `PRIMARY KEY`를 참조하는 컬럼. | 참조 무결성 보장 (참조하는 데이터가 존재해야 함) |
| `UNIQUE` | 컬럼의 모든 값이 고유해야 함. `NULL`은 여러 번 허용. | 컬럼 값의 고유성 보장 |
| `NOT NULL` | 컬럼에 `NULL` 값을 허용하지 않음. | 필수 데이터 누락 방지 |
| `DEFAULT` | 컬럼에 값을 명시하지 않을 경우 자동으로 삽입될 기본 값. | 데이터 입력 편의성, 기본값 설정 |
| `CHECK` | 컬럼에 저장될 값의 범위나 조건을 정의. | 데이터의 유효성 검사 (예: 나이는 0 이상) |

#### 3.1.1. `PRIMARY KEY`: 기본 키

테이블의 로우를 고유하게 식별하는 데 사용됩니다. `AUTO_INCREMENT`와 함께 자주 사용됩니다.

*   **대리 키(Surrogate Key) vs 자연 키(Natural Key) (실무적 관점):**
    *   **대리 키 (Surrogate Key):** 비즈니스적인 의미 없이, 오직 로우의 고유 식별을 위해서만 인위적으로 생성된 키입니다. `AUTO_INCREMENT`를 사용하는 `employee_id`가 대표적인 예입니다.
        *   **장점:** 비즈니스 요구사항이 변경되어도 키 값 자체가 변경될 일이 없어 안정적입니다. (예: 사용자의 이메일 주소가 변경되어도 `user_id`는 그대로 유지)
        *   **단점:** 키 값 자체에는 아무런 의미가 없습니다.
    *   **자연 키 (Natural Key):** 비즈니스적인 의미를 가지는 컬럼을 기본 키로 사용하는 것입니다. (예: `주민등록번호`, `이메일 주소`, `ISBN`)
        *   **장점:** 키 값만으로도 데이터의 의미를 파악할 수 있습니다.
        *   **단점:** 비즈니스 로직이 변경되면 키 값 자체가 변경될 수 있어, 이 키를 참조하는 다른 모든 테이블에 영향을 미칩니다. (예: 이메일 주소를 PK로 사용했는데, 사용자가 이메일을 변경하는 경우)
    *   **실무 가이드:** 대부분의 현대적인 데이터베이스 설계에서는 **대리 키를 기본 키로 사용하는 것을 강력히 권장**합니다. 이는 시스템의 유연성과 확장성을 크게 높여주기 때문입니다. 자연 키는 `UNIQUE` 제약조건을 통해 데이터의 고유성을 보장하는 용도로 활용하는 것이 일반적입니다.

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY AUTO_INCREMENT, -- 대리 키
    product_code VARCHAR(20) NOT NULL UNIQUE, -- 자연 키 (또는 비즈니스 키)
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL
);
```

#### 3.1.2. `FOREIGN KEY`: 외래 키 (참조 무결성)

다른 테이블의 기본 키를 참조하여 두 테이블 간의 관계를 설정하고 참조 무결성을 유지합니다.

```sql
-- employees 테이블에 department_id 컬럼에 외래 키 추가
ALTER TABLE employees
ADD CONSTRAINT fk_department
FOREIGN KEY (department_id) REFERENCES departments(department_id)
ON DELETE SET NULL -- 참조되는 부서가 삭제되면 해당 직원의 department_id를 NULL로 설정
ON UPDATE CASCADE; -- 참조되는 부서 ID가 변경되면 해당 직원의 department_id도 함께 변경
```

**`ON DELETE` 및 `ON UPDATE` 옵션:**
*   `CASCADE`: 부모 테이블의 로우가 삭제/업데이트되면 자식 테이블의 관련 로우도 함께 삭제/업데이트됩니다.
*   `SET NULL`: 부모 테이블의 로우가 삭제/업데이트되면 자식 테이블의 외래 키 컬럼을 `NULL`로 설정합니다.
*   `RESTRICT`: 부모 테이블의 로우가 자식 테이블에서 참조되고 있으면 삭제/업데이트를 허용하지 않습니다.
*   `NO ACTION`: `RESTRICT`와 유사하지만, 표준 SQL에서는 지연된 제약조건 검사를 의미합니다. MySQL에서는 `RESTRICT`와 동일하게 동작합니다.

#### 3.1.3. `UNIQUE`: 고유 제약조건

컬럼의 모든 값이 고유해야 함을 보장합니다. `NULL` 값은 여러 번 허용됩니다.

```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) UNIQUE
);
```

#### 3.1.4. `NOT NULL`: 필수 값

컬럼에 `NULL` 값이 저장되는 것을 방지합니다. 데이터 입력 시 해당 컬럼에 반드시 값이 있어야 합니다.

```sql
CREATE TABLE tasks (
    task_id INT PRIMARY KEY AUTO_INCREMENT,
    task_name VARCHAR(255) NOT NULL,
    due_date DATE
);
```

#### 3.1.5. `DEFAULT`: 기본 값

컬럼에 값을 명시하지 않을 경우 자동으로 삽입될 기본 값을 설정합니다.

```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY AUTO_INCREMENT,
    order_date DATETIME DEFAULT CURRENT_TIMESTAMP, -- 현재 시간으로 기본값 설정
    status VARCHAR(50) DEFAULT 'Pending'
);
```

#### 3.1.6. `CHECK`: 값 범위/조건 검사

컬럼에 저장될 값의 범위나 조건을 정의합니다. MySQL에서는 `CHECK` 제약조건이 구문적으로는 허용되지만, 8.0.16 이전 버전에서는 실제로 강제되지 않았습니다. 8.0.16부터는 제대로 동작합니다.

```sql
CREATE TABLE products_with_check (
    product_id INT PRIMARY KEY AUTO_INCREMENT,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL CHECK (price >= 0),
    stock_quantity INT CHECK (stock_quantity >= 0)
);
```

### 3.2. 제약조건 테스트 및 관리

제약조건이 올바르게 작동하는지 확인하고, 필요에 따라 기존 테이블의 제약조건을 관리합니다.

#### 3.2.1. 제약조건 위반 시 동작 확인

제약조건을 위반하는 `INSERT` 또는 `UPDATE` 문을 실행하면 데이터베이스는 오류를 반환하고 작업을 거부합니다.

```sql
-- UNIQUE 제약조건 위반 예시
INSERT INTO users (username, email) VALUES ('john_doe', 'john@example.com');
INSERT INTO users (username, email) VALUES ('john_doe', 'another@example.com'); -- 오류 발생: Duplicate entry for key 'users.username'

-- NOT NULL 제약조건 위반 예시
INSERT INTO tasks (task_id, due_date) VALUES (1, '2025-12-31'); -- 오류 발생: Field 'task_name' doesn't have a default value

-- FOREIGN KEY 제약조건 위반 예시
-- departments 테이블에 존재하지 않는 department_id를 employees 테이블에 삽입 시도
INSERT INTO employees (first_name, last_name, hire_date, job_id, salary, department_id)
VALUES ('Jane', 'Doe', '2025-01-01', 'DEV', 60000, 999); -- 오류 발생: Cannot add or update a child row: a foreign key constraint fails
```

#### 3.2.2. 기존 테이블에 제약조건 추가/삭제

`ALTER TABLE` 문을 사용하여 기존 테이블에 제약조건을 추가하거나 삭제할 수 있습니다.

```sql
-- 기존 employees 테이블에 email 컬럼에 UNIQUE 제약조건 추가
ALTER TABLE employees
ADD CONSTRAINT UQ_employees_email UNIQUE (email);

-- 기존 employees 테이블에서 fk_department 외래 키 제약조건 삭제
ALTER TABLE employees
DROP FOREIGN KEY fk_department;

-- (참고) PRIMARY KEY 삭제 시 인덱스 이름은 PRIMARY
ALTER TABLE products
DROP PRIMARY KEY;
```

## 4. 데이터베이스 설계 기초: 정규화(Normalization)

정규화는 데이터베이스의 중복을 최소화하고 데이터 무결성을 최대화하기 위한 체계적인 과정입니다. 데이터 분석가에게는 잘 정규화된 데이터베이스를 이해하고 쿼리하는 능력이 중요합니다.

### 4.1. 정규화의 필요성 및 목표

*   **필요성:** 데이터 중복으로 인한 저장 공간 낭비, 데이터 불일치(이상 현상) 발생 가능성 증가, 데이터 유지보수 비용 증가 등을 방지하기 위함입니다.
*   **목표:**
    *   데이터 중복 최소화
    *   데이터 무결성 보장
    *   데이터베이스 구조의 안정성 및 확장성 향상
    *   데이터 검색 및 갱신 효율성 증대

*   **데이터베이스 설계와 ERD:**
    정규화 과정은 데이터베이스를 효율적으로 설계하기 위한 핵심 단계입니다. 이 과정에서 **ERD(Entity-Relationship Diagram)**는 데이터베이스의 구조와 테이블 간의 관계를 시각적으로 표현하는 데 사용되는 필수 도구입니다. ERD를 통해 테이블, 컬럼, 기본 키, 외래 키, 그리고 관계(1:1, 1:N, N:M)를 명확하게 정의할 수 있습니다. 잘 설계된 ERD는 데이터베이스의 논리적 구조를 한눈에 파악하게 해주며, 개발자와 분석가 간의 원활한 소통을 돕습니다.
    *   **ERD 도구:** MySQL Workbench, DBeaver, draw.io, Lucidchart 등 다양한 도구를 활용하여 ERD를 작성할 수 있습니다.

*   **데이터 카탈로그/사전의 중요성 (실무적 관점):**
    데이터 분석가는 쿼리를 작성하기 전에 먼저 데이터의 의미를 정확히 파악해야 합니다. 실무 환경의 데이터베이스는 수백, 수천 개의 테이블과 컬럼으로 이루어져 있으며, 이름만으로는 그 의미를 유추하기 어렵습니다. 이때 **데이터 카탈로그(Data Catalog)** 또는 **데이터 사전(Data Dictionary)**이 필수적입니다.
    *   **데이터 카탈로그란?** 데이터에 대한 데이터, 즉 메타데이터(Metadata)를 관리하는 시스템입니다. 테이블, 컬럼, 스키마 정보뿐만 아니라, 각 데이터의 비즈니스적 의미, 데이터 소유자, 데이터 계보(Data Lineage), 데이터 품질 정보 등을 포함합니다.
    *   **신입 분석가의 첫걸음:** 새로운 프로젝트에 투입되면 가장 먼저 데이터 카탈로그를 통해 분석 대상이 되는 테이블과 컬럼의 정의를 확인해야 합니다. 예를 들어, `sales` 테이블의 `amount` 컬럼이 '세금 포함 금액'인지 '세금 미포함 금액'인지, `user` 테이블의 `status` 컬럼의 '1'이 '활성'을 의미하는지 '탈퇴'를 의미하는지 등을 명확히 알아야 정확한 분석이 가능합니다.
    *   **데이터 거버넌스:** 잘 관리된 데이터 카탈로그는 조직의 데이터 거버넌스(Data Governance)의 핵심 요소로, 데이터의 신뢰성과 일관성을 보장하는 역할을 합니다.

*   **데이터베이스 설계와 ERD:**
    정규화 과정은 데이터베이스를 효율적으로 설계하기 위한 핵심 단계입니다. 이 과정에서 **ERD(Entity-Relationship Diagram)**는 데이터베이스의 구조와 테이블 간의 관계를 시각적으로 표현하는 데 사용되는 필수 도구입니다. ERD를 통해 테이블, 컬럼, 기본 키, 외래 키, 그리고 관계(1:1, 1:N, N:M)를 명확하게 정의할 수 있습니다. 잘 설계된 ERD는 데이터베이스의 논리적 구조를 한눈에 파악하게 해주며, 개발자와 분석가 간의 원활한 소통을 돕습니다.
    *   **ERD 도구:** MySQL Workbench, DBeaver, draw.io, Lucidchart 등 다양한 도구를 활용하여 ERD를 작성할 수 있습니다.

*   **데이터 카탈로그/사전의 중요성 (실무적 관점):**
    데이터 분석가는 쿼리를 작성하기 전에 먼저 데이터의 의미를 정확히 파악해야 합니다. 실무 환경의 데이터베이스는 수백, 수천 개의 테이블과 컬럼으로 이루어져 있으며, 이름만으로는 그 의미를 유추하기 어렵습니다. 이때 **데이터 카탈로그(Data Catalog)** 또는 **데이터 사전(Data Dictionary)**이 필수적입니다.
    *   **데이터 카탈로그란?** 데이터에 대한 데이터, 즉 메타데이터(Metadata)를 관리하는 시스템입니다. 테이블, 컬럼, 스키마 정보뿐만 아니라, 각 데이터의 비즈니스적 의미, 데이터 소유자, 데이터 계보(Data Lineage), 데이터 품질 정보 등을 포함합니다.
    *   **신입 분석가의 첫걸음:** 새로운 프로젝트에 투입되면 가장 먼저 데이터 카탈로그를 통해 분석 대상이 되는 테이블과 컬럼의 정의를 확인해야 합니다. 예를 들어, `sales` 테이블의 `amount` 컬럼이 '세금 포함 금액'인지 '세금 미포함 금액'인지, `user` 테이블의 `status` 컬럼의 '1'이 '활성'을 의미하는지 '탈퇴'를 의미하는지 등을 명확히 알아야 정확한 분석이 가능합니다.
    *   **데이터 거버넌스:** 잘 관리된 데이터 카탈로그는 조직의 데이터 거버넌스(Data Governance)의 핵심 요소로, 데이터의 신뢰성과 일관성을 보장하는 역할을 합니다.

### 4.2. 이상(Anomaly) 현상: 삽입, 삭제, 갱신 이상

정규화되지 않은 테이블에서 발생하는 문제점들입니다.

*   **삽입 이상 (Insertion Anomaly):** 데이터를 삽입할 때 불필요한 정보도 함께 삽입해야 하거나, 필요한 정보를 삽입할 수 없는 경우.
    *   예: 부서 정보와 직원 정보가 하나의 테이블에 있을 때, 새로운 부서만 추가하고 싶어도 해당 부서에 속한 직원이 없으면 추가할 수 없는 경우.
*   **삭제 이상 (Deletion Anomaly):** 데이터를 삭제할 때 의도하지 않은 다른 정보까지 함께 삭제되는 경우.
    *   예: 특정 직원을 삭제했더니, 그 직원이 속한 부서의 유일한 직원이어서 부서 정보까지 함께 삭제되는 경우.
*   **갱신 이상 (Update Anomaly):** 중복된 데이터 중 일부만 갱신되어 데이터 불일치가 발생하는 경우.
    *   예: 한 부서의 이름이 여러 로우에 중복되어 있을 때, 일부 로우만 갱신하고 나머지는 갱신하지 않아 부서 이름이 여러 개로 존재하는 경우.

### 4.3. 정규형(Normal Form)의 종류

정규화는 여러 단계의 정규형(Normal Form)을 통해 이루어집니다. 각 정규형은 이전 정규형의 조건을 만족하면서 추가적인 제약조건을 가집니다.

#### 4.3.1. 제1정규형 (1NF)

*   **조건:**
    1.  모든 컬럼이 원자 값(Atomic Value)을 가짐 (더 이상 분해할 수 없는 단일 값).
    2.  모든 로우가 고유하게 식별 가능해야 함 (기본 키 존재).
*   **예시 (비정규화):**
    `employees` 테이블에 `skills` 컬럼이 있고, 한 직원이 여러 스킬을 콤마로 구분하여 저장하는 경우 (예: `'Python, SQL, Excel'`).
*   **1NF 적용:** `skills` 컬럼을 별도의 `employee_skills` 테이블로 분리하여 `employee_id`와 `skill_name`으로 구성.

#### 4.3.2. 제2정규형 (2NF)

*   **조건:**
    1.  1NF를 만족.
    2.  모든 비기본 키 컬럼이 기본 키 전체에 대해 완전 함수 종속적이어야 함 (부분 함수 종속 제거).
    *   **부분 함수 종속:** 기본 키가 복합 키(두 개 이상의 컬럼으로 구성된 키)일 때, 비기본 키 컬럼이 기본 키의 일부 컬럼에만 종속되는 경우.
*   **예시 (비정규화):**
    `order_details` 테이블의 기본 키가 `(order_id, product_id)`이고, `product_name` 컬럼이 `product_id`에만 종속되는 경우.
*   **2NF 적용:** `product_name`을 `products` 테이블로 분리.

#### 4.3.3. 제3정규형 (3NF)

*   **조건:**
    1.  2NF를 만족.
    2.  모든 비기본 키 컬럼이 기본 키에 대해 이행적 함수 종속(Transitive Functional Dependency)을 가지지 않아야 함.
    *   **이행적 함수 종속:** A -> B 이고 B -> C 일 때, A -> C 가 성립하는 경우 (기본 키가 아닌 컬럼이 다른 비기본 키 컬럼에 종속되는 경우).
*   **예시 (비정규화):**
    `employees` 테이블에 `department_name` 컬럼이 있고, `department_id` -> `department_name` 관계가 있는 경우.
*   **3NF 적용:** `department_name`을 `departments` 테이블로 분리.

#### 4.3.4. 보이스-코드 정규형 (BCNF)

*   **조건:**
    1.  3NF를 만족.
    2.  모든 결정자(Determinant)가 후보 키(Candidate Key)여야 함.
    *   **결정자:** 다른 컬럼의 값을 결정하는 컬럼(들).
    *   **후보 키:** 기본 키가 될 수 있는 컬럼(들)의 집합.
*   **설명:** 3NF의 강화된 형태로, 복합 키와 관련된 특정 유형의 종속성을 해결합니다. 실무에서는 3NF까지만 적용하는 경우가 많지만, BCNF는 더 엄격한 무결성을 보장합니다.

### 4.5. 정규화/비정규화 실용적 예시: 주문 데이터베이스 설계

정규화와 비정규화는 이론적인 개념을 넘어 실제 데이터베이스 설계에서 성능과 데이터 무결성 사이의 균형을 맞추는 중요한 의사결정 과정입니다. 다음은 주문 데이터를 예시로 정규화 과정을 살펴보고, 비정규화의 필요성을 이해하는 실용적인 예시입니다.

#### 4.5.1. 비정규화된 초기 주문 테이블 (문제점 파악)

처음에는 모든 주문 관련 정보를 하나의 테이블에 저장한다고 가정해봅시다.

```sql
CREATE TABLE orders_denormalized (
    order_id INT PRIMARY KEY,
    customer_id INT,
    customer_name VARCHAR(100),
    customer_email VARCHAR(100),
    order_date DATE,
    product_id INT,
    product_name VARCHAR(100),
    product_price DECIMAL(10, 2),
    quantity INT,
    total_item_price DECIMAL(10, 2),
    delivery_address VARCHAR(255),
    delivery_status VARCHAR(50)
);
```

**문제점:**
*   **삽입 이상:** 새로운 고객 정보를 추가하려면 반드시 주문이 있어야 합니다.
*   **삭제 이상:** 특정 주문을 삭제하면 해당 주문에만 있던 고객 정보나 상품 정보가 함께 삭제될 수 있습니다.
*   **갱신 이상:** 고객 이름이나 상품 가격이 변경되면, 해당 고객/상품이 포함된 모든 주문 로우를 찾아 일일이 갱신해야 합니다. (데이터 불일치 발생 가능성)
*   **데이터 중복:** 고객 정보, 상품 정보가 주문마다 반복적으로 저장되어 저장 공간 낭비가 심합니다.

#### 4.5.2. 정규화 과정 (1NF, 2NF, 3NF 적용)

위 `orders_denormalized` 테이블을 정규화하여 중복을 제거하고 무결성을 높여봅시다.

**1단계: 1NF 적용 (원자성 확보)**
*   `delivery_address`가 여러 정보를 포함할 수 있다면 분리 (예: `street`, `city`, `zip_code`).
*   여기서는 이미 원자성을 만족한다고 가정하고 다음 단계로 진행합니다.

**2단계: 2NF 적용 (부분 함수 종속 제거)**
*   `orders_denormalized` 테이블의 기본 키는 `order_id`입니다.
*   `product_name`, `product_price`는 `product_id`에만 종속됩니다.
*   `customer_name`, `customer_email`은 `customer_id`에만 종속됩니다.

이를 해결하기 위해 `products` 테이블과 `customers` 테이블을 분리합니다.

```sql
-- products 테이블 (상품 정보)
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    product_price DECIMAL(10, 2) NOT NULL
);

-- customers 테이블 (고객 정보)
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    customer_email VARCHAR(100) UNIQUE
);

-- orders 테이블 (주문 정보 - 주문 자체의 속성)
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL, -- FK to customers
    order_date DATE NOT NULL,
    delivery_address VARCHAR(255),
    delivery_status VARCHAR(50),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- order_items 테이블 (주문 상세 - N:M 관계 해소)
-- 하나의 주문에 여러 상품, 하나의 상품이 여러 주문에 포함될 수 있으므로 별도 테이블 필요
CREATE TABLE order_items (
    order_item_id INT PRIMARY KEY AUTO_INCREMENT,
    order_id INT NOT NULL, -- FK to orders
    product_id INT NOT NULL, -- FK to products
    quantity INT NOT NULL,
    total_item_price DECIMAL(10, 2) NOT NULL,
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

**3단계: 3NF 적용 (이행적 함수 종속 제거)**
*   위 `orders` 테이블에서 `customer_id` -> `customer_name`, `customer_email`과 같은 이행적 종속성은 이미 `customers` 테이블로 분리되어 제거되었습니다.
*   만약 `orders` 테이블에 `customer_city`와 같은 컬럼이 있고, `customer_id` -> `customer_address` -> `customer_city`와 같은 관계가 있다면, `customer_city`를 `customers` 테이블로 옮겨야 합니다.

**정규화된 스키마 요약:**
*   `customers` (customer_id PK, customer_name, customer_email)
*   `products` (product_id PK, product_name, product_price)
*   `orders` (order_id PK, customer_id FK, order_date, delivery_address, delivery_status)
*   `order_items` (order_item_id PK, order_id FK, product_id FK, quantity, total_item_price)

#### 4.5.3. 비정규화(Denormalization)의 고려: 분석용 요약 테이블

정규화된 스키마는 데이터 무결성과 중복 제거에 매우 유리하지만, 특정 분석 쿼리에서는 여러 테이블을 `JOIN`해야 하므로 성능 저하가 발생할 수 있습니다. 예를 들어, "일별 총 매출"을 계산하려면 `orders`와 `order_items`를 `JOIN`하고 `GROUP BY`를 수행해야 합니다. 이러한 쿼리가 매우 빈번하게 실행된다면, 의도적으로 비정규화를 고려할 수 있습니다.

**예시: 일별 매출 요약 테이블 (Summary Table)**

```sql
-- 일별 매출 요약 테이블 (물리적인 테이블)
CREATE TABLE daily_sales_summary (
    sale_date DATE PRIMARY KEY,
    total_daily_revenue DECIMAL(15, 2) NOT NULL,
    total_daily_orders INT NOT NULL
);

-- 이 테이블은 매일 배치 작업으로 업데이트됩니다.
-- 예시 쿼리 (매일 자정에 실행)
INSERT INTO daily_sales_summary (sale_date, total_daily_revenue, total_daily_orders)
SELECT
    order_date,
    SUM(oi.quantity * p.product_price) AS total_revenue,
    COUNT(DISTINCT o.order_id) AS total_orders
FROM
    orders o
JOIN
    order_items oi ON o.order_id = oi.order_id
JOIN
    products p ON oi.product_id = p.product_id
WHERE
    order_date = CURDATE() - INTERVAL 1 DAY -- 어제 날짜 데이터만 집계
GROUP BY
    order_date
ON DUPLICATE KEY UPDATE -- 이미 데이터가 있다면 업데이트
    total_daily_revenue = VALUES(total_daily_revenue),
    total_daily_orders = VALUES(total_daily_orders);
```

**비정규화의 장점:**
*   `daily_sales_summary` 테이블을 조회하는 쿼리는 `JOIN` 없이 단일 테이블에서 데이터를 가져오므로 매우 빠릅니다.
*   자주 사용되는 집계 결과를 미리 계산해두어 분석 쿼리의 응답 시간을 단축합니다.

**비정규화의 단점 및 주의점:**
*   **데이터 중복:** `daily_sales_summary` 테이블은 원본 데이터의 집계된 중복을 포함합니다.
*   **데이터 일관성 유지:** 원본 데이터(`orders`, `order_items`, `products`)가 변경될 경우, `daily_sales_summary` 테이블도 반드시 업데이트되어야 합니다. 이를 위해 배치 작업, 트리거, 또는 Materialized View(DBMS 지원 시)와 같은 추가적인 관리 메커니즘이 필요합니다.
*   **저장 공간 증가:** 중복된 데이터로 인해 저장 공간이 증가할 수 있습니다.

**결론:**
정규화는 데이터 무결성과 중복 제거를 위한 기본 원칙이지만, 모든 경우에 최적의 성능을 보장하지는 않습니다. 데이터 분석가는 비즈니스 요구사항과 쿼리 패턴을 고려하여, 필요한 경우 전략적으로 비정규화를 적용하고, 그에 따른 데이터 일관성 유지 방안을 마련해야 합니다. 요약 테이블은 대규모 데이터 분석 환경에서 성능을 최적화하는 매우 효과적인 비정규화 전략 중 하나입니다.
