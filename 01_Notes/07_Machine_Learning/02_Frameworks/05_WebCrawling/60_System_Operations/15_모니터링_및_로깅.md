## 1. "조용한 크롤러가 가장 무섭다"

자동화된 크롤러가 서버에서 조용히 실행되고 있을 때, 우리는 두 가지 가능성을 생각해야 합니다. "잘 돌고 있구나" 또는 "오래전에 죽었지만 아무도 모르고 있구나". 후자의 경우, 몇 주, 몇 달간 데이터 수집이 중단된 사실을 뒤늦게 발견하고 큰 손실을 입을 수 있습니다.

**로깅(Logging)**은 크롤러의 모든 행동과 상태를 상세히 기록하는 것이고, **모니터링(Monitoring)**은 이 기록을 바탕으로 크롤러가 건강하게 동작하는지 감시하는 행위입니다. 문제가 발생했을 때 즉시 알아챌 수 있는 유일한 방법입니다.

## 2. `print()`를 넘어서: Python의 `logging` 모듈

개발 중에는 `print()`로 간단히 변수를 확인할 수 있지만, 운영 환경에서는 다음과 같은 한계 때문에 부적합합니다.

- **출력 제어 불가:** 로그 레벨(DEBUG, INFO, WARNING, ERROR)에 따라 출력을 선택적으로 보거나 끌 수 없습니다.
- **정보 부족:** 타임스탬프, 로그 레벨, 코드가 실행된 파일명 등 문제 해결에 필수적인 맥락 정보가 없습니다.

**Scrapy는 Python의 `logging` 모듈을 기반**으로 한 강력한 로깅 시스템을 내장하고 있습니다.

**`settings.py`에서 로깅 설정:**
```python
# mycrawler/settings.py

# 로그 레벨 설정: INFO 레벨 이상의 로그만 기록 (DEBUG는 제외)
LOG_LEVEL = 'INFO'

# 로그를 저장할 파일 경로
LOG_FILE = 'crawler.log'

# 로그 인코딩
LOG_ENCODING = 'utf-8'

# True로 설정하면 로그를 파일과 표준 출력(콘솔)에 모두 기록
LOG_STDOUT = False
```

**스파이더에서 로그 남기기:**
스파이더 내에서는 `print()` 대신 `self.log()` 메서드를 사용합니다.
```python
import logging

class MySpider(scrapy.Spider):
    # ...
    def parse(self, response):
        self.log("크롤링을 시작합니다.", level=logging.INFO)
        try:
            # ... 데이터 추출 로직 ...
            yield item
        except Exception as e:
            self.log(f"파싱 중 에러 발생: {e}", level=logging.ERROR)
```

## 3. 크롤러의 건강 지표: 핵심 모니터링 항목

단순히 로그를 쌓는 것을 넘어, 크롤러의 상태를 파악할 수 있는 핵심 지표(Metric)들을 주기적으로 확인해야 합니다. Scrapy는 실행 중에 다양한 통계 정보를 수집하며, 이는 크롤러가 종료될 때 로그에 출력됩니다.

- **`downloader/response_status_count/...`**: `200`, `404`, `503` 등 HTTP 상태 코드별 응답 횟수. `4xx`, `5xx` 에러가 급증한다면 사이트 구조 변경이나 차단을 의심할 수 있습니다.
- **`item_scraped_count`**: 수집된 아이템의 총 개수. 이 값이 갑자기 `0`이 된다면 스파이더의 선택자(selector)가 더 이상 유효하지 않다는 강력한 신호입니다.
- **`log_count/ERROR`**: 에러 로그의 발생 횟수. 에러가 없는지 항상 확인해야 합니다.
- **`finish_reason`**: 스파이더가 종료된 이유. `finished`가 정상이며, `shutdown`이나 다른 이유라면 원인을 파악해야 합니다.
- **`elapsed_time_seconds`**: 총 실행 시간. 실행 시간이 비정상적으로 길어지면 성능 문제를 의심할 수 있습니다.

## 4. 문제가 생겼을 때 즉시 알기: 장애 알림

모니터링이 수동적인 감시라면, **알림(Alerting)**은 문제가 발생했을 때 우리에게 능동적으로 알려주는 시스템입니다.

- **`cron`과 이메일:** `cron` 작업 실행 시 에러가 발생하면, 그 결과를 메일로 보내도록 설정할 수 있습니다. 가장 간단한 형태의 알림입니다.
- **Airflow의 알림 기능:** Airflow는 태스크(task) 실패 시 이메일이나 슬랙(Slack)으로 알림을 보내는 기능을 내장하고 있습니다. 운영 환경에서는 이 기능이 매우 중요합니다.
    ```python
    # Airflow DAG 파일 내에서 Operator 설정
    crawl_task = BashOperator(
        task_id='run_crawler',
        bash_command='...',
        email_on_failure=True,
        email='devops-team@example.com',
    )
    ```
- **외부 모니터링 서비스 연동 (고급):**
    - **Sentry, Datadog:** 애플리케이션 에러 및 성능 모니터링 전문 서비스입니다. Scrapy와 연동하여 에러가 발생할 때마다 상세한 정보(에러 내용, 발생 위치, 관련 변수 등)를 Sentry나 Datadog 대시보드로 보내고, 설정된 규칙에 따라 담당자에게 즉시 알림을 보낼 수 있습니다.
    - **Prometheus + Grafana:** 수집된 통계 정보(e.g., `item_scraped_count`)를 시계열 데이터베이스(Prometheus)에 저장하고, 이를 대시보드(Grafana)로 시각화하여 추이를 모니터링합니다. 특정 임계값(e.g., 아이템 수가 2회 연속 0개)을 넘으면 Alertmanager를 통해 알림을 보낼 수 있습니다.

---

**핵심 요약:** **로깅**은 비행기의 블랙박스처럼 모든 것을 기록하는 것이고, **모니터링**은 조종사가 계기판을 보는 것이며, **알림**은 계기판에 경고등이 들어오는 것입니다. 안정적인 자동화 시스템을 위해서는 이 세 가지가 모두 필수적입니다.**으로 한 강력한 로깅 시스템을 내장하고 있습니다.
